# governance cohort

Cohort: `governance`. Ratified by the governance batch against #40's
strategy and #44's row generator, covering issue #65's own next-batch list:
the Config remainder (rules, aggregators, conformance packs), Control
Tower, License Manager, Organizations, Resource Explorer, Resource Groups,
the Service Catalog remainder plus AppRegistry, and Audit Manager.
Well-Architected was named in the recipe but proposed no types this cycle
- `go run ./tools/row-gen` has no `AWS::WellArchitected::*` section at all,
so there was nothing to ratify or reject there. Mechanism: #48 (see
`live/e2e/estates/example/README.md` for the proof-of-mechanism cohort).
Generated by `tools/estate-gen` (issue #56) from hashicorp/aws 6.58.0's
schema and `internal/live/identity/table.go`'s identity table.

This cohort exercises every type this batch ratified into
`internal/live/lint/admission.go` and `internal/live/identity/table.go`:
24 types across nine services. No single CFN service name unifies the
batch, so regenerate with an explicit `-types` list:

```
go run ./tools/estate-gen -cohort governance -types aws_config_config_rule,aws_config_configuration_aggregator,aws_config_conformance_pack,aws_config_organization_conformance_pack,aws_config_remediation_configuration,aws_controltower_baseline,aws_controltower_control,aws_controltower_landing_zone,aws_organizations_account,aws_organizations_organizational_unit,aws_organizations_policy,aws_organizations_resource_policy,aws_resourceexplorer2_index,aws_resourceexplorer2_view,aws_resourcegroups_group,aws_servicecatalog_portfolio,aws_servicecatalog_portfolio_share,aws_servicecatalog_product,aws_servicecatalog_provisioned_product,aws_servicecatalogappregistry_application,aws_servicecatalogappregistry_attribute_group,aws_servicecatalogappregistry_attribute_group_association,aws_auditmanager_assessment,aws_auditmanager_framework -out /tmp/estate-gen/governance
```

## Rejected

**License Manager**: `aws_licensemanager_grant` is row-gen's only proposal
in this service, and its server-assigned-ARN identity is genuinely clean -
but `live/survey-full.json`'s real-schema signal says it is untaggable
with no native list resource in the pinned v6.59.0 provider. None of this
package's four admission paths (`internal/live/doc.go`) can recover an
existing grant: no marker (untaggable), no list-and-content-match (no list
resource), no client-named or parent-derived path either (the ARN is
wholly server-minted). A clean import grammar is not the same claim as a
working admission path.

**Organizations**: `aws_organizations_organization` (the org singleton)
is row-gen's proposal for a server-assigned ID, confirmed clean against
the provider's docs - but it carries the identical untaggable/unlistable
shape as the License Manager grant above, so it is unratified for the same
reason. This is why the batch's own named scope ("accounts, OUs,
policies") never listed the organization singleton itself.
`aws_organizations_policy_attachment` (row-gen: evidence-only,
property-child of `AWS::Organizations::Policy`) is deferred as follow-on
work, not named in this batch's scope. No delegated-admin type exists
under `AWS::Organizations::*` in this cycle's registry pool at all - the
DelegatedAdmin shape lives on individual services (SecurityHub's own
`aws_securityhub_organization_admin_account`, already evidence-only and
out of this batch anyway).

**Config**: this batch's own named scope was "clean proposals only," so
four evidence-only/needs-hand-separator types are deferred rather than
ratified even though independent verification found clean answers for two
of them: `aws_config_configuration_recorder` and
`aws_config_delivery_channel` are both registry-laggard (row-gen's
evidence-only call comes from `registry.json`'s opaque `Id`
`primaryIdentifier`, which CloudFormation never actually returns for
either type - but the provider's own docs document a plain, clean
name-based import for both). `aws_config_aggregate_authorization` is a
needs-hand-separator composite the provider's docs resolve cleanly too
(`account_id:authorized_region`, colon-joined) but, again, out of this
batch's scope. The three `OrganizationConfigRule` aliases
(`aws_config_organization_custom_policy_rule`,
`aws_config_organization_custom_rule`,
`aws_config_organization_managed_rule`) carry the same registry-laggard
shape. All five are left for a future batch.

**Service Catalog remainder**: `aws_servicecatalog_service_action` and
`aws_servicecatalog_tag_option` are both row-gen proposals with clean,
confirmed server-assigned import grammars, but both are untaggable with no
native list resource per `live/survey-full.json` - the same unrecoverable
shape as the License Manager grant and Organizations singleton above.
`aws_servicecatalog_tag_option_resource_association`'s own composite
identity (`tag_option_id:resource_id`, colon-joined, corrected from
needs-hand-separator the same way the portfolio share above is) is
mechanically sound on its own terms, but with `aws_servicecatalog_tag_option`
itself carrying no admission path, a stateless configuration could never
contain an admitted `aws_servicecatalog_tag_option` resource to reference
- deferred alongside `tag_option` rather than admitted on that
technicality. `aws_servicecatalog_principal_portfolio_association` and
`aws_servicecatalog_product_portfolio_association` both document an
import ID that requires `accept_language`, an optional, defaulted
argument this table's `Component` vocabulary has no way to supply when
omitted from configuration - the same literal-fallback gap the messaging
batch's `aws_cloudwatch_event_rule` left unratified.
`aws_servicecatalog_constraint` stays reasoned-none per this batch's own
instruction and was not touched at all - it does not even appear in
row-gen's pool.

## A deliberate Organizations gap: no org mutations against floci

Organizations resources are account-wide by nature: creating an
`aws_organizations_account`, an OU, or an SCP does not scope to one
estate's tag the way a bucket or an EC2 instance does - it mutates the
organization every other estate in the same AWS account lives under. This
batch's identity ratification for the four Organizations types above rests
on clean import evidence alone (server-assigned ID, taggable, confirmed
against the provider's own docs); it makes no separate claim about
`floci`'s ability to serve Organizations operations safely, and this
cohort deliberately does not `terraform apply` any of them against the
pinned floci image.

That caution turned out to be warranted on the evidence, not just
policy: floci was probed live (`docker run` of the pinned
`ghcr.io/lex00/floci` image, then the AWS CLI against its endpoint) before
any decision to skip. `_localstack/health` does not list `organizations`,
`controltower`, `resource-explorer-2`, `resource-groups`, `servicecatalog`,
or `license-manager` among its running services at all (only `config`
does, of the nine services this batch touches - `servicecatalog-
appregistry` is absent from the health payload too but does answer real
requests, see below). A direct `DescribeOrganization` call against the
floci endpoint returns `UnknownOperationException` outright; `ListGroups`
(Resource Groups) and `ListLandingZones` (Control Tower) do not even reach
a service-specific handler - they fall through to floci's S3 request
router and come back as S3-shaped XML errors (`POST on bucket requires
?delete parameter`). None of that is "explicitly serves them safely," so
none of the four Organizations types is exercised here. `terraform
validate` still passes for all four (HCL syntax and provider-schema
correctness, no live call), and that is the extent of this cohort's
Organizations coverage.

## Live floci results (the other eight services)

The same live probe covered every non-Organizations service this batch
touches, and the results were worse than a typical cohort's - most of this
batch's services are control-plane and account-wide, exactly the kind
`floci` (a `LocalStack`-family emulator built for workload-shaped services)
has the least reason to implement deeply.

**Config**: the only service in this batch with real, working handlers.
A live `terraform apply -target=aws_config_config_rule.app` against the
floci endpoint created and destroyed cleanly (`Creation complete after
0s`, then a clean `Destruction complete`). `aws_config_configuration_
aggregator` and `aws_config_remediation_configuration` both fail outright
(`Could not find operation PutConfigurationAggregator` /
`PutRemediationConfigurations` - genuinely unimplemented, not just slow).
`aws_config_conformance_pack` creates successfully on the wire (`Config
Service: PutConformancePack` succeeds) but its own status waiter never
reaches `CREATE_COMPLETE` - floci reports `CREATE_SUCCESSFUL`, a
one-word mismatch against what the provider's own waiter polls for, so
`terraform apply` times out on a resource that in fact exists (confirmed
by the follow-up destroy, which correctly found and removed it). Ratified
here anyway, on identity grounds, the same stance the storage batch's
whole FSx family and the EC2 networking batch's NAT gateway took for their
own blocked-emulator findings. `aws_config_organization_conformance_pack`
was not probed live for the same reason the Organizations types above
were not - it is an org-wide type despite mapping to Config's own CFN
service - but `PutOrganizationConformancePack` is absent from floci's own
handler table by the same evidence as the two "Could not find operation"
rows above.

**Service Catalog AppRegistry**: real requests reach a real handler
(`ListApplications` returns `200 {"Items":[]}`, not a stub), but creation
fails: `aws_servicecatalogappregistry_application` returns an opaque
"empty output" error from the provider's own response parser, and both
`aws_servicecatalogappregistry_attribute_group` and its association
sibling get back an HTML error page instead of JSON
(`invalid character '<' looking for beginning of value` - a route
floci's own JSON API does not actually implement, despite `list`
answering). All three ratified here on identity grounds regardless -
floci's own partial implementation is not evidence against any of their
import identities, which come from the provider's docs independent of
what floci happens to serve.

**Control Tower, Resource Explorer, Resource Groups, Service Catalog
(portfolio/product/provisioned_product/portfolio_share), License
Manager**: `_localstack/health` omits every one of these services, and
direct AWS CLI calls against the floci endpoint confirm it - each returns
either `UnknownOperationException` or falls through to floci's S3 router
entirely. Not probed further; not evidence against identity, same as
Config's own two "Could not find operation" rows. `aws_licensemanager_
grant` is unratified anyway (see Rejected above), so this is moot for it
specifically.

**Audit Manager**: `ListAssessments` returns a raw S3 `NoSuchBucket` XML
error, the same fall-through-to-S3 shape as Resource Groups and Control
Tower above. Not probed further.

## Gating

`go test ./internal/live/lint/... ./internal/live/identity/...` picks this
directory up through `internal/live/flocitest.FixtureDirs` (#48's union
pin) - the coverage those two tests provide is purely structural (every
admitted type has a fixture row and vice versa), independent of whether
`floci` itself can serve any given type.

`terraform validate` passes clean against the pinned provider release
(6.58.0) this fixture pins, for all 24 ratified types including the four
Organizations ones this cohort otherwise does not exercise live.
