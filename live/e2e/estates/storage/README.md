# storage cohort

Cohort: `storage`. Ratified by: the fourth registry-backed ratification
batch against #40's strategy and #44's row generator — EFS, FSx and Backup
(issue #65). Mechanism: #48 (see `live/e2e/estates/example/README.md` for
the proof-of-mechanism cohort, and `live/e2e/estates/messaging/README.md`
for the third registry-backed cohort this one follows). Generated by
`tools/estate-gen`:

```
go run ./tools/estate-gen -cohort storage -types aws_efs_file_system,aws_efs_access_point,aws_fsx_lustre_file_system,aws_fsx_ontap_file_system,aws_fsx_windows_file_system,aws_fsx_openzfs_file_system,aws_fsx_ontap_storage_virtual_machine,aws_fsx_ontap_volume,aws_fsx_openzfs_volume,aws_fsx_openzfs_snapshot,aws_fsx_data_repository_association,aws_fsx_s3_access_point_attachment,aws_backup_plan,aws_backup_vault,aws_backup_framework,aws_backup_report_plan,aws_backup_restore_testing_plan,aws_backup_logically_air_gapped_vault -out /tmp/estate-gen/storage
```

`-types` is explicit rather than the default `-cohort`-name lookup because
this cohort spans three CloudFormation services (EFS, FSx, Backup), and
`tools/estate-gen`'s no-`-types` default only ever matches one CFN service
against the cohort name (`cohort.go`'s `defaultCohortTypes`).

This cohort exercises every type this batch ratified into
`internal/live/lint/admission.go` and `internal/live/identity/table.go`.

## Enumeration source: `aws_efs_file_system` and Cloud Control

`aws_efs_file_system` is issue #47's own worked example, named directly in
`internal/live/lint/admission.go`'s marker-cohort comment as the type that
motivated the Cloud Control enumeration fallback: the AWS provider ships it
no native list resource at all. Confirmed directly against a real
`terraform providers schema -json` pull of the pinned v6.58.0 release: zero
of its 183 `list_resource_schemas` entries name any EFS, FSx or Backup
type, for any type in this cohort.

For `aws_efs_file_system` specifically, the fallback applies:
`live/mapping.json` maps it to `AWS::EFS::FileSystem` via `"name"`, and
`live/registry.json` records that CFN type as listable
(`handlers.list: true`, no `list_required_input`) — so
`internal/live/registry.Roster.EnumerationSource` resolves a CFN type for
it, and `internal/live/discovery/cloudcontrol.go`'s `scanTypeCloudControl`
is the code path that would enumerate it whenever a caller supplies
`Request.CloudControl` and `Request.Roster`. `internal/live/discovery/
cloudcontrol_test.go` uses exactly this type as its worked fake-server
example, confirming the mechanism at the package's own test tier.

It does not apply today at the command layer: `internal/command/
live_plan.go` builds its `discovery.Request` with neither `CloudControl`
nor `Roster` set (confirmed by inspection), so no real `tofu` invocation
reaches this fallback yet — wiring the command layer to it is separate,
follow-on work, not this batch's. The gap is real either way: floci itself
serves no EFS API at all (see "Verifying by hand" below), so even a wired
fallback would have nothing to enumerate against today's pinned emulator.

None of the other types in this cohort get the same fallback:

- The FSx family's `AWS::FSx::FileSystem`, `AWS::FSx::StorageVirtualMachine`,
  `AWS::FSx::Volume` and `AWS::FSx::Snapshot` are all `handlers.list: false`
  in `live/registry.json` — not listable through Cloud Control at all, for
  any of the seven FSx types that fold onto them.
- `aws_efs_access_point` (`AWS::EFS::AccessPoint`) and
  `aws_fsx_data_repository_association` (`AWS::FSx::DataRepositoryAssociation`)
  are both `handlers.list: true` with no required input, so the fallback
  would apply the same way it does for the file system — but neither is the
  type issue #47 named, and neither is exercised end to end here.
- `aws_backup_plan`, `aws_backup_vault`, `aws_backup_framework`,
  `aws_backup_report_plan`, `aws_backup_restore_testing_plan` and
  `aws_backup_logically_air_gapped_vault` need no enumeration fallback at
  all where they are client-named (`vault`, `framework`, `report_plan`,
  `restore_testing_plan`, `logically_air_gapped_vault`): their import
  identity is built straight from configuration. `aws_backup_plan` is the
  one marker-path exception, and its `AWS::Backup::BackupPlan` mapping is
  `via: "service-alias"` in `live/mapping.json` — a via `Roster.cfnType`
  does not index at all (only `"name"` and `"alias"` rows do), so Cloud
  Control enumeration does not reach it either, fallback or not.

## The FSx fold

Four Terraform resource types — `aws_fsx_lustre_file_system`,
`aws_fsx_ontap_file_system`, `aws_fsx_windows_file_system`,
`aws_fsx_openzfs_file_system` — all map to CloudFormation's one generic
`AWS::FSx::FileSystem` via `live/mapping.json`'s `"alias"` rows, confirmed
by reading the four rows directly: identical `cfn_type`, identical
registry evidence (`primary_identifier=["Id"]`,
`read_only_properties=["ResourceARN","Id","LustreMountName","RootVolumeId","DNSName"]`).
None of the four has a `name` argument in the provider's own schema at
all — every one imports by the server-assigned `id` alone, per
`live/import-grammar.json`'s identical "using the `id`" text for all four.
The same fold shape repeats one level down: `aws_fsx_ontap_volume` and
`aws_fsx_openzfs_volume` both map to `AWS::FSx::Volume`.

## Corrected, not merely accepted

Three rows landed here with a different identity than `tools/row-gen`
proposed, the same failure shape the Lambda batch's `aws_lambda_alias` and
the IAM batch's `aws_iam_policy` established: the CloudFormation registry's
`primaryIdentifier ⊆ readOnlyProperties` heuristic pointed at a read-only
ARN or opaque `Id` field that the Terraform provider does not actually
import by.

- `aws_backup_framework` — row-gen proposed server-assigned via the
  registry's `FrameworkArn`. The provider's documented Import section says,
  in its own words, "import Backup Framework using the `id` which
  corresponds to the name of the Backup Framework." `name` is a required
  argument already in configuration. Wired client-named via `name`.
- `aws_backup_report_plan` — the identical sentence in the provider's docs,
  against row-gen's `ReportPlanArn` proposal. Wired client-named via
  `name`.
- `aws_backup_logically_air_gapped_vault` — row-gen proposed nothing
  pastable at all: its own argument-name guess (`backup_vault_name`) was
  unbacked by any schema (v6.58.0 ships no identity schema for this type),
  so it surfaced evidence-only per #44's non-goals. The provider's rendered
  docs (`website/docs/r/backup_logically_air_gapped_vault.html.markdown`)
  resolve it cleanly: "The `id` ... The name of the Logically Air Gapped
  Backup Vault," with `name` required. Wired client-named via `name`, the
  same shape as `aws_backup_vault`.

## Rejected, and deliberately absent

`tools/row-gen`'s EFS, FSx and Backup service sections proposed rows for
this batch to evaluate. Three are rejected — one of them, unusually, on the
opposite finding from the three corrections above: here the registry and
the provider agree, and the honest answer is still that no admission path
recovers the type.

- `aws_efs_mount_target` — row-gen proposed server-assigned via the
  registry's `Id`, and the classification is not in question: the
  provider's documented import command (`terraform import
  aws_efs_mount_target.alpha fsmt-52a643fb`) confirms a server-assigned
  `MountTargetId` with nothing in configuration (`ip_address`,
  `subnet_id`, `file_system_id`) that reconstructs it. What sinks it is
  that no admission path recovers that id from a stateless run: the type
  carries no `tags` argument at all (`live/registry.json`'s
  `AWS::EFS::MountTarget` records `tagging.taggable: false`, and the
  provider's own docs list no tags block), so the marker path has nothing
  to search on; and `live/registry.json`'s
  `handlers.list_required_input` for the same CFN type is
  `["FileSystemId"]` rather than empty, so
  `internal/live/registry.Roster.Listable` reports false and the Cloud
  Control fallback that rescues `aws_efs_file_system` above does not apply
  either — `scanTypeCloudControl` only ever calls `ListResources` with no
  input. `live/survey-full.json`'s own mechanical classifier reaches the
  same verdict independently: `"path": "moves to Ops"`, `"evidence": "no
  identity schema in v6.58.0; untaggable and no native list resource, so
  no admission path recovers it"`.
- `aws_backup_selection` — row-gen proposed server-assigned via the
  registry's opaque, undocumented `Id`. Unlike the three corrections above,
  the provider agrees with the registry's read here: its real, documented
  import command (`terraform import aws_backup_selection.example
  plan-id|selection-id`) is a two-part composite, and the second half — the
  selection's own Backup Selection identifier — really is server-assigned,
  with no configuration argument that reconstructs it (`plan_id` is a live
  reference to an already-admitted parent, but the selection id is minted
  by AWS Backup and exists nowhere until after create). The type also
  carries no `tags` argument, so the marker path cannot substitute either.
  `live/survey-full.json`'s classifier reaches the same "moves to Ops"
  verdict independently.
- `aws_backup_restore_testing_selection` — row-gen marks this
  needs-hand-separator (a composite `RestoreTestingPlanName` +
  `RestoreTestingSelectionName` primary identifier, per its own
  non-goals). Unusually for that class, `live/import-grammar.json` does
  name the separator this time —
  `"using name:restore_testing_plan_name"` — and the provider's own schema
  confirms both halves are required, client-supplied arguments (`name`,
  `restore_testing_plan_name`), not a server-assigned value the way the
  selection above is. That makes it a real candidate for a future batch,
  but this batch keeps the standing discipline the Lambda, IAM/ECR and
  messaging batches already established: never hand-write a composite
  row-gen itself declined to propose.

Every property-child ("evidence-only", `via: "fold"`) row row-gen printed
for EFS and Backup — `aws_efs_backup_policy`, `aws_efs_file_system_policy`,
`aws_efs_replication_configuration`, `aws_backup_vault_lock_configuration`,
`aws_backup_vault_notifications`, `aws_backup_vault_policy` — carries no
pastable row by row-gen's own non-goals (issue #44) and is simply outside
this batch's scope, not a rejection.

## Untaggable types

One type in the table above, `aws_fsx_s3_access_point_attachment`, carries
no `tags` argument in the AWS provider (confirmed against both the
provider's own schema pull and `live/registry.json`'s
`AWS::FSx::S3AccessPointAttachment` `tagging.taggable: false`) — the same
shape as `aws_cloudwatch_dashboard` in the messaging batch. Unlike that
batch, this one *is* added to `live/LIMITATIONS.md`'s "Untaggable types
cannot be removed by the sweep" entry and to
`internal/live/stamp/stamp_test.go`'s `untaggableAdmittedTypes`: issue #54
landed since the messaging batch ratified, and the doc's derivation now
reads `live/survey-full.json`'s full registry-backed roster
(`tools/survey-gen/untaggable_render.go`) rather than only the curated 68,
so there is no longer a roster boundary to carve around. Regenerated with
`go run ./tools/survey-gen -render`.

`aws_efs_mount_target` would have hit this same untaggable shape from
*inside* an admitted type, but it never gets there — see "Rejected, and
deliberately absent" above for why untaggability is only one of two
reasons it stays out entirely.

## Verifying by hand

```
docker run -d --rm -p 4621:4566 --name tofu-storage-cohort-verify floci/floci:latest
export AWS_ENDPOINT_URL=http://localhost:4621 AWS_ACCESS_KEY_ID=test \
       AWS_SECRET_ACCESS_KEY=test AWS_REGION=us-east-1

terraform init
terraform validate

docker rm -f tofu-storage-cohort-verify
```

`terraform validate` passes against the real provider release (6.58.0) this
fixture pins — confirming every argument name, block and enum member above
is real, not just registry-plausible (see "Files" above for what it took to
get there). A full `apply` was not attempted against this fixture: FSx and
EFS both need real VPC subnets to create anything at all, the same
VPC-and-friends problem `estates/example/README.md` notes for its own
fixture, and — as the probing below found — neither service is served by
the pinned emulator regardless. Instead, ratification probed the pinned
emulator directly with the AWS CLI against each ratified type's create/list
operation, the same standard of evidence the Lambda and messaging batches'
full applies established, and found the emulator's actual coverage even
narrower than "EFS and FSx are unserved" predicted:

- `efs create-file-system` and (by the complete absence of an `"efs"` key
  in `/_localstack/health`'s services map) every other EFS operation:
  unserved. The call does not even reach an EFS-shaped handler — floci
  returns an S3 `InvalidArgument` error body ("POST requires either
  ?uploads, ?uploadId, ?restore or ?select parameter"), the same
  mis-routing symptom the messaging batch saw shaped differently.
- `fsx create-file-system`: unserved, and unlike EFS, this one fails
  loudly and honestly — `UnknownOperationException: Unknown operation:
  AWSSimbaAPIService_v20180301.CreateFileSystem`. `/_localstack/health`
  carries no `"fsx"` key either.
- `backup create-backup-vault` and `backup list-backup-vaults`: **work**,
  cleanly, end to end — floci's `backup: running` health entry is not a lie
  for this operation pair.
- `backup create-backup-plan`: **works** the same way.
- `backup create-framework`, `backup create-report-plan`,
  `backup create-restore-testing-plan` and
  `backup create-logically-air-gapped-backup-vault`: all four fail with
  the identical S3-shaped mis-routing symptom EFS hit above (`InvalidArgument`
  "POST requires either ?uploads..." for the first two,
  `NoSuchBucket` for the latter two) — `/_localstack/health` says
  `backup: running`, but four of the six Backup operations this batch
  ratified are not actually implemented behind it.

None of this is evidence against any type's admission: identity and
enumeration are properties of the provider and the CloudFormation registry,
not of one emulator's completeness — the same standing position the
Lambda and messaging batches' READMEs take for their own floci gaps.
`aws_backup_vault` and `aws_backup_plan` are the two types in this cohort
with a clean, real floci round-trip; every other type here is ratified on
provider-documentation evidence with the gap above written down rather than
hidden.
