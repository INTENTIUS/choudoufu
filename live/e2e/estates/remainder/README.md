# remainder cohort

Cohort: `remainder`. Ratified by the REMAINDER ratification batch (issue
#65's own recipe): everything left in `tools/row-gen`'s proposal pool once
every concurrently-worked batch's own scope is excluded — SageMaker; the
Media\* family and IVS/IVSChat; Connect, WorkSpaces and WorkSpacesWeb;
Bedrock\*, Location, Lex and the other AI services; Config, Organizations,
the Resource\* services, LicenseManager, ServiceCatalog\*, ControlTower and
AuditManager; and the databases and networking-advanced agents' own scopes
(Redshift\*, OpenSearch\*, Neptune\*, DocDB\*, Timestream, QLDB, MemoryDB,
Cassandra, NetworkFirewall, NetworkManager, VpcLattice, GlobalAccelerator).
What's left is a long tail: roughly 90 services, most contributing only a
handful of types each. Mechanism: #48 (see `live/e2e/estates/example/README.md`
for the proof-of-mechanism cohort). Generated by `tools/estate-gen` (issue
#56) from hashicorp/aws 6.58.0's schema and `internal/live/identity/table.go`'s
identity table:

```
go run ./tools/estate-gen -cohort remainder -types <see GENERATED.md for the authoritative 24-type roster>
```

### A structural check this batch ran after the fact

Wave three's finding prompted a direct check of every other type this
batch's own contribution admits against the same
`live/survey-full.json` signal (`taggable: false`, `list_resource: false`,
`identity_schema: false` — the automated pass's own "moves to Ops, no
admission path recovers it" classification). 28 more types in this
batch's own final 184 share that exact signal shape. All 28 were
independently confirmed safe rather than dropped, for one of three
reasons the automated signal does not itself distinguish:

- **Client-named or parent-derived, not marker-path at all**
  (`aws_devopsguru_resource_collection`, `aws_appsync_api_cache`,
  `aws_appsync_domain_name_api_association`): the identity is read
  straight from a configuration argument (or a parent's own identity
  attribute), so whether the type itself is listable is irrelevant — no
  discovery of *this* type ever happens.
- **A genuine one-per-account or one-per-region singleton**
  (`aws_securityhub_account`, `aws_securityhub_organization_configuration`,
  `aws_macie2_account`, `aws_shield_proactive_engagement`,
  `aws_sesv2_account_vdm_attributes`, `aws_ssmincidents_replication_set`):
  the same shape `aws_ecr_registry_policy` and its two account-singleton
  siblings already established as admissible in the IAM/ECR batch,
  confirmed by inspection that each of these has at most one live
  instance per account (or, for the two fixed-sentinel-id types, is
  literally always the same import string).
- **CloudFormation Cloud Control lists it with no required input**
  (the remaining 20 — the CloudFront policy/identity family,
  `aws_appconfig_extension_association`, `aws_athena_named_query`,
  `aws_efs_mount_target`, `aws_glue_security_configuration`,
  `aws_msk_cluster_policy`, `aws_notifications_event_rule`,
  `aws_notifications_notification_hub`, `aws_route53_cidr_collection`,
  `aws_route53_resolver_dnssec_config`,
  `aws_route53_resolver_query_log_config_association`,
  `aws_route53profiles_resource_association`,
  `aws_route53recoverycontrolconfig_routing_control`,
  `aws_ssmcontacts_plan`, and others): confirmed directly against
  `live/registry.json` that each one's CFN type carries
  `handlers.list: true` with an empty `list_required_input` — the same
  "registry-backed path" `aws_efs_file_system` and `aws_nat_gateway`
  already established as a real, precedent-backed admission mechanism in
  earlier batches (not yet wired to the command layer, the same standing
  gap every prior batch's README already documents, not a blocker to
  admission). 95 types admitted before this session started share this
  exact `taggable: false, list_resource: false` signal shape, confirming
  this is well-trodden ground, not a one-off exception invented here.

## Estate-covered vs identity-only-verified

Building a `terraform-validate`-clean fixture resource, a narrated
Coverage-map row and a hand-verified floci probe for all 184 of this
batch's own admissions is not what ratification gates on: the identity
evidence (the provider's own documented Import section, read and judged
per type) is. So, with the coordinator's own sign-off for this batch
specifically, this cohort holds a **representative 25-type subset**
instead of one resource per admitted type, chosen for service diversity
and a clean `terraform validate` with the least override machinery.
`TestAdmissionTableCoversEstate` and `TestTableCoversFixtureTypes`
(`internal/live/lint/lint_test.go`, `internal/live/identity/identity_test.go`)
were relaxed from an exact bijection to a floor (every fixture type must
be admitted; not every admitted type needs a fixture) specifically to
allow this — see each test's own updated doc comment.

The other **159 types** this batch admits are **identity-only-verified**:
present in `admittedTypesV0` and `DefaultTable`, each one's mechanism
checked against the pinned v6.58.0 provider's own documented Import
section (or, missing one, its Identity Schema or source), but with no
fixture resource and no floci probe. They are listed by service in
"Identity-only-verified types" below, each with its admission mechanism in
one line rather than a full Coverage-map row.

### A correction estate generation caught

`aws_cloudtrail` was accepted as-is from row-gen's raw proposal by this
batch's verification pass (a client-named type via the `arn` argument,
sourced from the provider's own identity schema). Row-gen's `argument:`
line names its source as "provider identity schema
(live/survey-full.json)" — the schema's own `required_for_import` field
name, read literally as a settable configuration argument. Running this
cohort's estate through `terraform validate` refused it directly: `arn` is
Computed-only in the real v6.58.0 wire schema, so `attr("arn")`'s
assumption (this is a configuration argument the run can set) does not
hold. Corrected to `serverAssigned`, discovered by listing, the same
marker path every other CloudTrail-shaped type in this batch takes. This
is the standing argument for keeping a `terraform validate` pass in the
loop even for types a docs-reading verification pass judged clean: the
provider's own wire schema is more precise than its prose docs about which
identity-schema field names are also real configuration arguments.

## Reversed 2026-08-16: five taggable server-minted composites (wall/servermint)

Five types this batch and the `ecs_eks` batch recorded as rejected below
are now admitted: `aws_ecs_task_set`, `aws_eks_pod_identity_association`,
`aws_prometheus_anomaly_detector`,
`aws_service_discovery_private_dns_namespace` and
`aws_vpc_ipam_pool_cidr_allocation`.

The rejections were right about the shape and wrong about what the shape
costs. Each reason said the classifier's flat server-assigned proposal
"drops a config-supplied component" - `cluster`/`service` for the task
set, `workspace_id` for the anomaly detector, `domain_identifier`-style
parent scopes for the rest. That is true of the import ID string, and it
does not matter for a `ServerAssigned` row: the import ID is never built
from `Components` for such a type. It is read back from the cloud, and
`ImportSyntax` is documentation only, as `internal/live/identity/table.go`
says in the field's own doc comment. The shipped table already carries 51
`ServerAssigned` rows whose `ImportSyntax` has a separator in it -
`aws_connect_queue` `INSTANCEID:QUEUEID`, `aws_transfer_agreement`
`SERVER_ID/AGREEMENT_ID` (its `agreement_id` sits under Attribute
Reference in the same doc cache these rejections were read from) - so the
line these four sat behind was not a capability boundary.

What does matter is taggability, and it is the whole test. All four carry
a top-level `tags` argument at v6.59.0 (`live/survey-full.json`
`signals.taggable`), so `internal/live/stamp` writes the ownership marker
and the tag-filtered sweep finds it. The parent scope is not load-bearing:
**parent-scoped enumeration can confirm an identity the configuration has
already narrowed to one; it cannot supply one.** For a taggable type the
marker does the narrowing and the parent only shrinks the candidate set,
which is why these four move and the 38 untaggable members of the same
bucket stay refused - for them there is nowhere to write a marker at all,
and `tools/row-gen/rejected.json` now says so in those words.

All five are reproduced by row-gen's own fresh classifier
(`live/rowgen-convergence.json`: `matched`, no mismatch classes), so
nothing here is a hand-written row standing in for a derivation. Four
needed no generator change at all. The fifth,
`aws_vpc_ipam_pool_cidr_allocation`, needed one in
`tools/importdocs-gen`: its Import section reads "using the allocation
`id` and `pool id`, separated by `_`", and the scrape's clause reader
matched only backticked tokens shaped like snake_case arguments, so it
found one token against a two-segment example, failed its own arity gate,
and emitted no `id_parts` for the page. With the spaced token read, the
`id` segment resolves to the doc's own Attribute Reference and
`tryDocNamedServerSegment` fires the same way it does for the Connect and
Transfer families. Reach of that widening across the pinned v6.59.0 doc
cache, measured rather than assumed: one page of 1,693.
