# ec2-core cohort

Cohort: `ec2-core`. Ratified by: the fourth registry-backed ratification
batch against #40's strategy and #44's row generator — EC2 core
(instances, EBS, ENI; issue #65's own suggested next batch), following the
Lambda, IAM/ECR and messaging batches above it. Mechanism: #48 (see
`live/e2e/estates/example/README.md` for the proof-of-mechanism cohort, and
`live/e2e/estates/lambda/README.md` for the first registry-backed cohort
this one follows).

This cohort exercises every type this batch ratified into
`internal/live/lint/admission.go` and `internal/live/identity/table.go`.
`aws_instance` is this batch's headline type — the repo's long-standing
canonical unadmitted example (`live/e2e/limits/unadmitted-type`,
`live/LIMITATIONS.md`), swapped to `aws_nat_gateway` in the same change. See
that fixture's own comment for why `aws_nat_gateway` is a stable
replacement rather than a type a future batch would immediately have to
re-swap.

Generated by `tools/estate-gen` (issue #56) from `hashicorp/aws` 6.58.0's
schema and `internal/live/identity/table.go`'s identity table. Regenerate
with (`-types` is required here: `ec2-core` is not itself a CloudFormation
service name `defaultCohortTypes` can derive from `live/mapping.json`, since
this batch's scope is "instances and their periphery" within the EC2
service, not the whole thing — see "Scope" below):

```
go run ./tools/estate-gen -cohort ec2-core -types \
  aws_instance,aws_key_pair,aws_placement_group,aws_ec2_fleet,aws_ec2_capacity_reservation,aws_ec2_host,aws_network_interface,aws_network_interface_attachment,aws_network_interface_permission,aws_eip_association,aws_volume_attachment,aws_spot_fleet_request,aws_ebs_snapshot_block_public_access \
  -out live/e2e/estates/ec2-core
```

## Scope

Issue #65 names this batch "EC2 core (instances, EBS, ENI)" as one of
several suggested next batches, distinct from a future batch over the rest
of `tools/row-gen`'s 114-type EC2 registry section — the
VPC/Transit-Gateway/VPN/Client-VPN/IPAM/Verified-Access/route-server/
NAT-gateway families that make up most of that count. This cohort's
thirteen types are exactly "instances and their periphery": the instance
itself, what it launches from and into (key pair, placement group,
capacity reservation, dedicated host), the fleet mechanisms that launch
many at once (EC2 Fleet, Spot Fleet), its network attachment surface
(ENI, ENI attachment, ENI permission, EIP association), its storage
attachment surface (EBS volume attachment — `aws_ebs_volume` itself was
already admitted), and one EBS account/region setting
(`aws_ebs_snapshot_block_public_access`) that files under the same EBS
subcategory the provider's own docs use.

## Coverage map

| Coverage row | Resource block | Why it lands there |
|---|---|---|
| Server-assigned path | `aws_instance.app` | EC2 mints the instance ID (`i-…`) at create time; `ami`/`instance_type`/`subnet_id` describe what to launch, not what comes back. Confirmed against the provider's own identity schema (v6.58.0: required `id`) and its documented import command. |
| Client-named path | `aws_key_pair.app` | Identity is the `key_name` argument, already in config — row-gen proposed this correctly (registry primary identifier `KeyName`, in `create_only_properties` and not `read_only_properties`). Confirmed against the documented import command and the Attribute Reference (`id` = "The key pair name"). |
| Client-named path | `aws_placement_group.app` | Identity is the `name` argument — row-gen filed this **evidence-only** (registry's `GroupName` does not string-match the provider's `name` closely enough for row-gen's classifier), but the provider's real, documented import command settles it independently: `terraform import aws_placement_group.prod_pg production-placement-group`. The one correction this batch makes to row-gen's own classification rather than to the provider's identity. |
| Server-assigned path | `aws_ec2_fleet.app` | EC2 mints the fleet's identifier (`fleet-…`) at create time; `launch_template_config`/`target_capacity_specification` describe what to launch, not the fleet's own identity. |
| Server-assigned path | `aws_ec2_capacity_reservation.app` | EC2 mints the reservation's ID (`cr-…`) at create time; `instance_type`/`instance_platform`/`availability_zone` describe what capacity to reserve, not the reservation's own identity. |
| Server-assigned path | `aws_ec2_host.app` | EC2 mints the dedicated host's ID (`h-…`) at create time; `availability_zone`/`instance_type` describe what the host supports, not the host's own identity. Not named in row-gen's own headline set but the same shape as `aws_ec2_capacity_reservation` alongside it — a natural extension of "instances and their periphery", added by this batch's own judgment. |
| Server-assigned path | `aws_network_interface.app` | EC2 mints the ENI's ID (`eni-…`) at create time; `subnet_id` names where the interface lives, not the interface itself. Confirmed against the provider's own identity schema (v6.58.0: required `id`). |
| Server-assigned path, untaggable | `aws_network_interface_attachment.app` | EC2 mints the attachment's own ID (`eni-attach-…`), distinct from the `instance_id`/`network_interface_id` arguments naming the two ends. The provider's docs export no `id` attribute for this type at all, only `attachment_id`, which is also the documented import ID. Carries no `tags` argument — see "Untaggable types" below. |
| Server-assigned path, untaggable | `aws_network_interface_permission.app` | EC2 mints the permission's own ID, distinct from `network_interface_id`/`aws_account_id`/`permission`. The provider's docs export no `id` attribute, only `network_interface_permission_id`, which is also the documented import ID. |
| Server-assigned path, untaggable | `aws_eip_association.app` | EC2 mints the association's own ID (`eipassoc-…`), distinct from `allocation_id`/`instance_id`/`network_interface_id`, which name what is being associated. |
| Parent-derived path, untaggable | `aws_volume_attachment.app` | Row-gen filed this needs-hand-separator (composite primary identifier `[VolumeId, InstanceId]`, no separator in any schema). The separator is not a guess: `live/import-grammar.json`'s scrape of the provider's own Import section names it directly, `DEVICE_NAME:VOLUME_ID:INSTANCE_ID`, and the provider's own identity schema requires exactly those three arguments (all Required in the Argument Reference too). Parent-derived over `aws_ebs_volume` (already admitted) and `aws_instance` (ratified above in this same batch). |
| Server-assigned path | `aws_spot_fleet_request.app` | EC2 mints the spot fleet request's ID (`sfr-…`) at create time; `launch_specification`/`target_capacity` describe what to launch, not the request's own identity. |
| Literal-concrete path, untaggable | `aws_ebs_snapshot_block_public_access.app` | Row-gen proposed this server-assigned via the registry's `AccountId` — the same singleton-per-account shape as the IAM/ECR batch's three ECR registry-level types. The provider disagrees about the shape: its own identity schema requires nothing for import at all, and the documented import command is always the fixed literal string `"default"`, not an account ID. This is a per-region settings object needing no discovery at all — the table's first entry whose `Components` is a pure literal and whose `ServerAssigned` is deliberately `false`. |

`aws_ebs_volume` and `aws_launch_template` are not coverage rows here: both
were already admitted (the third marker slice, #20), and `aws_eip` likewise
(the survey's original list-plus-content-match slice) — this cohort adds
`aws_eip_association` alongside it, not `aws_eip` itself.

## Rejected, and out of scope

Every pastable proposal `tools/row-gen` made in this batch's
instances/EBS/ENI slice checked out against the provider's real import
behaviour — a first for a registry-ratified batch, worth naming precisely
because the Lambda, IAM/ECR and messaging batches each found at least one
CFN-says-one-thing-provider-says-another mismatch. Nothing above is a
correction to the provider's identity; `aws_placement_group`'s correction
(above) is to row-gen's own classification, not to the identity itself.

Out of scope for this batch, not rejected on the evidence:

- `aws_ec2_instance_connect_endpoint` — a real, server-assigned, cleanly
  proposed type (registry primary identifier `Id`, read-only and not
  create-only), but it is SSH/RDP connectivity infrastructure for reaching
  an instance, not part of the instance's own identity, EBS, or ENI
  periphery this batch's mandate covers. Left for a networking-focused
  batch.
- `aws_nat_gateway_eip_association` and `aws_network_interface_sg_attachment`
  — both evidence-only, property-children row-gen folds onto a parent
  (`AWS::EC2::NatGateway` and `AWS::EC2::NetworkInterface` respectively)
  with no pastable row of their own (issue #44's own non-goals). The
  second parent, `aws_network_interface`, is ratified above; the first,
  `aws_nat_gateway`, is not admitted at all (`live/SURVEY.md`'s
  blocked-emulator: floci loses `subnet_id` on read) and is out of this
  batch's scope regardless.
- The rest of `tools/row-gen`'s 114-type EC2 registry section — VPC,
  Transit Gateway, VPN, Client VPN, IPAM, Verified Access, route server,
  NAT gateway, network ACL, DHCP options, egress-only IGW, flow logs,
  carrier/customer/local gateways — is simply outside "instances and their
  periphery", not evidence-only or needs-hand-separator findings this
  batch touched.

## Untaggable types

Five types in the table above carry no `tags` argument in the AWS
provider: `aws_network_interface_attachment`, `aws_network_interface_permission`,
`aws_eip_association` and `aws_volume_attachment` (their Argument Reference
names no `tags` block at all), plus `aws_ebs_snapshot_block_public_access`
(whose only argument is `state`). None of the five is in `live/survey.json`'s
curated 68 (`aws_instance` and `aws_key_pair` are the only two curated-68
members this batch touches, and both are taggable), so — the same shape
the Lambda batch's `aws_lambda_layer_version` and the messaging batch's
three untaggable types established — `live/LIMITATIONS.md`'s "Untaggable
types cannot be removed by the sweep" entry picks all five up mechanically
through `go run ./tools/survey-gen -render`, which derives that entry from
`live/survey-full.json` (the full registry-backed roster) intersected with
the admission table, not from a hand edit here.

## Hand adjustments beyond the overrides table

None. Every constraint `terraform validate` found — a closed enum
(`state`, `instance_platform`, `default_target_capacity_type`, `strategy`),
an `ExactlyOneOf`/`RequiredWith` the wire schema does not express
(`aws_ec2_fleet`'s `launch_template_specification`, `aws_ec2_host`'s
`instance_family`/`instance_type`, `aws_eip_association`'s
`instance_id`/`network_interface_id`, `aws_spot_fleet_request`'s
`launch_specification`/`launch_template_config`), or a format check
(`aws_network_interface_permission`'s `aws_account_id`,
`aws_spot_fleet_request`'s `iam_fleet_role` ARN, `aws_instance`'s
`ami`/`instance_type`) — was expressible through `tools/estate-gen`'s
`typeOverrides` table (`tools/estate-gen/overrides.go`), the same mechanism
the Lambda and S3 cohorts' overrides use. The cross-resource references
noted in "Files" above are also overrides-table entries, not hand edits to
the generated `.tf`: `identityArgName`'s automatic `parentRef` wiring only
fires for a client-named type's own single-argument identity (issue #56),
so it does not reach a server-assigned type like `aws_instance` or
`aws_network_interface` on its own — four of this cohort's overrides exist
only to point a sibling's `instance_id`/`network_interface_id` at them by
hand, the same way `iamRoleRefExpr` already does for the Lambda cohort's
IAM role.

## Gating

Nothing here runs against a live or emulated cloud yet. `go test
./internal/live/lint/... ./internal/live/identity/...` picks this directory
up through `internal/live/flocitest.FixtureDirs` (#48's union pin) and
checks it by static HCL parse — `TestAdmissionTableCoversEstate` and
`TestTableCoversFixtureTypes` require `admittedTypesV0` and `DefaultTable`
to cover exactly the union of `live/e2e/estate/` and every `estates/*`
cohort, this one included.

`live/e2e/run.sh` and the gated `internal/live/discovery` floci integration
test still stand up only the demo estate (confirmed by inspection: neither
mentions `estates/` or "cohort"). Wiring cohort estates into the gated
apply-against-floci tier is separate follow-on work, the same note
`estates/example/README.md`, `estates/lambda/README.md` and
`estates/messaging/README.md` already make.

`terraform validate` passes against the real provider release (6.58.0)
this fixture pins — confirming every argument name above is real, not
just registry-plausible.

## Verifying by hand

```
docker run -d --rm -p 4611:4566 --name tofu-ec2-core-cohort-verify \
  ghcr.io/lex00/floci@sha256:4753246c0260a22af1056c65993f4d73b0a907729a9580b9baba5d628b6dad34
export AWS_ENDPOINT_URL=http://localhost:4611 AWS_ACCESS_KEY_ID=test \
       AWS_SECRET_ACCESS_KEY=test AWS_REGION=us-east-1

terraform init
terraform validate
terraform apply -auto-approve

terraform destroy -auto-approve
docker rm -f tofu-ec2-core-cohort-verify
```

Run by hand against `internal/live/flocitest`'s own pinned digest during
this batch's ratification (not wired into any automated tier — see
"Gating" above). `terraform validate` passes cleanly (already noted above).
`apply` was more revealing than any prior batch's manual check: of the
thirteen ratified types, only two actually create against this image today.

- `aws_instance.app` creates and destroys cleanly, in about 10s, reaching
  `running` with no waiter hang. `live/SURVEY.md`'s own `blocked-emulator`
  roster records an earlier probe where "floci jumps a new instance
  straight to `terminated`, and the provider's create waits for `running`"
  (lex00/floci#32, closed upstream 2026-08-12) — this run did not reproduce
  that failure against the same pinned digest that note says predates the
  fix. Recorded as observed, not as a correction to `live/SURVEY.md`'s own
  entry: the two probes may have hit different floci behavior (a race, a
  since-changed default) rather than a contradiction, and resolving which
  is out of this batch's scope. Either way it does not change the
  ratification: the identity was already sound on paper before this apply,
  which is what actually justified admitting the type.
- `aws_key_pair.app` created and destroyed cleanly on a first attempt
  against a fresh container. A second attempt against a container that had
  already destroyed one `tofu-ec2-core-cohort-key-pair` failed with
  `InvalidKeyPair.Duplicate` on create — floci's own destroy path does not
  fully clear its key-pair store, an emulator bookkeeping quirk turned up
  by repeat-testing this same fixture by hand, not a gap in the type's
  identity or in a single real run of this estate.
- Eight types fail to create outright, every one with the same shape:
  floci's `/_localstack/health` reports `ec2: running`, but the specific
  EC2 operation each type's create path calls returns
  `UnsupportedOperation: Operation ... is not supported.` —
  `aws_ebs_snapshot_block_public_access.app` (`EnableSnapshotBlockPublicAccess`),
  `aws_ec2_capacity_reservation.app` (`CreateCapacityReservation`),
  `aws_ec2_fleet.app` (`CreateFleet`), `aws_ec2_host.app` (`AllocateHosts`),
  `aws_network_interface.app` (`CreateNetworkInterface`),
  `aws_placement_group.app` (`CreatePlacementGroup`),
  `aws_spot_fleet_request.app` (`RequestSpotFleet`), and
  `aws_volume_attachment.app` (`AttachVolume`, reached only after
  `aws_instance.app` itself creates successfully). The same split the
  messaging batch found for CloudWatch (`monitoring: running`, but
  `PutCompositeAlarm`/`PutDashboard`/`PutMetricStream` all unimplemented) —
  the health check advertises the service, not its operation coverage.
  This is a floci gap (`choudoufu#26` territory), not evidence against any
  of the eight types' admission: identity and enumeration are properties
  of the provider and the registry, not of one emulator's completeness,
  the same standing this batch's own README entries above already argue
  case by case.
- `aws_network_interface_attachment.app` and
  `aws_network_interface_permission.app` were never reached: both
  reference `aws_network_interface.app`, which fails to create first, so
  Terraform never attempts either. Their own identity and Argument
  Reference evidence is independent of this — see the coverage map above —
  and nothing about this run casts doubt on it.
- `aws_eip_association.app` failed on `InvalidAllocationID.NotFound`: this
  fixture's `allocation_id` is a literal placeholder
  (`eipalloc-0123456789abcdef0`), not a real allocation, because `aws_eip`
  is not part of this cohort's own coverage (see "Files" above) and no
  sibling `aws_eip` resource exists in this run to reference the way
  `instance_id` references `aws_instance.app`. Not a floci gap: a real
  configuration referencing a real `aws_eip.id` would not hit this, and a
  manual check that added one confirmed `AssociateAddress` itself is not
  on the eight-type unsupported list above.
