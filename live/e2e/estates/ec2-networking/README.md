# ec2-networking cohort

Cohort: `ec2-networking`. Ratified by: the fifth registry-backed
ratification batch against #40's strategy and #44's row generator — EC2
networking beyond the core (issue #65's own next-batch suggestion): VPC
endpoints (plus services and connection notifications), the Transit
Gateway family, VPN, Client VPN, IPAM, prefix lists, VPC peering, DHCP
options, network ACLs (plus rules), flow logs, and `aws_nat_gateway`.
Mechanism: #48 (see `live/e2e/estates/example/README.md` for the
proof-of-mechanism cohort, and `live/e2e/estates/route53-cloudfront/README.md`
for the fourth registry-backed cohort this one follows). Generated by
`tools/estate-gen`:

```
go run ./tools/estate-gen -cohort ec2-networking -types aws_vpc_endpoint,aws_vpc_endpoint_service,aws_vpc_endpoint_policy,aws_vpc_endpoint_private_dns,aws_vpc_endpoint_route_table_association,aws_vpc_endpoint_subnet_association,aws_vpc_endpoint_security_group_association,aws_ec2_transit_gateway,aws_ec2_transit_gateway_connect,aws_ec2_transit_gateway_connect_peer,aws_ec2_transit_gateway_metering_policy,aws_ec2_transit_gateway_metering_policy_entry,aws_ec2_transit_gateway_multicast_domain,aws_ec2_transit_gateway_peering_attachment,aws_ec2_transit_gateway_policy_table,aws_ec2_transit_gateway_policy_table_association,aws_ec2_transit_gateway_route,aws_ec2_transit_gateway_route_table,aws_ec2_transit_gateway_route_table_association,aws_ec2_transit_gateway_route_table_propagation,aws_ec2_transit_gateway_vpc_attachment,aws_customer_gateway,aws_vpn_connection,aws_vpn_gateway,aws_ec2_client_vpn_endpoint,aws_ec2_client_vpn_route,aws_vpc_ipam,aws_vpc_ipam_pool,aws_vpc_ipam_pool_cidr,aws_vpc_ipam_resource_discovery,aws_vpc_ipam_resource_discovery_association,aws_vpc_ipam_scope,aws_ec2_managed_prefix_list,aws_ec2_managed_prefix_list_entry,aws_vpc_peering_connection,aws_vpc_dhcp_options,aws_vpc_dhcp_options_association,aws_network_acl,aws_network_acl_rule,aws_flow_log,aws_nat_gateway,aws_nat_gateway_eip_association -out live/e2e/estates/ec2-networking
```

`-types` is explicit rather than the default `-cohort`-name lookup because
every type this batch ratified maps to the EC2 CFN service
(`live/mapping.json`), the same service the already-admitted `ec2-core`
cohort's types map to — `tools/estate-gen/cohort.go`'s no-`-types` default
matches by CFN service name alone, so it would pull in every ec2-core type
too, not just this batch's forty-three.

This cohort exercises every type this batch ratified into
`internal/live/lint/admission.go` and `internal/live/identity/table.go`.

## Enumeration source: `aws_ec2_client_vpn_endpoint`

Every other marker-path type in this batch is either natively listable in
the pinned provider (`aws_vpc_endpoint`, `aws_ec2_transit_gateway_metering_policy`,
`aws_flow_log`, `aws_nat_gateway` — confirmed against `live/survey-full.json`'s
`list_resource` signal) or listable through CloudFormation Cloud Control
with no required input (`live/registry.json`'s `handlers.list: true`,
empty `list_required_input`) — the same fallback issue #47's
`aws_efs_file_system` worked example established, not yet wired to the
command layer (see `live/e2e/estates/storage/README.md`'s "Enumeration
source" for the full mechanism trail).

`aws_ec2_client_vpn_endpoint` is this batch's one exception: its
CloudFormation mapping, `AWS::EC2::ClientVpnEndpoint`, is
`handlers.list: false` (no Cloud Control fallback at all), and
`live/survey-full.json` shows the pinned provider ships it no native list
resource either. Ratified anyway — taggable, and the gap is a discovery
mechanism this fork does not yet have, not a fact about the type's
identity, the same standing every prior batch's own documented gaps take.

`aws_vpc_ipam_pool_cidr_allocation` hits the same "list-free" bar from the
other direction and is *not* ratified — see "Rejected, and deliberately
absent" below for why that type's gap is disqualifying while this one's is
not: this type's identity is genuinely server-assigned-and-taggable with no
composable alternative, so the marker path is the only candidate and
`aws_ec2_client_vpn_endpoint` clears it; `aws_vpc_ipam_pool_cidr_allocation`
additionally needs a parent-scoped Cloud Control list Roster.listable
(`internal/live/registry/roster.go`) never grants regardless.

## Corrected, not merely accepted

Sixteen rows landed here with more identity than `tools/row-gen` itself
proposed — the same "needs hand separator" and "evidence-only" promotions
the storage and Route53/CloudFront batches made, here concentrated because
EC2's CloudFormation registry entries for join/entry sub-resources are
unusually thin on `primaryIdentifier` evidence:

- The five VPC endpoint children (`aws_vpc_endpoint_policy`,
  `aws_vpc_endpoint_private_dns`, `aws_vpc_endpoint_route_table_association`,
  `aws_vpc_endpoint_subnet_association`, `aws_vpc_endpoint_security_group_association`)
  carry no CloudFormation registry entry at all (`live/mapping.json` folds
  all five onto `AWS::EC2::VPCEndpoint` with no argument names attached).
  Each has its own documented Import section in the real provider docs at
  the pinned v6.58.0 tag, giving either the parent endpoint's own id
  (policy, private DNS — named singleton children) or a slash-joined
  parent/child composite (the three associations).
- `aws_ec2_managed_prefix_list_entry`, `aws_ec2_transit_gateway_metering_policy_entry`,
  `aws_ec2_transit_gateway_policy_table_association`, `aws_ec2_transit_gateway_route`,
  `aws_ec2_transit_gateway_route_table_association`,
  `aws_ec2_transit_gateway_route_table_propagation`, `aws_ec2_client_vpn_route`
  and `aws_network_acl_rule` were all filed "needs hand separator" by
  row-gen against a composite `primaryIdentifier` with no join character in
  any schema. Each provider Import section supplies the separator directly
  (comma, underscore or colon), confirmed by fetching the page at the
  pinned v6.58.0 tag rather than guessed.
- `aws_nat_gateway_eip_association` was filed evidence-only (a
  property-child fold of `AWS::EC2::NatGateway` with no registry
  `primaryIdentifier` of its own); the provider's own Import section gives
  a complete `nat_gateway_id,allocation_id` grammar.
- `aws_vpc_dhcp_options_association` and `aws_vpc_ipam_pool_cidr` are the
  two rows where the *registry* evidence was not merely thin but actively
  oversold the real shape: row-gen filed both "needs hand separator"
  against a two-part registry `primaryIdentifier`
  (`DhcpOptionsId`+`VpcId`, `IpamPoolId`+`IpamPoolCidrId`), but the real
  provider Import sections resolve to `vpc_id` alone (a VPC has at most one
  DHCP options association) and `cidr_ipam-pool-id` respectively — a
  different, simpler-or-differently-shaped grammar than the registry's own
  composite implied. The same correction shape as the storage batch's
  `aws_backup_framework`/`aws_backup_report_plan`.

## Rejected, and deliberately absent

`tools/row-gen`'s EC2 service section proposed or evidenced rows across
this batch's whole scope; eleven are rejected here, on independent
verification against the pinned provider's own documentation:

- `aws_ec2_client_vpn_authorization_rule` — row-gen proposed
  server-assigned via the registry's opaque `Id`, but the provider's own
  Import section shows the real identity is a composite the registry
  evidence never saw: endpoint ID and target network CIDR, comma-separated
  — and *conditionally* a third segment (a client-chosen group name)
  whenever the rule sets `access_group_id` instead of
  `authorize_all_groups`. Building the two-segment form unconditionally
  would silently address the wrong rule (or none) for every group-scoped
  authorization; this table's `Component` vocabulary has no way to express
  "an extra segment, conditioned on which of two mutually exclusive
  arguments is set" — the same shape the RDS batch's `aws_db_proxy_target`
  rejection already established, here conditioning a whole trailing
  segment rather than one literal within it. Untaggable either way.
- `aws_ec2_client_vpn_network_association` — row-gen proposed
  server-assigned via the registry's opaque `Id`. The provider's Import
  section confirms a composite (endpoint ID, association ID,
  comma-separated) — but the second half is the association's own
  server-minted `cvpn-assoc-…` id, not `subnet_id` or
  `client_vpn_endpoint_id`, so nothing in configuration reconstructs it.
  Untaggable.
- `aws_ec2_transit_gateway_multicast_domain_association`,
  `aws_ec2_transit_gateway_multicast_group_member` and
  `aws_ec2_transit_gateway_multicast_group_source` — row-gen filed all
  three "needs hand separator" against a composite registry
  `primaryIdentifier`. Confirmed directly against the provider's docs at
  the pinned v6.58.0 tag: none of the three carries a `## Import` section
  at all (fetched and read each page in full, past the Argument and
  Attribute Reference sections) — not merely silent on the separator the
  way row-gen's own rule expects, genuinely unimportable — and none
  carries a `tags` argument, so there is no marker path either.
- `aws_network_acl_association` — row-gen proposed server-assigned via the
  registry's opaque `AssociationId`, confirmed against the provider's
  Import section (a bare `aclassoc-…` id). Untaggable (a subnet-to-ACL
  association carries no `tags` argument), and the import id is a third,
  independently server-minted token: neither `subnet_id` nor
  `network_acl_id` — the association's own two configuration arguments —
  appears in it.
- `aws_vpc_endpoint_connection_notification` — row-gen proposed
  server-assigned via the registry's opaque
  `VPCEndpointConnectionNotificationId`, confirmed against the provider's
  Import section (a bare `vpce-nfn-…` id, unrelated to `service_id`/
  `vpc_endpoint_id`). Untaggable.
- `aws_vpc_endpoint_service_allowed_principal` — row-gen found no mapped
  CloudFormation type to fold this onto at all
  (`AWS::EC2::VPCEndpointServicePermissions` has no corresponding
  Terraform resource in `live/mapping.json`) and proposed nothing.
  Independently checked directly against the provider's docs: no
  `## Import` section, and its two arguments
  (`vpc_endpoint_service_id`, `principal_arn`) both required with no
  `tags` argument between them — the same unimportable-and-untaggable
  shape as the three Transit Gateway multicast rejections above.
- `aws_vpc_ipam_pool_cidr_allocation` — row-gen filed this "needs hand
  separator" against a composite registry `primaryIdentifier`. The
  provider's own Import section confirms a real composite (the
  allocation's own id, an underscore, the pool id) — but the first half is
  IPAM's own server-minted `ipam-pool-alloc-…` id, not `ipam_pool_id` or
  `cidr`, so it is not parent-derived. It *is* taggable, so the marker path
  is the only remaining candidate, and that needs an enumeration mechanism
  this type does not have — see "Enumeration source" above.
- `aws_vpn_gateway_attachment` — row-gen filed this "needs hand separator"
  against a composite registry `primaryIdentifier` (`AttachmentType`,
  `VpcId`). The provider's own Import section is unambiguous and stronger
  than a mere gap: "You cannot import this resource." Untaggable either
  way. This is the batch's new unadmitted-type example — see
  `live/e2e/limits/unadmitted-type/main.tf` and `live/LIMITATIONS.md`.
- `aws_vpn_gateway_route_propagation` and `aws_vpn_connection_route` — row-gen
  proposed the first server-assigned via the registry's opaque `Id` and
  filed the second "needs hand separator". Neither provider docs page
  carries a `## Import` section at all, and neither type's schema carries a
  `tags` argument (each is a two- or three-argument join resource) — the
  same unimportable-and-untaggable shape as the Transit Gateway multicast
  rejections above.

Out of scope, never proposed by row-gen and not named in issue #65's own
wording: `aws_vpn_concentrator` (a distinct, newer EC2 networking feature —
VPN Concentrators are not "VPN gateways" or "VPN connections" in the
classic sense the issue names) and every EC2 sub-service this batch's own
scope excludes (Carrier Gateway, Local Gateway/Outposts, Network Insights,
Traffic Mirroring, Verified Access, Route Server, VPC Block Public Access,
VPC Encryption Control).

## Verifying by hand

```
docker run -d --rm -p 4622:4566 --name tofu-ec2-networking-cohort-verify floci/floci:latest
export AWS_ENDPOINT_URL=http://localhost:4622 AWS_ACCESS_KEY_ID=test \
       AWS_SECRET_ACCESS_KEY=test AWS_REGION=us-east-1

terraform init
terraform validate

docker rm -f tofu-ec2-networking-cohort-verify
```

`terraform validate` passes cleanly against the real provider release
(6.58.0) this fixture pins, confirming every argument name, enum member,
CIDR/ARN shape and block structure above is real, not just
registry-plausible. `/_localstack/health` reports `"ec2": "running"` for
the pinned image, but "running" is a service-presence flag, not an
operation inventory — the same distinction the messaging and storage
batches' READMEs already draw. Ratification probed the pinned emulator
directly with the AWS CLI against a representative create/list operation
per family (the same standard of evidence those batches established), and
found EC2's core object model well served but almost everything this
batch's own scope adds unserved:

**Works, cleanly:**

- `ec2 create-vpc`, `create-subnet`, `create-network-acl`,
  `create-network-acl-entry`, `describe-network-acls`: **work** — the
  network ACL family this batch adds rides on EC2's already-admitted core
  plumbing.
- `ec2 allocate-address`, `create-nat-gateway`, `describe-nat-gateways`:
  **work** end to end, including the address association at create time.
- `ec2 create-flow-logs`, `describe-flow-logs`: **work**.
- `ec2 create-vpc-endpoint`, `describe-vpc-endpoints`: **work** for a
  Gateway-type endpoint (`com.amazonaws.REGION.s3`).

**Unserved (`UnsupportedOperation`), despite `ec2: running`:**

- `create-customer-gateway`, `create-vpn-gateway`: unserved — floci
  refuses both VPN Site-to-Site primitives outright, which blocks
  `aws_vpn_connection` (needs a gateway to reference) from being exercised
  at all.
- `create-transit-gateway`: unserved — blocks every Transit Gateway type
  this batch ratified (fourteen of the forty-two), since none has anything
  to attach to without the gateway itself.
- `create-dhcp-options`: unserved — blocks `aws_vpc_dhcp_options` and, in
  turn, `associate-dhcp-options` (`aws_vpc_dhcp_options_association`),
  independently confirmed unserved too.
- `create-managed-prefix-list`: unserved — blocks
  `aws_ec2_managed_prefix_list` and its entry child.
- `create-vpc-peering-connection`: unserved.
- `create-ipam`: unserved — blocks the whole IPAM family (pool, scope,
  resource discovery, resource discovery association, pool CIDR).
- `create-client-vpn-endpoint`: unserved — blocks `aws_ec2_client_vpn_route`
  too, which needs an endpoint to reference.
- `create-vpc-endpoint-service-configuration`: unserved — blocks
  `aws_vpc_endpoint_service`.
- `modify-vpc-endpoint`: unserved — the single operation behind all five
  VPC endpoint children in this cohort (`aws_vpc_endpoint_policy`,
  `aws_vpc_endpoint_private_dns`, and the three `*_association` types), so
  all five are blocked by the one gap.
- `associate-nat-gateway-address`: unserved — blocks
  `aws_nat_gateway_eip_association`, independent of the NAT gateway
  create/list pair above, which does work.

None of this is evidence against any type's admission: identity and
enumeration are properties of the provider and the CloudFormation
registry, not of one emulator's completeness — the same standing position
every earlier batch's README takes for its own floci gaps. Five types in
this cohort (`aws_vpc_endpoint`, `aws_nat_gateway`, `aws_network_acl`,
`aws_network_acl_rule`, `aws_flow_log`) have a clean, real floci
create/list round-trip; every other type here is ratified on provider
documentation evidence with the gap above written down rather than hidden.
