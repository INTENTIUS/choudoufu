# devtools cohort

Cohort: `devtools`. Ratified by: the fifth registry-backed ratification
batch against #40's strategy and #44's row generator, issue #65's recipe —
developer tools (CodeArtifact, CodeBuild, CodeCommit,
CodeConnections/CodeStarConnections, CodeStarNotifications, CodeDeploy,
CodePipeline, and the ECR-public leftover from the IAM/ECR batch's own ECR
section). Mechanism: #48 (see `live/e2e/estates/example/README.md` for the
proof-of-mechanism cohort, and `live/e2e/estates/lambda/README.md` for the
first registry-backed cohort this one follows). Generated by
`tools/estate-gen` (issue #56) from hashicorp/aws 6.58.0's schema and
`internal/live/identity/table.go`'s identity table.

This cohort exercises every type this batch ratified into
`internal/live/lint/admission.go` and `internal/live/identity/table.go`.

Regenerate with:

```
go run ./tools/estate-gen -cohort devtools -types aws_codeartifact_domain,aws_codeartifact_domain_permissions_policy,aws_codeartifact_repository,aws_codeartifact_repository_permissions_policy,aws_codebuild_fleet,aws_codebuild_project,aws_codebuild_report_group,aws_codebuild_webhook,aws_codecommit_repository,aws_codeconnections_connection,aws_codestarconnections_connection,aws_codestarnotifications_notification_rule,aws_codedeploy_app,aws_codedeploy_deployment_config,aws_codedeploy_deployment_group,aws_codepipeline,aws_codepipeline_custom_action_type,aws_codepipeline_webhook,aws_ecrpublic_repository,aws_ecrpublic_repository_policy -out live/e2e/estates/devtools
```

(`-types` is explicit because `defaultCohortTypes` matches a cohort name
against exactly one `live/mapping.json` CFN service, and this cohort spans
nine — the same reason the `data`, `ecs-eks`, `storage` and
`route53-cloudfront` cohorts' own README regenerate commands are
illustrative rather than literally reproducible with `-cohort` alone.)

## Coverage map

### Account-derived path

| Coverage row | Resource block | Why it lands there |
|---|---|---|
| `aws_codeartifact_domain.app` | row-gen proposed server-assigned via the registry's opaque `Arn` — right that the ARN is the identity, but the flat `serverAssigned()` template undersells it the same way it undersold `aws_sns_topic`, `aws_sqs_queue` and `aws_cloudfront_realtime_log_config` in earlier batches: the ARN (`arn:aws:codeartifact:REGION:ACCOUNT:domain/DOMAIN`) is built from the required `domain` argument plus the run's region and account. |
| `aws_codeartifact_repository.app` | Same correction one level deeper: `arn:aws:codeartifact:REGION:ACCOUNT:repository/DOMAIN/REPOSITORY`, built from the required `domain` and `repository` arguments. |
| `aws_codebuild_report_group.app` | row-gen proposed server-assigned via the registry's opaque `Id` (itself the ARN, per the provider's own Attribute Reference). `AWS::CodeBuild::ReportGroup` ships every CFN Registry handler false, so the registry's classification carries no corroborating capability — but the provider's own documented Import section confirms the ARN (`arn:aws:codebuild:REGION:ACCOUNT:report-group/NAME`) is built from the required `name` argument plus region and account, the same account-derived shape as the CodeArtifact rows above. |
| `aws_codepipeline_webhook.app` | row-gen proposed server-assigned via the registry's opaque `Id` — the provider's own Identity Schema requires exactly one field, `arn`, and its documented import command confirms the ARN (`arn:aws:codepipeline:REGION:ACCOUNT:webhook:NAME`) is built from the required `name` argument plus region and account, joined with a colon rather than a slash. |

| Coverage row | Resource block | Why it lands there |
|---|---|---|
| `aws_codeconnections_connection.app` | CodeConnections mints the connection's own ARN at create time, embedding a random connection id no argument reconstructs — genuinely server-assigned, not account-derived. `AWS::CodeConnections::Connection` reports CFN Registry `handlers.list = true` with no required list input, but the pinned provider itself has no native list resource for this type (`live/survey-full.json`), so this is the same Cloud Control fallback shape `aws_efs_file_system` uses in the storage batch — proven at `internal/live/discovery`'s own test tier, not yet reachable from a real run (see that batch's README for the same caveat). |
| `aws_codestarconnections_connection.app` | The predecessor CFN type of the row above, from before the CodeStar Connections service was renamed CodeConnections; not deprecated as of the pinned v6.58.0. Same shape, same Cloud Control fallback. |
| `aws_codestarnotifications_notification_rule.app` | CodeStar Notifications mints the rule's own ARN at create time, embedding a random rule id; the required `name` and `resource` arguments (a display name and the ARN of the thing being watched) do not reconstruct it. Same Cloud Control fallback shape as the two connections above. |

| `aws_codepipeline_custom_action_type.app` | row-gen filed this needs-hand-separator (registry `primaryIdentifier` `["Category", "Provider", "Version"]`, composite, no separator in any schema). `live/import-grammar.json`'s own scraped Import section supplies both the separator and a correction row-gen would not guess from the registry alone: a colon joins all three, and the provider's real argument is `provider_name`, not the registry's `Provider`. |

## Rejected

- **`aws_codebuild_source_credential`** — row-gen proposed server-assigned
  via the registry's opaque `Id`, and the provider's own documented import
  command confirms an ARN (`arn:aws:codebuild:REGION:ACCOUNT:token/SERVERTYPE`)
  — but unlike `aws_codebuild_report_group` above, no argument reconstructs
  it: `server_type` and `auth_type` name the kind of credential, not an
  identifying name, and `token` holds the secret value itself, never echoed
  back. The provider's own Argument Reference carries no `tags` block for
  this type at all (untaggable), and `live/survey-full.json`'s own signal
  agrees there is no native list resource either — no admission path
  recovers a pre-existing instance.

## Untaggable types

Five of the twenty rows above carry no `tags` argument in the pinned
provider's wire schema: `aws_codeartifact_domain_permissions_policy`,
`aws_codeartifact_repository_permissions_policy` and
`aws_ecrpublic_repository_policy` are the three permission-policy folds
(the same shape as `aws_sns_topic_policy` and `aws_sqs_queue_policy` in the
messaging batch — a policy document and a parent reference, nothing else),
and `aws_codebuild_webhook` and `aws_codedeploy_deployment_config` are
explicit in the provider's own docs ("This resource does not support
tags"). All five are added to `internal/live/stamp/stamp_test.go`'s
`untaggableAdmittedTypes` list, and `live/LIMITATIONS.md`'s "Untaggable
types cannot be removed by the sweep" entry picks them up automatically
when regenerated with `go run ./tools/survey-gen -render` (issue #54's
derivation from the full registry roster, not the curated 68).

## Gating

Nothing here runs against a live or emulated cloud automatically. `go test
./internal/live/lint/... ./internal/live/identity/...` picks this directory
up through `internal/live/flocitest.FixtureDirs` (#48's union pin) and
checks it by static HCL parse — `TestAdmissionTableCoversEstate` and
`TestTableCoversFixtureTypes` require `admittedTypesV0` and `DefaultTable`
to cover exactly the union of `live/e2e/estate/` and every `estates/*`
cohort, this one included.

`live/e2e/run.sh` and the gated `internal/live/discovery` floci integration
test still stand up only the demo estate. Wiring cohort estates into the
gated apply-against-floci tier is separate follow-on work, the same note
every earlier cohort's README already makes.

## Verifying by hand

```
docker run -d --rm -p 4622:4566 --name tofu-devtools-cohort-verify \
  ghcr.io/lex00/floci@sha256:4753246c0260a22af1056c65993f4d73b0a907729a9580b9baba5d628b6dad34

export AWS_ENDPOINT_URL=http://localhost:4622 AWS_ACCESS_KEY_ID=test \
       AWS_SECRET_ACCESS_KEY=test AWS_REGION=us-east-1

terraform init
terraform validate
terraform apply -auto-approve

terraform destroy -auto-approve
docker rm -f tofu-devtools-cohort-verify
```

`terraform validate` passes against the real provider release (6.58.0) this
fixture pins — confirming every argument name above is real, not just
registry-plausible.

An `apply` against the pinned `lex00/floci` image was run by hand during
ratification (not wired into any automated tier — see "Gating" above), and
found this emulator's CodeBuild/CodeDeploy/CodePipeline coverage real but
partial, and CodeArtifact/CodeCommit/CodeConnections/CodeStarConnections/
ECR-public entirely absent from its own advertised service list (confirmed
in the container's own startup log, "Enabled services: [...]" — `codebuild`,
`codedeploy` and `codepipeline` are named; `codeartifact`, `codecommit`,
`codeconnections`/`codestar`-anything and an ECR-public variant are not):

- `aws_codedeploy_app.app`, `aws_codedeploy_deployment_config.app`,
  `aws_codedeploy_deployment_group.app`, `aws_codepipeline.app` and
  `aws_codepipeline_webhook.app` all created (and read back) cleanly.
- `aws_codepipeline_custom_action_type.app` creates cleanly (`CreateCustomActionType`
  succeeds and Terraform records it in state) but the very next call, the
  tag round-trip every taggable type's create cycle does
  (`ListTagsForResource`), 404s: `ResourceNotFoundException: Resource not
  found: arn:aws:codepipeline:...:actiontype:Custom/Build/...` — the same
  "advertises the write, not the matching read" gap earlier batches found
  for other services, not evidence against this type's admission.
- `aws_codebuild_project.app`'s own `CreateProject` call succeeds, but the
  provider's post-create read (`BatchGetProjects`) comes back empty, which
  the provider treats as "not found" and fails the apply — the same
  create-vs-read split as the custom action type above, one step earlier
  in the cycle.
- `aws_codebuild_fleet.app` and `aws_codebuild_webhook.app` both fail
  outright at create: `InvalidAction: Action CreateFleet is not supported`
  and `InvalidAction: Action CreateWebhook is not supported` respectively —
  CodeBuild's own service is present, but these two operations are not
  implemented within it. `aws_codebuild_report_group.app` was never reached
  in this run (it names its own `name` via a fixture cross-reference this
  cohort also uses elsewhere, which this apply never resolved) and remains
  independently untested against this image.
- `aws_codeartifact_domain.app`, `aws_codeartifact_domain_permissions_policy.app`,
  `aws_codeartifact_repository.app` and
  `aws_codeartifact_repository_permissions_policy.app` all fail identically:
  every CodeArtifact call returns an HTML error page
  (`deserialization failed ... invalid character '<' looking for beginning
  of value`) rather than a JSON API response — the service is not
  registered in this image at all.
- `aws_codecommit_repository.app`, `aws_codeconnections_connection.app` and
  `aws_codestarconnections_connection.app` each fail with
  `UnknownOperationException: Unknown operation: <ServiceProtocol>.Create*`
  — none of the three operations exists in this image.
- `aws_codestarnotifications_notification_rule.app` was never reached in
  this run — its `resource` argument references
  `aws_codebuild_project.app.arn`, and Terraform will not use a computed
  attribute from a resource whose own apply failed (the read-back gap
  above). CodeStarNotifications is also absent from this image's own
  advertised service list, so it would fail on its own regardless of that
  dependency.
- `aws_ecrpublic_repository.app` (and, downstream of it,
  `aws_ecrpublic_repository_policy.app`) fails with
  `UnknownOperationException: Unknown operation:
  SpencerFrontendService.CreateRepository` — only plain ECR is implemented
  in this image (`ecr` is in the advertised service list; no ECR-public
  variant is).

None of this is evidence against any row's admission above: identity and
enumeration are properties of the provider and the CFN registry, not of one
emulator's implementation completeness — the same framing every earlier
cohort's README already gives its own floci findings.
