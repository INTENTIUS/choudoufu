# ai-location cohort

Cohort: `ai-location`. Ratified by: the sixth registry-backed ratification
batch against issue #65's recipe — Bedrock (Guardrail, Inference Profile),
Bedrock Agents (Agent, Agent Alias, Flow, Knowledge Base, Prompt),
BedrockAgentCore (the v6.59.0 registry snapshot's runtime/gateway/memory/
policy surface — fourteen marker-path types plus Resource Policy),
Location Service (map, place index, route calculator, tracker, geofence
collection, plus the tracker/consumer association), Lex V2 Models (Bot and
Bot Locale), and the thin-coverage Comprehend, Kendra, Q Business and
Rekognition slices. Mechanism: #48 (see `live/e2e/estates/example/README.md`
for the proof-of-mechanism cohort, and `live/e2e/estates/streaming/README.md`
for the fifth registry-backed cohort this one follows).

Generated by `tools/estate-gen` (issue #56) from hashicorp/aws 6.58.0's
schema and `internal/live/identity/table.go`'s identity table. Regenerate
with:

```
go run ./tools/estate-gen -cohort ai-location -types aws_bedrock_guardrail,aws_bedrock_inference_profile,aws_bedrockagent_agent,aws_bedrockagent_agent_alias,aws_bedrockagent_flow,aws_bedrockagent_knowledge_base,aws_bedrockagent_prompt,aws_bedrockagentcore_agent_runtime,aws_bedrockagentcore_agent_runtime_endpoint,aws_bedrockagentcore_api_key_credential_provider,aws_bedrockagentcore_browser,aws_bedrockagentcore_browser_profile,aws_bedrockagentcore_code_interpreter,aws_bedrockagentcore_evaluator,aws_bedrockagentcore_gateway,aws_bedrockagentcore_harness,aws_bedrockagentcore_memory,aws_bedrockagentcore_oauth2_credential_provider,aws_bedrockagentcore_online_evaluation_config,aws_bedrockagentcore_policy_engine,aws_bedrockagentcore_resource_policy,aws_location_geofence_collection,aws_location_map,aws_location_place_index,aws_location_route_calculator,aws_location_tracker,aws_location_tracker_association,aws_lexv2models_bot,aws_lexv2models_bot_locale,aws_comprehend_document_classifier,aws_kendra_index,aws_qbusiness_application,aws_rekognition_collection,aws_rekognition_project,aws_rekognition_stream_processor -out /tmp/estate-gen/ai-location
```

`-types` is explicit rather than the default `-cohort`-name lookup because
this cohort spans nine CFN services (Bedrock, BedrockAgentCore, Location,
Lex, Comprehend, Kendra, QBusiness, Rekognition — `AWS::Bedrock::*` and
`AWS::BedrockAgent*` both fold onto `tools/row-gen`'s single "Bedrock"
grouping in `live/mapping.json`, `AWS::BedrockAgentCore::*` is its own
ninth), and `tools/estate-gen`'s no-`-types` default only ever matches one
CFN service per cohort name — the same reason the streaming and
ec2-networking batches before this one both had to name `-types` explicitly.

This cohort exercises every type this batch ratified into
`internal/live/lint/admission.go` and `internal/live/identity/table.go`.

## Rejected on independent verification

Cross-checked against both `live/survey-full.json`'s per-type
taggable/listable/identity-schema signals and the provider's documented
Argument/Attribute/Import sections at the pinned v6.59.0 tag — not accepted
on the registry's classification alone:

- **`aws_bedrock_guardrail_version`** — row-gen proposed this cleanly
  (registry `GuardrailId,Version` ⊆ readOnlyProperties), but the provider's
  own docs carry no `tags` argument and `live/survey-full.json` confirms it
  untaggable with no native list resource — the same "moves to Ops"
  mechanism gap as `aws_vpc_ipam_pool_cidr_allocation` in the
  ec2-networking batch. The registry evidence is real; nothing discovers it.
- **`aws_bedrockagent_agent_action_group`, `aws_bedrockagent_agent_collaborator`,
  `aws_bedrockagent_agent_knowledge_base_association`, `aws_bedrockagent_data_source`** —
  each mints its own server-assigned id (`action_group_id`,
  `collaborator_id`, `data_source_id`) scoped under a parent agent or
  knowledge base, with no config argument supplying it, and all four are
  untaggable with no native list resource. Unlike `aws_bedrockagent_agent_alias`
  above, taggability does not rescue these.
- **`aws_bedrockagentcore_gateway_target`, `aws_bedrockagentcore_memory_strategy`,
  `aws_bedrockagentcore_workload_identity`** — same shape: a server-assigned
  id with no config-argument source, untaggable, no native list resource.
- **`aws_lexv2models_bot_version`, `aws_lexv2models_intent`,
  `aws_lexv2models_slot`, `aws_lexv2models_slot_type`** — siblings of
  `aws_lexv2models_bot_locale` (ratified above) that do not share its
  fully-reconstructable shape: each mints its own server-assigned id
  (`bot_version`'s own version number, `intent_id`, `slot_id`,
  `slot_type_id`) that is exported but never a config argument, and all
  four are untaggable with no native list resource.

## Deferred, out of this batch's mechanism

`aws_bedrockagentcore_gateway_rule` and `aws_bedrockagentcore_policy` are
both untaggable with a native list resource that requires a parent-scoped
list argument (`gateway_identifier`, `policy_engine_id`) —
`live/survey-full.json`'s own "list + content match" path, which needs
`internal/live/foreign/classify.go`'s `matchTable` (list-plus-content-match
adoption). row-gen's own non-goals explicitly exclude matchTable adoption
rows (issue #44), and no ratification batch to date has touched that table,
so both stay out of scope rather than guessed at.
`aws_bedrockagentcore_registry` shows the same "list + content match" shape
in `live/survey-full.json` but was never proposed by row-gen at all (no
`AWS::BedrockAgentCore::Registry` entry in `live/registry.json` — the
provider's own identity schema is the only evidence for it), noted here so
a future matchTable batch does not have to re-derive it.

## Deferred, out of this batch's named scope

Issue #65's recipe scopes Comprehend, Kendra, Rekognition and Polly to
"only clean proposals," so these are not rejected on the merits, just not
corrected the way Location and Lex V2 Models were in this batch:

- `aws_kendra_data_source`, `aws_kendra_faq` — both "needs hand separator"
  per row-gen (composite `Id`+`IndexId`, no join character in the
  registry). Kendra's own thin CFN registry coverage (3 types total, only
  Index proposed cleanly) is exactly the "mostly thin provider coverage"
  shape this batch's recipe calls out.
- `aws_textract_*`, `aws_polly_*` — no `AWS::Textract::*` or `AWS::Polly::*`
  entry anywhere in `live/registry.json`, the same registry-absent shape as
  the streaming batch's SWF family; row-gen proposes nothing for either
  service.
- `aws_comprehend_entity_recognizer` — the provider ships this resource,
  but it has no `AWS::Comprehend::*` registry entry beyond
  `DocumentClassifier` (row-gen's own "Comprehend (1 types)" count), so
  there is no CFN evidence to ratify against.

```
docker run -d --rm -p 4620:4566 --name tofu-ai-location-cohort-verify \
  ghcr.io/lex00/floci@sha256:4753246c0260a22af1056c65993f4d73b0a907729a9580b9baba5d628b6dad34
export AWS_ENDPOINT_URL=http://localhost:4620 AWS_ACCESS_KEY_ID=test \
       AWS_SECRET_ACCESS_KEY=test AWS_REGION=us-east-1

terraform init
terraform validate
terraform apply -auto-approve

terraform destroy -auto-approve
docker rm -f tofu-ai-location-cohort-verify
```

Applied by hand against the pinned floci image (the same digest
`internal/live/flocitest.defaultImage` pins). Every one of this batch's 35
types is a service this floci build does not usefully emulate yet — none of
them created cleanly, but none of the failures is evidence against any
type's identity; the shapes below are exactly the "floci gap, not an
identity gap" standing every prior batch's own documented gaps take:

- **Seventeen types return an unmapped-route response** — `aws_bedrock_guardrail`,
  `aws_bedrockagent_agent_alias`, `aws_bedrockagent_flow`,
  `aws_bedrockagent_prompt`, `aws_bedrockagentcore_agent_runtime_endpoint`,
  `aws_bedrockagentcore_evaluator`, `aws_bedrockagentcore_gateway`,
  `aws_bedrockagentcore_memory`, `aws_bedrockagentcore_online_evaluation_config`,
  `aws_bedrockagentcore_policy_engine`, `aws_bedrockagentcore_resource_policy`,
  `aws_lexv2models_bot_locale`, `aws_location_geofence_collection`,
  `aws_location_map`, `aws_location_place_index`,
  `aws_location_route_calculator` and `aws_location_tracker` all fail
  identically: `deserialization failed, failed to decode response body,
  invalid character '<' looking for beginning of value`. floci's own
  container log has no matching line for any of these `Create*` calls — no
  warning, no stack trace, nothing — which is what an unmapped REST route
  looks like from the framework's side: a bare HTML 404 page the AWS SDK
  then fails to parse as JSON. Bedrock, Bedrock Agents, BedrockAgentCore,
  Location and Lex V2 Models are simply services this floci build has no
  route table entries for at all, the same "floci coverage gap, not
  evidence against identity" standing the streaming batch's own AppFlow/
  AmazonMQ/KafkaConnect gaps take.
- **Two types return `UnknownOperationException`** — `aws_rekognition_collection`
  (`CreateCollection`) and `aws_rekognition_project` (`CreateProject`).
  floci's Rekognition emulation exists (unlike the eighteen above, it
  answers with a real Rekognition-shaped error rather than a 404) but does
  not implement these two specific operations.
- **One type crashes the provider plugin itself** —
  `aws_bedrockagent_agent`'s `Create` panics with a nil pointer
  dereference inside `terraform-provider-aws`'s own
  `internal/service/bedrockagent/agent.go:203` (confirmed by the stack
  trace naming that exact source location), almost certainly because
  floci's Bedrock Agent stub returns a response shape (an unpopulated
  field the provider assumes is always present) real AWS never sends. This
  is a genuine defect in the pinned provider release when talking to this
  particular emulator response, not a fact about `aws_bedrockagent_agent`'s
  identity — its own registry and provider-doc evidence (see the Coverage
  map above) is independently confirmed regardless. The crash takes the
  shared provider plugin process down mid-apply (terraform's default
  parallelism runs many resources against one shared plugin process), which
  is why nine more types in the same run fail with `Plugin did not respond`
  or `Request cancelled` — `aws_bedrock_inference_profile`,
  `aws_bedrockagent_knowledge_base`, `aws_bedrockagentcore_api_key_credential_provider`,
  `aws_bedrockagentcore_harness`, `aws_qbusiness_application`,
  `aws_rekognition_stream_processor`, `aws_comprehend_document_classifier`,
  `aws_kendra_index` and `aws_lexv2models_bot` — collateral damage from the
  one crash, not nine independent failures, and not evidence against any
  of those nine types either.
- **Four types get far enough to mint a real id, then fail waiting for it
  to become available** — `aws_bedrockagentcore_agent_runtime`,
  `aws_bedrockagentcore_browser`, `aws_bedrockagentcore_browser_profile`
  and `aws_bedrockagentcore_code_interpreter` all fail with `serialization
  failed: input member <x>Id must not be empty` from the provider's own
  post-create `Get*` waiter — floci's `Create*` response accepts the
  request but the id field it should populate comes back empty, so the
  very next read the provider makes to confirm the resource exists fails
  immediately. A create this far along is stronger identity evidence, not
  weaker: the provider's Create call itself succeeds against floci, and the
  gap is specifically in floci's response completeness, not in whether
  these types' identity shape (all four ratified as marker path, see the
  Coverage map above) is real.
- **`aws_bedrockagentcore_oauth2_credential_provider`** fails
  `CreateOauth2CredentialProvider` with `1 validation error(s) found -
  missing required field`, from floci's own stricter-than-real-AWS
  validation of the empty `custom_oauth2_provider_config {}` block this
  cohort's override intentionally leaves minimal (every field inside it is
  Optional per the provider's own docs) — a floci validation gap, not an
  identity gap.

That accounts for 34 of this batch's 35 types (17 + 2 + 1 + 9 + 4 + 1).
The 35th, `aws_location_tracker_association`, depends on both
`aws_location_geofence_collection` and `aws_location_tracker` — both
already failed above — so Terraform never attempted it at all; it carries
no error line of its own, only the two upstream failures it inherits.
  identity gap.
