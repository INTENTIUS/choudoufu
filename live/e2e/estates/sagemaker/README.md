# sagemaker cohort

Cohort: `sagemaker`. Ratified by the SageMaker batch against issue #65's
ratification campaign and #44's row generator — domains, user profiles,
models, endpoints and their configs, notebook instances, feature groups,
model package groups, pipelines, spaces and apps, plus the surrounding
algorithm/hub/image/workteam/monitoring family. Mechanism: #48 (see
`live/e2e/estates/example/README.md` for the proof-of-mechanism cohort, and
`live/e2e/estates/lambda/README.md` for the first registry-backed cohort
this one follows). Generated by `tools/estate-gen` (issue #56) from
hashicorp/aws 6.58.0's schema and `internal/live/identity/table.go`'s
identity table.

`go run ./tools/row-gen`'s SageMaker section proposed 29 types. 27 ratify
here; two are rejected (see "Rejected" below). This batch's own instruction
was to take what row-gen proposes with clean evidence, but SageMaker turns
out to be a service the CFN registry sweeps had already flagged
registry-laggard for several of its types — and independent verification
against the provider's own docs finds that laggardness runs far wider than
row-gen's mechanical classifier alone could see. See "A registry-laggard
family" below: eighteen of this batch's 27 ratified rows correct a
row-gen "evidence-only" or GUESSED-argument verdict once the real
Argument/Attribute Reference (and, for several types, a genuine Terraform
1.12+ Identity Schema) are read directly, not accepted on the registry's
classification alone.

Regenerate with:

```
go run ./tools/estate-gen -cohort sagemaker -types aws_sagemaker_algorithm,aws_sagemaker_app,aws_sagemaker_app_image_config,aws_sagemaker_code_repository,aws_sagemaker_data_quality_job_definition,aws_sagemaker_device_fleet,aws_sagemaker_domain,aws_sagemaker_endpoint,aws_sagemaker_endpoint_configuration,aws_sagemaker_feature_group,aws_sagemaker_hub,aws_sagemaker_image,aws_sagemaker_mlflow_app,aws_sagemaker_mlflow_tracking_server,aws_sagemaker_model,aws_sagemaker_model_card,aws_sagemaker_model_package_group,aws_sagemaker_model_package_group_policy,aws_sagemaker_monitoring_schedule,aws_sagemaker_notebook_instance,aws_sagemaker_notebook_instance_lifecycle_configuration,aws_sagemaker_pipeline,aws_sagemaker_project,aws_sagemaker_space,aws_sagemaker_studio_lifecycle_config,aws_sagemaker_user_profile,aws_sagemaker_workteam -out live/e2e/estates/sagemaker
```

(`-types` names the batch's admitted rows explicitly, the same as the
security cohort's own README explains, rather than relying on
`defaultCohortTypes`' single-service match — SageMaker is in fact a single
CFN service here, so the default match would likely reach the same set, but
naming the rows keeps the regenerate command self-documenting.)

## Rejected

**`aws_sagemaker_device`**: row-gen classified this `[evidence-only]` (its
registry `primaryIdentifier` is the composite `Device/DeviceName`, and the
argument name was GUESSED). Independent verification confirms row-gen's
own caution rather than correcting it: the provider's documented import
command is `device-fleet-name/device-name`, but the resource's own Argument
Reference nests `device_name` inside a Required `device{}` block as an
Optional field (alongside an equally Optional `iot_thing_name`) — neither
is guaranteed present in any given config, and `internal/live/identity`'s
`Component` vocabulary reads top-level resource arguments by name, not
fields nested inside a block. No clean proposal.

**`aws_sagemaker_image_version`**: row-gen proposed server-assigned via the
registry's `ImageVersionArn`. Independent verification finds a real gap
row-gen's registry-only view could not see: the provider's documented
import ID is a comma-delimited `image_name,version` composite, where
`image_name` is a Required argument but `version` is a plain output int
("version - The version of the image." in the Attribute Reference only, no
corresponding argument anywhere in the Argument Reference) — SageMaker AI
assigns each image version its own ordinal at create time, the same way
`aws_lambda_layer_version`'s own version number is server-assigned.
`internal/live/identity`'s `Component` vocabulary composes configuration
arguments, cloud properties and fixed literals; it has nothing that reads a
sibling instance's own not-yet-known server-assigned output mid-composite.
No clean proposal from configuration alone.

Neither rejection is credential-adjacent — issue #65's own standing
instruction to exclude credential-carrying types by rule does not apply to
either: `aws_sagemaker_device` fails on a nested-optional-argument shape,
and `aws_sagemaker_image_version` fails on a missing server-assigned
component, not on carrying a secret or a bearer credential. No type this
batch admits or rejects carries a live-readable secret value of its own —
SageMaker's credential-adjacent surface (model artifacts, container image
credentials, IAM execution roles) is all reference-by-ARN, the same
`aws_iam_role`/`aws_kms_key_id`-argument shape every other admitted AWS
service uses, not a resource that itself holds a password or a token.

## A registry-laggard family

The dominant finding this batch makes is not a one-off correction: for
eighteen of the twenty-three client-named rows above, `live/registry.json`'s
`primaryIdentifier` names a field CFN models as read-only (an opaque `Id`
or an ARN), and row-gen's classifier correctly declines to propose a row on
that evidence alone — either `[evidence-only]` (`rule: primaryIdentifier ⊆
readOnlyProperties`) or a GUESSED argument name from the CFN property,
never backed by a schema. But the AWS provider's own Argument Reference and
Attribute Reference — fetched directly from
`https://github.com/hashicorp/terraform-provider-aws` at the pinned
v6.58.0 tag, not merely `live/import-grammar.json`'s cache — show every one
of these types is actually client-named: its Attribute Reference states
plainly "id - The name of the `<Type>`", and its Import section documents
import by that same name, not by any ARN.

Several of these doc pages carry an unrelated copy-paste artifact in their
worked example. `aws_sagemaker_hub`, `aws_sagemaker_image` and
`aws_sagemaker_model_package_group`'s own Import sections all reuse the
literal string `my-code-repo` — `aws_sagemaker_code_repository`'s own
worked example, pasted into three unrelated doc pages — and
`aws_sagemaker_mlflow_tracking_server`'s Import prose says "using the
`workteam_name`", copied verbatim from the Workteam page below it. In every
case the surrounding Argument Reference and the "using the `name`"
sentence are what this batch trusts, not the reused example string, which
is immaterial to the argument grammar it demonstrates — confirmed
independently against each type's own Argument Reference (which required
argument is named `hub_name`, `image_name`, `model_package_group_name` and
`tracking_server_name` respectively is not in question, whatever example
value the Import section happens to print).

This is exactly the class of correction the security and streaming
batches' own table entries already document one or two instances of
(`aws_guardduty_filter`'s docs-tier correction, `aws_appsync_domain_name_api_association`'s
outright registry disagreement); this batch just finds it concentrated in
one service, which is what motivated writing it up as its own section
rather than repeating the same three-sentence justification eighteen
times in `internal/live/identity/table.go`'s comments.

## A collision, three times over

`tools/estate-gen`'s generic pass wires a required argument to another
resource's own identity argument by matching argument *names*
(`gen.go`'s `parentRef`, via `identityArgName`). Several types this cohort
admits self-identify by a plain `name` argument — `aws_sagemaker_endpoint`,
`aws_sagemaker_notebook_instance` and the shared `aws_iam_role` support
resource among them — so the generic pass wired three *other* types' own
`name` argument to whichever same-`"name"` resource it happened to
encounter first, not to themselves:

- `aws_sagemaker_endpoint_configuration.app`'s own `name` was wired to
  `aws_sagemaker_endpoint.app.name` — an unrelated sibling's name, not its
  own.
- `aws_sagemaker_mlflow_app.app`'s own `name` was wired to
  `aws_iam_role.sagemaker.name` — the shared support role's name.
- `aws_sagemaker_notebook_instance_lifecycle_configuration.app`'s own
  `name` was wired to `aws_sagemaker_notebook_instance.app.name`.

Same collision class as `aws_glue_catalog_database`'s existing entry in
`tools/estate-gen/overrides.go` (the data-plane batch's own "name"
collision with `aws_athena_data_catalog`) and the GuardDuty `detector_id`
collision the security cohort's own README documents, fixed the same way:
`tools/estate-gen/overrides.go` overrides all three back to a real
placeholder name of their own. None of the three is a `terraform validate`
failure — a plain string satisfies the schema whichever resource it names
— so this is a fixture-realism fix, not a constraint fix, the same
distinction `aws_eip_association`'s own override entry draws.

## The space-owned app gap

`aws_sagemaker_app` supports two ownership shapes: `user_profile_name` or
`space_name`, "at least one of ... required". The provider's documented
import command demonstrates only the `user_profile_name`-owned ARN shape
(`arn:aws:sagemaker:REGION:ACCOUNT:app/DOMAIN_ID/USER_PROFILE_NAME/APP_TYPE/APP_NAME`);
no worked example or Argument/Attribute Reference text confirms whether a
space-owned app's ARN substitutes a `space/SPACE_NAME` segment or something
else entirely. CFN's own registry entry for `AWS::SageMaker::App` models
only the `AppName, AppType, DomainId, UserProfileName` shape too — the
space-owned variant is outside what either source documents.

`internal/live/identity/table.go`'s entry for `aws_sagemaker_app` does not
guess: it reads `user_profile_name` specifically, not `space_name` as a
fallback, so a space-owned app's identity simply fails to resolve from
configuration (`ClassNeedsDiscovery`, the honest outcome) rather than
construct an unverified ARN. The same restraint `aws_inspector2_enabler`
and `aws_wafv2_web_acl_rule_group_association` already show elsewhere in
this table for a branching, mode-dependent import shape with no identity
schema to settle which branch applies.

## Untaggable types

`aws_sagemaker_model_package_group_policy` is this batch's one untaggable
type: its Argument Reference names only `region` and
`model_package_group_name`, no `tags` block at all — the same shape every
other resource-policy row in this fork's table already carries
(`aws_secretsmanager_secret_policy`, `aws_s3_bucket_policy`). Every other
ratified row in this cohort carries a `tags` argument, confirmed against
each type's own documented Argument Reference at the pinned v6.58.0 tag.

## Verifying by hand

A pinned floci container (`ghcr.io/lex00/floci`, the same image
`internal/live/flocitest`'s `defaultImage` runs) was probed directly with
the AWS CLI before any ratification decision. SageMaker is absent from
floci's own `/_localstack/health` service list entirely (confirmed against
the live container's own health endpoint: 70 services listed, `sagemaker`
not among them), and every SageMaker operation probed —
`sagemaker:CreateDomain`, `sagemaker:ListDomains`,
`sagemaker:CreateModel` — answers `UnknownOperationException`, the
router-level tell the security cohort's own README already names for
ACM-PCA, GuardDuty, Macie2, SecurityHub and Inspector2: the service has no
handler registered with floci's router at all, not merely an unimplemented
operation within a registered service.

No `terraform apply` against floci was attempted for this cohort, the same
restraint the security batch's README applies to its own five entirely
unserved services above (Secrets Manager, KMS and WAFv2 got a real-provider
`terraform apply` there precisely because they *are* served; nothing here
is). This is a floci gap, not an identity-soundness problem with any row
in this table: issue #65's own recipe treats it as "documented in the
cohort README, not blocking," the same standing every prior batch's own
floci gap already has. A real AWS run would not hit any of these
`UnknownOperationException` responses — SageMaker AI is one of AWS's
largest, most actively developed services, not an edge case floci simply
has not gotten to yet in the way a single missing operation might be.
