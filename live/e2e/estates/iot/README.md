# iot cohort

Cohort: `iot`. Ratified by: the sixth registry-backed ratification batch
against #40's strategy and #44's row generator, issue #65's recipe — IoT
core (things, thing types/groups, policies, topic rules, authorizers,
billing groups, domain configurations, provisioning templates, role
aliases, and one topic rule destination). Mechanism: #48 (see
`live/e2e/estates/example/README.md` for the proof-of-mechanism cohort, and
`live/e2e/estates/lambda/README.md` for the first registry-backed cohort
this one follows). Generated by `tools/estate-gen` (issue #56) from
hashicorp/aws 6.58.0's schema and `internal/live/identity/table.go`'s
identity table.

This cohort exercises every type this batch ratified into
`internal/live/lint/admission.go` and `internal/live/identity/table.go`.

Regenerate with:

```
go run ./tools/estate-gen -cohort iot -types aws_iot_authorizer,aws_iot_billing_group,aws_iot_domain_configuration,aws_iot_policy,aws_iot_provisioning_template,aws_iot_role_alias,aws_iot_thing,aws_iot_thing_group,aws_iot_thing_type,aws_iot_topic_rule,aws_iot_topic_rule_destination -out live/e2e/estates/iot
```

## Rejected

- **`aws_iot_ca_certificate`** — row-gen proposed server-assigned via the
  registry's opaque `Id`. The provider's own docs (fetched as raw markdown
  source at the pinned v6.59.0 tag, not the rendered page, to rule out a
  fetch artifact) carry no `## Import` heading anywhere in the file — no
  classic import command, no import-block identity schema, nothing. A CA
  certificate is client-supplied (`ca_certificate_pem` is a required
  argument, not a server-generated output), so this rejection is not the
  credential-material one below; it is the plainer "the provider documents
  no way in" rejection, the same kind `aws_codebuild_source_credential` got
  in the developer-tools batch, just for a structural reason (no Import
  section at all) rather than a missing-argument one.
- **`aws_iot_certificate`** — row-gen proposed server-assigned via the
  registry's opaque `Id`. Same structural gap as the CA certificate above
  (no `## Import` heading anywhere in the provider's raw doc source), but
  this type also fails a second, independent bar this batch was asked to
  check it against explicitly: `live/SURVEY.md`'s "three the rule excludes"
  permanently bars a type that is a credential born server-side alongside a
  secret that can never be read again, the same standing exclusion that
  keeps `aws_iam_access_key` out. The provider's own Attribute Reference for
  this type: "When neither CSR nor certificate is provided, the public
  key" / "...the private key" — confirmed against the doc's own "Without
  CSR" example usage, which creates the resource with neither a `csr` nor a
  `certificate_pem` argument set. That is a legal, documented
  configuration, and a caller who uses it gets a resource whose live state
  carries a private key AWS mints once and never returns again — exactly
  the forwarding-to-Ops shape `live/SURVEY.md` draws for
  `aws_iam_access_key` and `aws_secretsmanager_secret_version`. **Ruling:
  excluded by that rule**, independent of and in addition to the missing
  Import section. Unlike `aws_iam_access_key`, whether a given instance
  actually carries key material depends on how it was created (a `csr`- or
  `certificate_pem`-supplied instance carries none), but the admission
  table has no per-instance granularity, only per-type, so the type as a
  whole is excluded rather than admitted on the optimistic case.
- **`aws_iot_policy_attachment`** — row-gen proposed server-assigned via the
  registry's opaque `Id`. The provider's own docs carry no `## Import`
  heading at all, and its Attribute Reference is explicit that the resource
  "exports no additional attributes" beyond the two required arguments
  (`policy`, `target`) — no id-bearing output of any kind for an import
  mechanism to key off even if one existed.
- **`aws_iot_thing_principal_attachment`** — the same shape as the policy
  attachment just above, one binding away (`principal`, `thing` instead of
  `policy`, `target`): no `## Import` heading in the provider's docs, and an
  Attribute Reference that "exports no additional attributes" beyond the
  two required arguments.

## Out of this batch's named scope

Issue #65's own recipe names IoT (things, thing types/groups, policies,
topic rules, certificates), IoT Events, IoT Analytics, Greengrass (v1
skipped as a deprecated service; GreengrassV2 "if proposed"), IoT SiteWise
and IoT TwinMaker ("if proposed with clean evidence"). Only the plain IoT
service had any row-gen proposals at all: `live/registry.json` carries CFN
schemas for IoT Events, IoT Analytics, Greengrass (both versions), IoT
SiteWise and IoT TwinMaker resources, but `live/mapping.json` carries zero
rows for any of the five, and `tools/row-gen`'s own service listing has no
section for any of them. Confirmed independently against the pinned
provider's own `website/docs/r/` directory listing at the v6.59.0 tag,
which ships no `aws_iotevents_*`, `aws_iotanalytics_*`, `aws_greengrass*`
(either version), `aws_iotsitewise_*` or `aws_iottwinmaker_*` resource at
all — a provider gap, not a `live/mapping.json` curation gap. There is
nothing to admit or reject for any of the five services in this checkout's
pinned provider release; Greengrass V1 would be deprecated-service skip
regardless. `live/mapping.json`'s own `aws_iot_event_configurations`,
`aws_iot_indexing_configuration`, `aws_iot_logging_options` and
`aws_iot_thing_group_membership` rows are marked "tf-only" (no CFN model),
so `tools/row-gen`'s registry-driven pipeline does not — and structurally
cannot — propose them either; they are left for a batch prepared to
evidence tf-only rows some other way.

## Verifying by hand

```
docker run -d --rm -p 4633:4566 --name tofu-iot-cohort-verify \
  ghcr.io/lex00/floci@sha256:4753246c0260a22af1056c65993f4d73b0a907729a9580b9baba5d628b6dad34

export AWS_ENDPOINT_URL=http://localhost:4633 AWS_ACCESS_KEY_ID=test \
       AWS_SECRET_ACCESS_KEY=test AWS_REGION=us-east-1

terraform init
terraform validate
terraform apply -auto-approve

terraform destroy -auto-approve
docker rm -f tofu-iot-cohort-verify
```

`terraform validate` passes against the real provider release (6.58.0) this
fixture pins — confirming every argument name above is real, not just
registry-plausible.

An `apply` against the pinned `lex00/floci` image was run by hand during
ratification (not wired into any automated tier — see "Gating" above). The
image's own startup log advertises `iot` and `iotdata` in its "Enabled
services" list, and this cohort's coverage split three ways against it:

- `aws_iot_thing.app`, `aws_iot_policy.app` and `aws_iot_topic_rule.app`
  all created (and read back) cleanly — the emulator's IoT surface is real
  for these three.
- `aws_iot_thing_group.app` and `aws_iot_thing_type.app` both create
  successfully (`CreateThingGroup`/`CreateThingType` succeed and Terraform
  records each in state), but the very next call, the tag round-trip every
  taggable type's create cycle does (`ListTagsForResource`), 400s:
  `InvalidRequestException: Invalid resource ARN:
  arn:aws:iot:us-east-1:000000000000:thinggroup/...` (and `.../thingtype/
  ...`) — the emulator's own tagging validator does not recognize these two
  ARN resource-type segments, the same "advertises the write, not the
  matching read" gap earlier batches found for other services (the
  devtools batch's own `aws_codepipeline_custom_action_type`, for one), not
  evidence against either type's admission. Both had to be removed from
  state by hand (`terraform state rm`) before `destroy` could complete,
  since the same broken read blocks the destroy-time refresh too.
- `aws_iot_authorizer.app`, `aws_iot_billing_group.app`,
  `aws_iot_domain_configuration.app`, `aws_iot_provisioning_template.app`,
  `aws_iot_role_alias.app` and `aws_iot_topic_rule_destination.app` all
  fail identically at create: `deserialization failed ... invalid
  character '<' looking for beginning of value` — an HTML error page
  rather than a JSON API response, meaning `CreateAuthorizer`,
  `CreateBillingGroup`, `CreateDomainConfiguration`,
  `CreateProvisioningTemplate`, `CreateRoleAlias` and
  `CreateTopicRuleDestination` are none of them implemented behind this
  image's advertised `iot` service, despite the service itself being
  listed as enabled.

None of this is evidence against any row's admission above: identity and
enumeration are properties of the provider and the CFN registry, not of one
emulator's implementation completeness — the same framing every earlier
cohort's README already gives its own floci findings.
