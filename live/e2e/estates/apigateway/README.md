# apigateway cohort

Cohort: `apigateway`. Ratified by the fourth registry-backed ratification
batch against #40's strategy and #44's row generator (issue #65) — API
Gateway v1 and v2. Mechanism: #48 (see `live/e2e/estates/example/README.md`
for the proof-of-mechanism cohort, and `live/e2e/estates/lambda/README.md`
for the first registry-backed cohort this one follows). Generated by
`tools/estate-gen` (issue #56) from hashicorp/aws 6.58.0's schema and
`internal/live/identity/table.go`'s identity table — the first cohort this
fork has actually run the generator against rather than hand-writing.

This cohort exercises every type this batch ratified into
`internal/live/lint/admission.go` and `internal/live/identity/table.go`; see
`internal/live/identity/table.go`'s "Registry-ratified ... fourth batch, API
Gateway v1 and v2" section comment for the per-type evidence and the
row-gen proposals this batch rejected or deferred.

Regenerate with:

```
go run ./tools/estate-gen -cohort apigateway -types aws_api_gateway_account,aws_api_gateway_api_key,aws_api_gateway_base_path_mapping,aws_api_gateway_client_certificate,aws_api_gateway_documentation_version,aws_api_gateway_domain_name,aws_api_gateway_domain_name_access_association,aws_api_gateway_gateway_response,aws_api_gateway_method,aws_api_gateway_model,aws_api_gateway_rest_api,aws_api_gateway_rest_api_policy,aws_api_gateway_stage,aws_api_gateway_usage_plan,aws_api_gateway_usage_plan_key,aws_api_gateway_vpc_link,aws_apigatewayv2_api,aws_apigatewayv2_domain_name,aws_apigatewayv2_routing_rule,aws_apigatewayv2_stage,aws_apigatewayv2_vpc_link -out live/e2e/estates/apigateway
```

The explicit `-types` list is required here, not optional convenience: this
cohort's 21 types span two different CFN services (`AWS::ApiGateway::*` and
`AWS::ApiGatewayV2::*`), and `defaultCohortTypes` (`tools/estate-gen/cohort.go`)
matches a bare `-cohort apigateway` against the single CFN service whose name
lowercases to `apigateway` — it would silently drop the five
`aws_apigatewayv2_*` types rather than error, because sixteen types is still
a nonempty, plausible-looking result.

After every previous version, the tool has a second habit worth watching for:
`parentRef` (`tools/estate-gen/gen.go`) only ever proposes a sibling whose own
identity is a single, self-named configuration argument, which excludes every
server-assigned type in this batch. Several REST API children collapsed onto
`aws_api_gateway_rest_api_policy.app` instead of the real REST API, and
`aws_apigatewayv2_routing_rule` collapsed onto the *v1* domain name instead of
the v2 one, purely because those were the only (or alphabetically-first)
candidates whose identity self-names the same argument. `tools/estate-gen/overrides.go`'s
API Gateway section corrects every one of these; diff the regenerated
`apigateway.tf` against this fixture's committed copy before trusting a fresh
run blind.

## Rejected, and deferred

`tools/row-gen`'s ApiGateway and ApiGatewayV2 service sections proposed 25
and 13 types respectively in this batch's scope; 16 and 5 ratify above (21
total). The rest fall into two groups, neither an identity weakness in
row-gen's own evidence — see `internal/live/identity/table.go`'s section
comment for the full per-type citations (Argument Reference, provider
source, or `live/survey-full.json`'s identity schema for each):

- **Rejected — a composite segment is the child's own server-minted id, not
  a configuration argument**: `aws_api_gateway_authorizer`,
  `aws_api_gateway_deployment`, `aws_api_gateway_documentation_part`,
  `aws_api_gateway_request_validator`, `aws_api_gateway_resource`,
  `aws_apigatewayv2_api_mapping`, `aws_apigatewayv2_authorizer`,
  `aws_apigatewayv2_deployment`, `aws_apigatewayv2_integration`,
  `aws_apigatewayv2_integration_response`, `aws_apigatewayv2_model`,
  `aws_apigatewayv2_route`, `aws_apigatewayv2_route_response`. Three of
  these (`aws_apigatewayv2_integration_response`, `aws_apigatewayv2_model`,
  `aws_apigatewayv2_route_response`) were confirmed directly against the
  provider's own source rather than inferred from its docs: each
  `resourceXCreate` calls `d.SetId(aws.ToString(output.XId))`, a value the
  API mints independently of any argument in configuration.
- **Deferred as method/response property-children**, per `live/mapping.json`'s
  fold (no independent `cfn_type` of their own — row-gen's own output marks
  each `(property-child of AWS::ApiGateway::Method)` or `...Stage`, "no
  pastable row"), not for any identity weakness — each one's identity is in
  fact fully composable from real configuration arguments alone, confirmed
  the same way `aws_api_gateway_method` itself was (which *is* ratified: it
  is its own CFN resource, merely with a composite `primaryIdentifier`, not a
  fold): `aws_api_gateway_integration`, `aws_api_gateway_integration_response`,
  `aws_api_gateway_method_response` (fold into `AWS::ApiGateway::Method`),
  `aws_api_gateway_method_settings` (fold into `AWS::ApiGateway::Stage`).
  Ratifying a property-child needs a parent-derived admission mechanism this
  table does not have yet — the same gap the APS service's
  `aws_prometheus_alert_manager_definition` and its siblings are waiting on
  upstream. `aws_api_gateway_rest_api_policy` is *not* in this group despite
  also being a fold in `live/mapping.json`: unlike the four above, its
  identity is a single argument (`rest_api_id`) with no separator to choose,
  the same named-singleton-child shape as `aws_s3_bucket_policy` and
  `aws_sns_topic_policy`, so it ratifies on that existing standard instead.

## Untaggable types

Nine of this batch's sixteen ApiGateway types and one of its five
ApiGatewayV2 types carry no `tags` argument in the AWS provider, confirmed
against each type's Argument Reference:
`aws_api_gateway_account`, `aws_api_gateway_base_path_mapping`,
`aws_api_gateway_documentation_version`, `aws_api_gateway_gateway_response`,
`aws_api_gateway_method`, `aws_api_gateway_model`,
`aws_api_gateway_rest_api_policy`, `aws_api_gateway_usage_plan_key`, and
`aws_apigatewayv2_routing_rule`. Unlike the Lambda and messaging batches'
untaggable types, none of these needed the `untaggableOutsideCuratedSurvey`
split in `internal/live/stamp/stamp_test.go`: `live/LIMITATIONS.md`'s
"Untaggable types cannot be removed by the sweep" entry is now rendered
mechanically from `live/survey-full.json` intersected with the admission
table (issue #54's apparatus, already in place by the time this batch
landed), so all nine plus one fold straight into that doc's derived span via
`go run ./tools/survey-gen -render` — see that command's diff to
`live/LIMITATIONS.md` in this batch's commit.

## Gating

Nothing here runs against a live or emulated cloud in the automated suite.
`go test ./internal/live/lint/... ./internal/live/identity/...` picks this
directory up through `internal/live/flocitest.FixtureDirs` (#48's union pin)
and checks it by static HCL parse — `TestAdmissionTableCoversEstate` and

this one included.

fixture pins, with the `typeOverrides` corrections above applied.

## Verifying by hand

```
docker run -d --rm -p 4620:4566 --name tofu-apigateway-cohort-verify \
  ghcr.io/lex00/floci@sha256:4753246c0260a22af1056c65993f4d73b0a907729a9580b9baba5d628b6dad34
export AWS_ENDPOINT_URL=http://localhost:4620 AWS_ACCESS_KEY_ID=test \
       AWS_SECRET_ACCESS_KEY=test AWS_REGION=us-east-1

terraform init
terraform validate
```

Both commands were run by hand during ratification (not wired into any
automated tier — see "Gating" above). A full `terraform apply` of this
fixture was not attempted, because `aws_api_gateway_rest_api`'s create-path
gap below makes any plan that includes it hang; the verification instead
went type by type, against a temporary scratch configuration and the raw AWS
CLI pointed at the same emulator, and against `terraform import` where a
composite identity needed confirming. floci's actual coverage is narrower
than its health check advertises, the same split every earlier batch found:

- **`aws_api_gateway_rest_api`**: re-verified against this pinned image for
  issue #65, because `internal/live/lint/admission.go`'s old comment cited a
  floci availability-waiter gap here from the marker cohort (#20) and asked
  that it not be trusted blind. The gap still reproduces exactly as before —
  `terraform apply` hangs on `waiting for API Gateway REST API (...) to
  become available: unexpected state '', wanted target 'AVAILABLE'` — but
  `CreateRestApi`, `GetRestApi` and, critically, a `terraform import` of a
  floci-created REST API all round-trip cleanly with zero plan diff. That
  narrows the old finding rather than reversing it: the create-path waiter
  is broken, the read/import path this table's admission actually depends on
  is not, and the same emulator-gap-does-not-block-ratification standard the
  messaging batch set for `aws_sqs_queue` applies here too. `choudoufu#26`
  territory.
- **`aws_api_gateway_model`, `aws_api_gateway_stage`,
  `aws_api_gateway_usage_plan_key`, `aws_apigatewayv2_api`**: created via the
  raw AWS CLI (bypassing the broken waiter above) and then round-tripped
  through a `terraform import` block against this table's Components —
  clean, zero-diff plans for all four, confirming the composite separators
  and argument wiring by hand, not just by reading the provider's docs.
- **`aws_api_gateway_api_key`**: reading one back **crashes the provider
  process** — a nil-pointer panic inside `resourceAPIKeyRead`
  (`internal/service/apigateway/api_key.go`), not a graceful error. Confirmed
  by hand: `CreateApiKey` and `GetApiKey` both succeed against floci's raw
  API, but a `terraform plan` that imports the key takes the whole provider
  process down with it. This is a more severe floci gap than the "operation
  not supported" shape the messaging batch found for CloudWatch — worth
  flagging distinctly for whoever picks up `choudoufu#26` next — but it is
  still not evidence against the identity, which real AWS serves without
  incident.
- **`aws_api_gateway_usage_plan`**: `CreateUsagePlan` succeeds, but
  `GetUsagePlan` misroutes to a stray S3-shaped `NoSuchBucket` error rather
  than reading the plan back. `aws_api_gateway_usage_plan_key`, its own
  child, is unaffected — `GetUsagePlanKey` is an independent floci code path
  and works cleanly, which is how the bullet above could confirm it end to
  end despite this one.
- **`aws_api_gateway_client_certificate`, `aws_api_gateway_vpc_link`**:
  floci returns 406 for `GenerateClientCertificate` and `CreateVpcLink` — not
  implemented at all, the same "service present, operation absent" shape the
  messaging batch found for `PutCompositeAlarm`/`PutDashboard`/`PutMetricStream`.
- **`aws_apigatewayv2_vpc_link`, `aws_apigatewayv2_integration`,
  `aws_apigatewayv2_route`, `aws_apigatewayv2_model` (rejected, not
  ratified — see above), `aws_apigatewayv2_authorizer` (rejected)**: all
  create cleanly via the raw AWS CLI. v2's surface is noticeably more
  complete against this image than v1's.
- **`aws_api_gateway_domain_name`, `aws_apigatewayv2_domain_name`**:
  `CreateDomainName` misroutes to an unrelated S3/InvalidArgument error on
  both generations — the same shape as the usage plan gap above. Neither
  type's identity is in question (both are a single client-named `domain_name`
  argument, confirmed against the provider's own Argument Reference); this
  fixture's `aws_api_gateway_base_path_mapping.app` and
  `aws_apigatewayv2_routing_rule.app` therefore reference a domain name that
  `terraform validate` accepts but a real `apply` against this emulator could
  not create.
- **`aws_api_gateway_documentation_version`, `aws_api_gateway_gateway_response`**:
  `CreateDocumentationVersion` returns 406 (not implemented);
  `PutGatewayResponse` misroutes the same way `CreateDomainName` does. Both
  types' identities were confirmed against the provider's Argument Reference
  and documented import command instead of against a live round-trip.
- **`aws_apigatewayv2_routing_rule`**: untested end to end — creating one
  needs a working `aws_apigatewayv2_domain_name` first, which the bullet
  above rules out on this image. The identity itself (a single server-minted
  ARN, confirmed computed rather than configurable via the provider's own
  Attribute Reference) does not depend on the emulator either way.

None of the gaps above changes which types this batch ratifies: identity and
enumeration are properties of the provider and the registry, not of one
emulator's completeness, the standard every batch since messaging has held
to.
