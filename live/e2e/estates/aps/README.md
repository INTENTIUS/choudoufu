# aps cohort

Cohort: `aps`. Ratified by issue #68's fold-child batch: the APS/Prometheus
half of the two "first slice" families that batch proves the fold-child
admission path against (the other is the API Gateway four, extending
`live/e2e/estates/apigateway`). Generated by `tools/estate-gen` (issue #56)
from hashicorp/aws 6.58.0's schema and `internal/live/identity/table.go`'s
identity table.

`aws_prometheus_workspace` and `aws_prometheus_scraper` are ordinary
server-assigned marker types, admitted here because the three fold-children
below need an admitted parent to key on — neither had a row before this
batch. `aws_prometheus_alert_manager_definition` and
`aws_prometheus_query_logging_configuration` are named-singleton children of
the workspace (Components: `[attr("workspace_id")]`, the same shape as
`aws_s3_bucket_policy`); `aws_prometheus_scraper_logging_configuration` is a
named-singleton child of the scraper the same way. See
`internal/live/identity/table.go`'s "Fold-children (issue #68)" section
comment for the full per-type evidence, including the correction to
row-gen's own registry-derived guess (both new parents identify by a bare
`ws-`/`s-` id, not the read-only `Arn` field row-gen proposed).

Regenerate with:

```
go run ./tools/estate-gen -cohort aps -types aws_prometheus_workspace,aws_prometheus_scraper,aws_prometheus_alert_manager_definition,aws_prometheus_query_logging_configuration,aws_prometheus_scraper_logging_configuration -out live/e2e/estates/aps
```

## Untaggable types

All three fold-children (`aws_prometheus_alert_manager_definition`,
`aws_prometheus_query_logging_configuration`,
`aws_prometheus_scraper_logging_configuration`) carry no `tags` argument,
confirmed against each type's Argument Reference. Each fits
`identity.SingleParentComponent` unchanged (one attribute-supplying
component, entirely the parent's), so `internal/live/discovery`'s existing
issue #60 parent-read sweep leg covers all three with no new discovery code
— report-only, the same "unverified against a real not-found response"
standard `aws_sns_topic_policy` and `aws_sqs_queue_policy` already carry.
`aws_prometheus_workspace` and `aws_prometheus_scraper` are both taggable
(ordinary marker path).

## Gating

Nothing here runs against a live or emulated cloud. `go test ./internal/live/lint/... ./internal/live/identity/...` picks this
directory up through `internal/live/flocitest.FixtureDirs` (#48's union pin).

`terraform validate` passes against the real provider release (6.58.0) this fixture pins.

No live floci verification: the pinned floci image's own health check
(`docker exec ... curl /_localstack/health`) lists no `amp`/`prometheus`
service at all (confirmed by hand against the same pinned image every other
cohort's "Verifying by hand" section uses), so Amazon Managed Prometheus is
not implemented by this emulator at any level - not a gap this batch's
identity work can be blamed for or verify around. The identity evidence
above stands on the provider's own documented Import section and source,
the same standard of care every other type in this table not reachable
through floci already holds to (`aws_api_gateway_client_certificate`,
`aws_apigatewayv2_routing_rule`, and others). Issue #68's own gated live
proof (`TestFoldChildReadSweepAgainstFloci`,
`internal/live/discovery/fold_read_live_test.go`) exercises the
API Gateway shape instead, for exactly this reason.
