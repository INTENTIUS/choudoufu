# databases cohort

Cohort: `databases`. Ratified by: the sixth registry-backed ratification
batch against #40's strategy and #44's row generator, issue #65's own
recipe — databases beyond RDS/DynamoDB/ElastiCache (Redshift,
OpenSearch/OpenSearchServerless, Neptune, DocDB, Timestream, QLDB,
MemoryDB, Cassandra/Keyspaces). Mechanism: #48 (see
`live/e2e/estates/example/README.md` for the proof-of-mechanism cohort).
Generated by `tools/estate-gen` (issue #56) from hashicorp/aws 6.58.0's
schema and `internal/live/identity/table.go`'s identity table.

This cohort exercises every type this batch ratified into
`internal/live/lint/admission.go` and `internal/live/identity/table.go`.
See `internal/live/identity/table.go`'s own "sixth batch, databases" comment
for the per-type identity evidence, the one rejection
(`aws_qldb_stream`), and the full list of row-gen proposals this batch left
out of scope per issue #65's own narrower per-service sub-lists.

Regenerate with:

```
go run ./tools/estate-gen -cohort databases -types aws_docdb_event_subscription,aws_docdbelastic_cluster,aws_elasticsearch_domain,aws_keyspaces_keyspace,aws_keyspaces_table,aws_memorydb_acl,aws_memorydb_cluster,aws_memorydb_multi_region_cluster,aws_memorydb_parameter_group,aws_memorydb_subnet_group,aws_memorydb_user,aws_neptune_cluster_parameter_group,aws_neptune_parameter_group,aws_neptune_subnet_group,aws_opensearch_domain,aws_opensearchserverless_access_policy,aws_opensearchserverless_collection,aws_opensearchserverless_collection_group,aws_opensearchserverless_lifecycle_policy,aws_opensearchserverless_security_policy,aws_qldb_ledger,aws_redshift_cluster,aws_redshift_parameter_group,aws_redshift_snapshot_schedule,aws_redshift_subnet_group,aws_redshiftserverless_namespace,aws_redshiftserverless_workgroup,aws_timestreaminfluxdb_db_cluster,aws_timestreaminfluxdb_db_instance,aws_timestreamquery_scheduled_query,aws_timestreamwrite_database,aws_timestreamwrite_table -out live/e2e/estates/databases
```

(`-types` is explicit because `defaultCohortTypes` matches a cohort name
against exactly one `live/mapping.json` CFN service, and this cohort spans
more than a dozen — the same reason the `devtools`, `data`, `ecs-eks`,
`storage` and `route53-cloudfront` cohorts' own README regenerate commands
are illustrative rather than literally reproducible with `-cohort` alone.)

## Rejected

- **`aws_qldb_stream`** — CFN registry primaryIdentifier is
  `["LedgerName", "Id"]`, and unlike every composite this batch resolves,
  one half (`Id`) is absent from `createOnlyProperties`: QLDB mints the
  stream's own id at create time, so no configuration argument, literal or
  cloud value reconstructs it. The same unrecoverable shape as
  `aws_elasticache_global_replication_group`'s rejection in the
  DynamoDB/ElastiCache batch — not a row-gen misclassification, a genuine
  gap in what configuration alone can recover.

## Out of scope

Per-service scope in this batch is deliberately narrower than "every
row-gen proposal in the service section", matching issue #65's own
sub-lists rather than exhausting each service. See
`internal/live/identity/table.go`'s own batch comment for the full,
per-service breakdown of what was left out and why:

- **Redshift**: everything but clusters, parameter/subnet groups and
  snapshot schedules (event subscription, scheduled action, integration,
  endpoint access/authorization, logging and iam_roles property children,
  snapshot, hsm client cert/config, usage limit, partner, idc application,
  the two data-share types, resource policy, authentication profile).
- **RedshiftServerless**: everything but namespaces and workgroups
  (snapshot, endpoint access, usage limit, resource policy,
  custom-domain-association).
- **RedshiftData**: not proposed by row-gen at all — no `aws_redshiftdata_*`
  type exists in `live/mapping.json`.
- **OpenSearch/Elasticsearch**: the domain policy and SAML-options folds
  (`aws_opensearch_domain_policy`, `aws_opensearch_domain_saml_options`,
  `aws_elasticsearch_domain_policy`), all property-children row-gen leaves
  evidence-only.
- **OpenSearchServerless**: `aws_opensearchserverless_security_config` (a
  SAML/IAM-Identity-Center configuration type, not a policy despite living
  beside them) and `aws_opensearchserverless_vpc_endpoint` (neither a
  collection nor a policy).
- **Neptune**: cluster, cluster instance, event subscription and global
  cluster (all evidence-only per row-gen); all of NeptuneGraph, a distinct
  CFN service issue #65 does not name.
- **DocDB**: cluster, cluster instance, cluster parameter group, global
  cluster, subnet group (all evidence-only per row-gen; `docdbelastic`'s
  own family is otherwise fully covered by this batch's one type).

## Floci coverage

A real `terraform apply` was run by hand against the pinned floci image
(`ghcr.io/lex00/floci@sha256:4753246c0260a22af1056c65993f4d73b0a907729a9580b9baba5d628b6dad34`),
first without and then with the host's Docker socket mounted into the
floci container (`-v /var/run/docker.sock:/var/run/docker.sock`) —
`aws_opensearch_domain`'s own real behavior (below) needs it, and neither
`live/e2e/run.sh` nor any earlier batch's own verification mounts it, so
this batch's own attempt is the first to notice the gap. This cohort's
coverage is genuinely mixed, wider than any earlier batch's own floci
findings:

**Real and working**, an apply completed with no error:

- `aws_neptune_cluster_parameter_group`, `aws_neptune_parameter_group` —
  Neptune's classic RDS-shaped query handler serves both synchronously.
- `aws_memorydb_user` — MemoryDB's own Create/Describe/ListTags path is
  real (`MemoryDB user ... created with authMode=PASSWORD`, in the
  container's own log).
- `aws_iam_role` (supporting) — real, as every earlier batch's own apply
  already established.

**Real, but only with the Docker socket mounted** — `aws_opensearch_domain`
and (by the same code path) `aws_elasticsearch_domain`. Both make floci
actually pull and start a real `opensearchproject/opensearch:2.19.5`
container per domain (confirmed in the floci container's own log: `Started
container ... for domain tofu-db-os-domain`; the emulated OpenSearch node's
own log shows its single-node cluster reaching `Cluster health status
changed from [YELLOW] to [GREEN]` within about a minute) — but
`DescribeDomain` never reports the domain as available afterward
(`"Created": false, "Processing": true`, unchanged for as long as this
verification waited). `docker exec <floci> getent hosts
floci-opensearch-<domain>` resolves nothing: the spawned OpenSearch
container and the floci container both land on the default `bridge`
network, which (unlike a user-defined network) does not do container-name
DNS, so floci's own internal health probe against
`http://floci-opensearch-<domain>:9200` can never reach the node it just
started, and the provider's availability waiter spins forever. A genuine
floci-image gap, not a configuration problem this batch's override can
fix — and without the socket mount at all (the invocation every earlier
batch, and `live/e2e/run.sh` itself, actually uses) domain creation never
even reaches the point of trying: `Creating DockerClient for host:
unix:///var/run/docker.sock` fails outright
(`java.net.SocketException: No such file or directory`).

**Unimplemented in this image** — every Create call below reached floci
(confirmed by the response's error shape, not a client-side failure) and
was refused:

- Redshift (classic): `aws_redshift_cluster`, `aws_redshift_parameter_group`,
  `aws_redshift_subnet_group`, `aws_redshift_snapshot_schedule` — floci's
  router dispatches every one to its SQS handler instead
  (`UnsupportedOperation: Operation ... is not supported by SQS`).
- RedshiftServerless: `aws_redshiftserverless_namespace`,
  `aws_redshiftserverless_workgroup` — `UnknownOperationException`.
- OpenSearchServerless: `aws_opensearchserverless_collection_group`,
  `aws_opensearchserverless_lifecycle_policy`,
  `aws_opensearchserverless_security_policy` (and, by the same code path,
  `aws_opensearchserverless_access_policy` and
  `aws_opensearchserverless_collection`, both graph-skipped once their own
  dependency — the security policy — failed first) — `UnknownOperationException`.
- Timestream, all three sub-services: `aws_timestreamwrite_database`
  (`DescribeEndpoints` itself unimplemented), `aws_timestreaminfluxdb_db_cluster`,
  `aws_timestreaminfluxdb_db_instance` — `UnknownOperationException`
  (`aws_timestreamwrite_table` and `aws_timestreamquery_scheduled_query`
  were graph-skipped once their own dependencies failed first).
- Keyspaces: `aws_keyspaces_keyspace` — `UnknownOperationException`
  (`aws_keyspaces_table` graph-skipped, since its `keyspace_name` argument
  is wired to the sibling keyspace above).
- MemoryDB, everything but the ACL/Cluster/User trio's own read paths:
  `aws_memorydb_parameter_group`, `aws_memorydb_subnet_group`,
  `aws_memorydb_multi_region_cluster` — `UnknownOperationException`.
  `aws_memorydb_acl` and `aws_memorydb_cluster` reach real handlers but
  fail on real MemoryDB semantics this cohort's own resources trip over
  independently of floci (see below).
- `aws_docdb_event_subscription` — `UnsupportedOperation`.
- Neptune's own `aws_neptune_subnet_group` reaches a real handler but
  fails validating the estate's synthetic `subnet-...` placeholder IDs
  (`InvalidSubnet: ... do not exist`), the ordinary shape every other
  cohort's synthetic-ID overrides already accept as a known, non-blocking
  limit of a Docker-only emulator with no real VPC behind it.

**Reached a real handler, but the handler crashes** — the response is an
HTML error page, not a JSON error body (`deserialization failed: invalid
character '<' looking for beginning of value`), a router-recognized but
broken implementation rather than an absent one:

- `aws_docdbelastic_cluster` (`CreateCluster`)
- `aws_qldb_ledger` (`CreateLedger`)
- (`aws_elasticsearch_domain`'s own `CreateElasticsearchDomain` hits this
  same shape when the Docker socket is *not* mounted; with it mounted, it
  reaches the real-container path described above instead.)

**Real MemoryDB semantics this cohort's own graph trips over**, floci
correctly enforcing rules the estate's synthetic resources do not
satisfy independently: `aws_memorydb_acl` needs a pre-existing default
user (`DefaultUserRequired`), and `aws_memorydb_cluster` needs the ACL it
names to already exist (`ACLNotFoundFault`) — both ordinary
apply-ordering/fixture gaps, not floci bugs, and not this batch's to fix
without inventing a `default` user resource this batch's own scope does
not ratify.

None of this blocks ratification, the same standing the storage and
devtools batches' own README sections already established for their own
unserved and partially-served types.
