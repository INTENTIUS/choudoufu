# stragglers cohort

Cohort: `stragglers`. Ratified by: the ratification-campaign stragglers batch
(issue #65) — not a new service sweep, but the reachable types six earlier
ratified batches (data-movement, networking-advanced, iam-ecr) each named in
their own cohort README as outside that batch's own stated scope. Mechanism:
#48 (see `live/e2e/estates/example/README.md` for the proof-of-mechanism
cohort). Generated by `tools/estate-gen` (issue #56) from hashicorp/aws
6.58.0's schema and `internal/live/identity/table.go`'s identity table.

This cohort exercises every type this batch ratified into
`internal/live/lint/admission.go` and `internal/live/identity/table.go`. See
`internal/live/identity/table.go`'s own "stragglers batch" comment for the
per-type identity evidence and the one rejection
(`aws_transfer_ssh_key`).

Regenerate with:

```
go run ./tools/estate-gen -cohort stragglers -types aws_transfer_certificate,aws_transfer_profile,aws_transfer_web_app,aws_transfer_web_app_customization,aws_transfer_agreement,aws_networkmanager_core_network_policy_attachment,aws_storagegateway_tape_pool,aws_ecr_lifecycle_policy,aws_ecr_pull_through_cache_rule,aws_ecr_pull_time_update_exclusion,aws_ecr_repository_creation_template,aws_ecr_repository_policy -out live/e2e/estates/stragglers
```

(`-types` is explicit for the same reason the `devtools`, `data`, `data-movement`,
`databases`, `ecs-eks`, `storage` and `route53-cloudfront` cohorts' own README
regenerate commands are: this cohort spans three services — Transfer,
NetworkManager and ECR — that `defaultCohortTypes` cannot match against a
single `live/mapping.json` CFN service.)

## Where each row came from

- **Transfer Family** (5 ratified, 1 rejected): the data-movement batch
  named servers, users, workflows and connectors only
  (`live/e2e/estates/data-movement/README.md`, "Left outside this batch's
  named scope"), leaving six more Transfer types reachable.
  `aws_transfer_certificate`, `aws_transfer_profile`, `aws_transfer_web_app`
  and `aws_transfer_agreement` are all server-assigned (the provider's own
  Attribute Reference documents each identifying id as resource-exported,
  absent from the Argument Reference entirely) but taggable, so they ratify
  via the marker path. `aws_transfer_web_app_customization` is a named
  singleton child of `aws_transfer_web_app`, keyed on `web_app_id`, a real
  Required argument — the same shape as `aws_s3_bucket_policy`.
  `aws_transfer_ssh_key` is rejected: see "Rejected" below.
- **NetworkManager** (1 ratified): `aws_networkmanager_core_network_policy_attachment`
  is the sole NetworkManager type row-gen proposes that the
  networking-advanced batch left out
  (`live/e2e/estates/networking-advanced/README.md`, "Deferred, out of this
  batch's named scope") — every other NetworkManager row-gen names is
  already ratified there. It is a named singleton child of
  `aws_networkmanager_core_network`, keyed on `core_network_id`, a real
  Required argument with no separator — the same shape as
  `aws_s3_bucket_policy`, not the composite property-child fold row-gen's
  own note suggested.
- **ECR remainder** (5 ratified): the IAM/ECR batch's own row-gen output
  classified `aws_ecr_lifecycle_policy`, `aws_ecr_pull_through_cache_rule`,
  `aws_ecr_pull_time_update_exclusion`, `aws_ecr_repository_creation_template`
  and `aws_ecr_repository_policy` evidence-only (per #44's own non-goals, no
  pastable row was ever generated for any of them) — not on any identity
  weakness. Independent verification against the pinned v6.58.0 provider
  docs supplies a clean, single-argument, Required-in-schema identity for
  each.

## Rejected

- **`aws_transfer_ssh_key`** — the documented import composite is
  `server_id/user_name/ssh_public_key_id`. `server_id` and `user_name` are
  both real Required arguments, but `ssh_public_key_id` is absent from both
  the Argument Reference and the Attribute Reference entirely ("This
  resource exports no additional attributes") — it exists only inside the
  opaque id string the provider mints at create time. Unlike
  `aws_transfer_web_app_customization` above, `server_id/user_name` is not a
  singleton key either: a single user can hold more than one SSH key, so the
  pair does not uniquely determine the resource the way a bucket name
  determines its policy. The provider ships no `tags` argument for this type
  at all (Argument Reference: `region`, `server_id`, `user_name`, `body`
  only), so there is no marker path either. No admission path recovers it —
  the same genuine, unrecoverable gap as `aws_qldb_stream` and
  `aws_elasticache_global_replication_group`'s own rejections, not a
  row-gen misclassification.

## Untaggable types

Seven of the twelve rows above carry no `tags` argument in the pinned
provider's wire schema, confirmed against the v6.58.0 docs and the generated
fixture: `aws_transfer_web_app_customization` (Argument Reference:
`web_app_id`, `favicon_file`, `logo_file`, `title` only) and
`aws_networkmanager_core_network_policy_attachment` (Argument Reference:
`core_network_id`, `policy_document` only) are both named-singleton-child
folds, the same untaggable shape as `aws_s3_bucket_policy`;
`aws_ecr_lifecycle_policy`, `aws_ecr_pull_through_cache_rule`,
`aws_ecr_pull_time_update_exclusion`, `aws_ecr_repository_creation_template`
and `aws_ecr_repository_policy` are all policy/rule documents or a
name-prefix template, the same shape as `aws_ecr_repository_policy`'s own
sibling entries above. All seven are added to
`internal/live/stamp/stamp_test.go`'s `untaggableAdmittedTypes` list;
`live/LIMITATIONS.md`'s "Untaggable types cannot be removed by the sweep"
entry picks them up automatically when regenerated with
`go run ./tools/survey-gen -render`.

## Floci coverage

A real `terraform apply` was run by hand against the pinned floci image
(`ghcr.io/lex00/floci@sha256:4753246c0260a22af1056c65993f4d73b0a907729a9580b9baba5d628b6dad34`),
started manually on a local port with the AWS provider pointed at it via
`AWS_ENDPOINT_URL` (the same mechanism `live/e2e/run.sh` uses). The
container's own `/_localstack/health` endpoint names which services it
implements at all: `transfer` and `ecr` are both `"running"`;
`networkmanager` and `storagegateway` are absent from the list entirely.
Coverage here is genuinely mixed, and every failure below is floci's own
implementation gap, not a fixture or override defect — `terraform validate`
is clean for all twelve types, and the two provider-side bugs this
verification pass did find (see the `aws_transfer_web_app` override's own
Reasons entry above) are already fixed in the fixture, confirmed by
re-running just that one resource afterward and watching the failure mode
change from a client-side panic to a clean floci 404.

**Not implemented by floci at all** (service absent from
`/_localstack/health`): `aws_networkmanager_core_network_policy_attachment`
(`PutCoreNetworkPolicy` — and `GetCoreNetwork` on a subsequent read/destroy
— both return an HTML error page the AWS SDK cannot even deserialize as a
JSON error, `deserialization failed ... invalid character '<' looking for
beginning of value`) and `aws_storagegateway_tape_pool`
(`CreateTapePool` — `UnknownOperationException`).

**Service present, operation not implemented** (`transfer` and `ecr` both
report `"running"`, but the specific API calls these five types need return
`UnknownOperationException` or `UnsupportedOperation`):
`aws_transfer_agreement` (`CreateAgreement`), `aws_transfer_certificate`
(`ImportCertificate`), `aws_transfer_profile` (`CreateProfile`),
`aws_transfer_web_app` (`CreateWebApp`),
`aws_transfer_web_app_customization` (`UpdateWebAppCustomization`),
`aws_ecr_pull_through_cache_rule` (`CreatePullThroughCacheRule`),
`aws_ecr_pull_time_update_exclusion` (`RegisterPullTimeUpdateExclusion`),
`aws_ecr_repository_creation_template`
(`CreateRepositoryCreationTemplate`). floci's own `transfer` implementation
serves only the server/user/workflow/connector core the data-movement batch
already ratified; its `ecr` implementation serves repository-level
operations, not these five newer API surfaces.

**Blocked on a missing parent, not a floci gap**: `aws_ecr_lifecycle_policy`
and `aws_ecr_repository_policy` both fail with `RepositoryNotFoundException`
— this cohort's fixture, like `aws_ecr_lifecycle_policy`'s own
`live/SURVEY.md` row already flags ("blocked-emulator ... needs a live
parent repository, which floci cannot create, choudoufu#26"), has no
`aws_ecr_repository` resource of its own to reference, and neither policy
type's own PUT operation creates the repository it targets.

None of this is blocking: `terraform validate` is the gate this batch's
tests actually run, and it is clean for all twelve types. The floci gaps
above are the same "genuinely mixed" shape the databases and
compute-platforms batches already documented for their own cohorts.
