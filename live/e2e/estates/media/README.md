# media cohort

Cohort: `media`. Ratified by: the sixth registry-backed ratification batch
against #40's strategy and #44's row generator, covering issue #65's media
services suggestion — MediaLive, MediaConvert, MediaPackage v1 and v2,
MediaStore, MediaTailor, MediaConnect, IVS and IVSChat. Mechanism: #48 (see
`live/e2e/estates/example/README.md` for the proof-of-mechanism cohort, and
`live/e2e/estates/streaming/README.md` for the fifth registry-backed cohort
this one follows). Generated by `tools/estate-gen` (issue #56) from
hashicorp/aws 6.58.0's schema and `internal/live/identity/table.go`'s
identity table.

This cohort exercises every type this batch ratified into
`internal/live/lint/admission.go` and `internal/live/identity/table.go`: 9
types across four services (MediaLive's Multiplex pair, MediaPackage v1 and
v2, IVS, IVSChat), against a `go run ./tools/row-gen` scope of 5 services
proposing 11 pastable-or-correctable rows. Four proposals are deferred
rather than ratified (registry-laggard), two more types never reached
row-gen at all and are moved out of scope by policy (MediaStore, see
below), and two services this batch was asked to check (MediaTailor,
Elastic Transcoder) turn out to have nothing to ratify for reasons
independent of row-gen.

**Two of the nine left the admission on 2026-08-14** (#124's acceptance
measurement; rulings recorded in `tools/row-gen/rejected.json`, the same
procedure #125 used for `aws_iam_access_key`): `aws_ivs_playback_key_pair`,
whose `public_key` is Required, ForceNew and write-only (no IVS read
returns the material, so a marker-rebuilt plan always proposes
replacement), and `aws_medialive_multiplex_program`, whose import under
the pinned provider leaves `multiplex_id` unset (reproduced directly:
`terraform import` by the documented `PROGRAM_NAME/MULTIPLEX_ID` id
populates `program_name` and the settings block but not `multiplex_id`,
which is ForceNew - so replan always proposes replacement; re-admittable
if a future pass backfills null ForceNew arguments from the identity
components that composed the import id). The coverage rows below keep
both types' original evidence for the record; the estate no longer
declares them.

Regenerate with:

```
go run ./tools/estate-gen -cohort media -types aws_ivs_channel,aws_ivs_recording_configuration,aws_ivschat_logging_configuration,aws_ivschat_room,aws_media_package_channel,aws_media_packagev2_channel_group,aws_medialive_multiplex -out /tmp/estate-gen/media
```

`-types` is explicit because `tools/estate-gen/cohort.go`'s no-`-types`
default matches a cohort's types by CFN service name alone, and this
batch's nine types span four different CFN services (MediaLive,
MediaPackage, MediaPackageV2, IVS, IVSChat) with no single service name in
common with the cohort's own name.

## Corrected, not merely accepted

Two rows landed here with different identity than `tools/row-gen` itself
proposed, the same "registry versus real provider docs" correction shape
the storage, ec2-networking and streaming batches made:

- **`aws_media_packagev2_channel_group`** — row-gen proposed server-assigned
  off the registry's `primaryIdentifier=[Arn]`. The provider disagrees
  outright: its documented import command (`terraform import
  aws_media_packagev2_channel_group.example example`) and its own prose
  ("import ... using the channel group's `name`") both name `name`, a
  Required argument already in configuration — not the ARN the registry's
  `readOnlyProperties` pointed at. Corrected client-named.
- **`aws_media_package_channel`** — row-gen's own registry evidence
  (`primaryIdentifier=[Id]`, in `createOnlyProperties`, not in
  `readOnlyProperties`) left it evidence-only: an argument name ("id") it
  had to guess rather than confirm. The real provider docs resolve the
  guess exactly: `channel_id` is "(Required) A unique identifier
  describing the channel," and the Attribute Reference states `id` is "The
  same as `channel_id`." Promoted from evidence-only to a full client-named
  row, the same promotion the ec2-networking batch's
  `aws_nat_gateway_eip_association` and the storage batch's
  `aws_backup_logically_air_gapped_vault` made from their own GUESSED
  starting points.

## Rejected: registry-laggard (MediaLive Channel/Input/InputSecurityGroup, MediaConvert Queue)

Four of row-gen's proposals in this batch's scope map to a CloudFormation
Registry entry whose `handlers` block is `create`/`read`/`update`/`delete`/`list`
**all false** — confirmed directly against `live/registry.json`:

| CFN type | handlers |
|---|---|
| `AWS::MediaLive::Channel` | all false |
| `AWS::MediaLive::Input` | all false |
| `AWS::MediaLive::InputSecurityGroup` | all false |
| `AWS::MediaConvert::Queue` | all false, and `tagging.taggable: false` |

This is the "registry-laggard" shape `live/LIMITATIONS.md`'s Registry-laggard
live services table already tracks, and this batch applies the same
standard the streaming batch's `aws_appsync_api_cache`/`aws_appsync_api_key`
rejections set: "a registry entry with no working handler at all supplies
no real evidence, whatever its `primaryIdentifier` field claims." That
batch held the line even where the real provider docs would have permitted
a hand correction (`aws_appsync_api_cache` imports cleanly by its parent
`api_id`); this batch holds it too, for consistency, even though the real
evidence for three of these four rows is uncomplicated:

- `aws_medialive_channel`, `aws_medialive_input` and
  `aws_medialive_input_security_group` all import by a plain
  server-assigned numeric id (`terraform import aws_medialive_channel.example
  1234567`, `aws_medialive_input.example 12345678`,
  `aws_medialive_input_security_group.example 123456`) — the same
  marker-path bucket row-gen itself proposed, with no correction needed at
  all. The registry's handler-less entry is the only thing standing
  between these three and ratification; a future registry-laggard sweep
  (or a CFN release that finally ships MediaLive working handlers) should
  expect to admit all three by name, unchanged from row-gen's own rows.
- `aws_media_convert_queue` additionally needed a correction, not just a
  registry-laggard wait: row-gen proposed server-assigned off the
  registry's `primaryIdentifier=[Id]`, but the provider's own docs import
  it "using the queue name" (`terraform import aws_media_convert_queue.test
  tf-test-queue`) and its Attribute Reference states `id` is "The same as
  `name`" — client-named, not server-assigned. Left unratified anyway,
  same consistency call as the three MediaLive rows above; a future batch
  picking this up should use the client-named correction, not row-gen's
  original proposal.

## MediaStore: deprecated-service, not ratified

MediaStore (`aws_media_store_container`, `aws_media_store_container_policy`)
was in row-gen's proposal scope — the container proposed server-assigned,
the policy evidence-only via a fold on the container — but this batch does
not ratify either. AWS announced MediaStore's discontinuation effective
**November 13, 2025**, already past as of this batch (issue #65's sixth,
2026-08):

> AWS will discontinue support for AWS Elemental MediaStore on November 13,
> 2025. After November 13, 2025, you will no longer be able to access the
> MediaStore console or MediaStore resources.
> — [aws.amazon.com/blogs/media/support-for-aws-elemental-mediastore-ending-soon](https://aws.amazon.com/blogs/media/support-for-aws-elemental-mediastore-ending-soon/)

This is not just AWS's blog talking. The pinned v6.58.0 provider's own
docs for both `aws_media_store_container` and
`aws_media_store_container_policy` carry the identical notice, verbatim,
at the top of each page:

> This resource is deprecated and will be removed in a future version. AWS
> has announced the discontinuation of AWS Elemental MediaStore, effective
> November 13, 2025. The documentation recommends transitioning to
> alternative solutions: Amazon S3 for simple live streaming, or AWS
> Elemental MediaPackage for advanced use cases requiring packaging, DRM,
> or cross-region redundancy.

`AWS::MediaStore::Container`'s own registry entry is also registry-laggard
(`handlers` all false) on top of this, which would have been reason enough
on its own per the section above — but the deprecation is the decisive
call, not the laggard handlers: MediaStore is not a service temporarily
lagging the registry's rollout, it is a service AWS has already retired.
This fork's existing `DeprecatedServices` roster (`live/residue.go`) names
seven services on exactly this judgment — Pinpoint, Greengrass V1, WAF
Classic (and its Regional sibling), App Mesh, AppStream 2.0, DAX — every
one of them either mid-retirement or long superseded, and every existing
entry's own end-of-support date (Pinpoint's October 30, 2026) is still in
the future relative to when its batch landed. MediaStore is the first
entry whose end-of-support date has already passed by the time this batch
ratifies anything, which is the stronger version of the same call, not a
different one.

`live/residue.go`'s `DeprecatedServices` gained an eighth entry:

```go
{
	TFPrefix:  "aws_media_store_",
	CFNPrefix: "AWS::MediaStore::",
	Service:   "MediaStore",
	Reason:    "a service AWS discontinued effective November 13, 2025 (already past), which the pinned provider's own docs also flag as deprecated",
},
```

`residue.Lookup` checks `DeprecatedServices` before it ever reaches the
registry-laggard branch (`live/residue.go`'s `Lookup`), so this takes
priority over the handler-less classification the section above would
otherwise have given `aws_media_store_container` — a refusal against
either MediaStore type now names the deprecated-service cohort, not
registry-laggard. `go run ./tools/survey-gen -render` propagated the
change into `live/LIMITATIONS.md`'s "Deprecated or EOL services" table (76
→ 77 CloudFormation Registry types across 7 → 8 services) and removed both
MediaStore rows from the "Registry-laggard live services" table, where
they previously sat (74 types remain there, down from 76).

## MediaTailor and MediaConnect: never in scope

Both services are fully modeled in the CloudFormation Registry —
MediaTailor's 7 types (`AWS::MediaTailor::Channel`,
`ChannelPolicy`, `Function`, `LiveSource`, `PlaybackConfiguration`,
`SourceLocation`, `VodSource`) and MediaConnect's 11 (`Bridge`,
`BridgeOutput`, `BridgeSource`, `Flow`, `FlowEntitlement`, `FlowOutput`,
`FlowSource`, `FlowVpcInterface`, `Gateway`, `RouterInput`,
`RouterNetworkInterface`, `RouterOutput`) — but the pinned v6.58.0 AWS
provider ships **no** `aws_mediatailor_*` or `aws_mediaconnect_*` resource
at all: `live/mapping.json` has zero rows for either prefix, and a direct
check of the provider's GitHub tree at the pinned tag
(`internal/service/mediatailor`, `internal/service/mediaconnect`) finds
neither directory exists. Nothing for `tools/row-gen` to propose, nothing
for this batch to ratify, and nothing a future sweep can recover short of
the provider adding the resources itself.

## Elastic Transcoder: untouched, already correctly classified

Confirmed status before doing anything, per this batch's own instruction
to check first: `aws_elastictranscoder_pipeline` and
`aws_elastictranscoder_preset` are real, addressable AWS resources
(PipelineId/Arn, PresetId/Arn) that this fork's terminal taxonomy (issue
#53) already classifies `via: "cfn-unmodeled"` in `live/mapping.json`,
curated pre-dating this batch — "the CFN registry has zero
`AWS::ElasticTranscoder::*` types at all," confirmed again here against the
current `live/registry.json`. Elastic Transcoder is AWS's oldest video
service and long-since eclipsed by MediaConvert, but that judgment is
moot: there is no CloudFormation model to admit it through regardless of

to attach to it. No change to `live/LIMITATIONS.md`'s existing

## MediaPackage and MediaConvert: what the provider does not implement

Two more gaps this batch found are provider-absent, the same shape as
MediaTailor/MediaConnect above but narrower — a real CFN family with only
part of it reachable through Terraform:

- **MediaConvert** models `Queue`, `Preset` and `JobTemplate` in the CFN
  registry; the pinned provider implements only `queue.go`
  (`aws_media_convert_queue`, deferred above) — no `aws_media_convert_preset`
  or `aws_media_convert_job_template` exists in `internal/service/mediaconvert`
  at the pinned tag.
- **MediaPackage v1** models `Channel`, `Asset`, `OriginEndpoint`,
  `PackagingConfiguration` and `PackagingGroup`; the pinned provider
  implements only `channel.go` (`aws_media_package_channel`, ratified
  above).
- **MediaPackageV2** models a larger family still (`ChannelGroup`,
  `Channel`, `OriginEndpoint`, and more); the pinned provider implements
  only `channel_group.go` (`aws_media_packagev2_channel_group`, ratified
  above).

## Enumeration source

`aws_medialive_multiplex`, the one marker-path type in this batch whose
identity table entry has no `Components` for the discovery mechanism to
build from, needs list-based enumeration to be swept — the same gap the
storage and ec2-networking batches documented for `aws_efs_file_system`
and `aws_ec2_client_vpn_endpoint`. `live/registry.json`'s
`AWS::MediaLive::Multiplex` entry is `handlers.list: true` with no
required input ("list-free"), so `internal/live/registry.Roster.EnumerationSource`
resolves a CFN type for it and the Cloud Control fallback
(`internal/live/discovery/cloudcontrol.go`) is the code path that would
enumerate it once a caller wires the command layer to it — not yet done,
the same documented, non-blocking gap issue #47's worked example
established. The five IVS/IVSChat marker types share the identical shape:
each is `handlers.list: true`, list-free, in the registry, even though
`live/survey-full.json` shows none of the five ships a native provider
list resource either. The remaining rows (`aws_media_package_channel`,
`aws_media_packagev2_channel_group`, `aws_medialive_multiplex_program`)
need no enumeration fallback at all — their identity is built straight
from configuration.

## Verifying by hand

A pinned floci container (`ghcr.io/lex00/floci`, the same image
`internal/live/flocitest`'s `defaultImage` runs) was checked three ways:
its own `/_localstack/health` service list, a direct AWS CLI/raw-HTTP
probe against the router, and a real `terraform apply` of this cohort's
full nine-resource estate.

**`/_localstack/health`**: the service list carries no entry for
`medialive`, `mediaconvert`, `mediapackage`, `mediapackagev2`,
`mediastore`, `ivs` or `ivschat` — every service this batch touches,
ratified or not, absent from the router's own advertised surface.

**Raw HTTP probe** (bypassing the AWS CLI's own endpoint-resolution
quirks): a hand-built `MediaLive.ListChannels` request against the
container's root endpoint gets back a clean, unambiguous answer —

```
HTTP/1.1 404 Not Found
x-amzn-query-error: UnknownOperationException;Sender
{"__type":"UnknownOperationException","message":"Unknown operation: MediaLive.ListChannels"}
```

— the same router-level "this service has no handler registered at all"
tell the security batch's ACM-PCA/GuardDuty/Macie2/SecurityHub probe
found, here reproduced through the JSON protocol layer directly rather
than through the CLI. The AWS CLI's own `medialive list-channels` and `ivs
list-channels` calls each fall through to a generic S3-shaped XML handler
instead (`NoSuchBucket`, `InvalidArgument`) — the same fallthrough
symptom, one layer up.

**Real `terraform apply`**, the full nine-resource cohort, endpoints
pointed at the pinned container, real provider 6.58.0 in the loop: every
one of the nine `Create` calls fails identically —

```
Error: creating AWS IVS (Interactive Video) Channel: operation error ivs: CreateChannel,
https response error StatusCode: 400, ... deserialization failed, failed to decode
response body, invalid character '<' looking for beginning of value
```

— floci answering an HTML error page where the AWS SDK expects JSON, for
all nine resources without exception (`aws_ivschat_logging_configuration`
included, once its own `destination_configuration` override — see
`tools/estate-gen/overrides.go` — supplied the Required block the generic
pass does not fill). `terraform state list` afterward is empty: nothing
partially created, nothing to destroy, a clean all-nine failure at the
first API call each resource makes.

None of this blocks ratification — issue #65's own recipe treats a floci
gap as "documented in the cohort README, not blocking," the same standing
the storage batch's EFS/FSx rows, the RDS batch's `aws_db_instance` row and
the security batch's ACM-PCA/GuardDuty/Macie2/SecurityHub rows already
have. Every finding here is a *floci* coverage gap, not an identity-soundness
problem with the table rows themselves: the identity evidence for all nine
types comes from the real, pinned AWS provider's own documented
Argument/Attribute/Import sections (`live/import-grammar.json`), confirmed
independent of whether any emulator can create the resource at all.
`terraform validate` against the real, pinned provider release (6.58.0) is
what this fixture actually gates on in CI (see "Gating" below); the
`terraform apply`, `curl` and `aws` commands above reproduce every finding
here against the pinned floci image.

### Provenance quirk: the "name" false parent match

`tools/estate-gen`'s generic pass wires a required argument to another
resource's own identity argument by matching argument *names*
(`gen.go`'s `parentRef`). `aws_media_packagev2_channel_group`'s own
identity is `Components: []Component{attr("name")}` — its own identity
argument is *named* "name" — and `aws_medialive_multiplex` also has a
plain `name` argument (its own client-chosen label, not an identity
component at all: the type is server-assigned). `parentRef`'s same-name
tiebreaker (comment in `gen.go`) exists for exactly the case where *two*
types both claim an argument as their own identity component
(`aws_iam_role` vs. `aws_lambda_capacity_provider` in that comment's own
example) — it has no guard for a server-assigned type's *ordinary*,
non-identity argument colliding by name with an unrelated type's identity
argument, because `identityArgName` already returns `ok=false` for a
server-assigned type and so never registers a competing claim. Left
uncorrected, the multiplex's `name` would have pointed at
`aws_media_packagev2_channel_group.app.name` — an unrelated MediaPackage
channel group's label, not a real dependency. `tools/estate-gen/overrides.go`
fixes it to a literal string. Same collision class as the security batch's
"detector_id" quirk (`live/e2e/estates/security/README.md`), one same-name
argument away from a false link instead of no link at all.
