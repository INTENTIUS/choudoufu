# data-movement cohort

Cohort: `data-movement`. Ratified by: the sixth registry-backed ratification
batch against #40's strategy and #44's row generator, issue #65's recipe —
data movement and transfer (Transfer Family's server/user/workflow/connector
core, DataSync's agents/locations/tasks in full, DMS including its three
registry-laggard replication types, AppIntegrations). Mechanism: #48 (see
`live/e2e/estates/example/README.md` for the proof-of-mechanism cohort, and
`live/e2e/estates/lambda/README.md` for the first registry-backed cohort
this one follows). Generated by `tools/estate-gen` (issue #56) from
hashicorp/aws 6.58.0's schema and `internal/live/identity/table.go`'s
identity table.

This cohort exercises every type this batch ratified into
`internal/live/lint/admission.go` and `internal/live/identity/table.go`.

Regenerate with:

```
go run ./tools/estate-gen -cohort data-movement -types aws_appintegrations_data_integration,aws_appintegrations_event_integration,aws_datasync_agent,aws_datasync_location_azure_blob,aws_datasync_location_efs,aws_datasync_location_fsx_lustre_file_system,aws_datasync_location_fsx_ontap_file_system,aws_datasync_location_fsx_openzfs_file_system,aws_datasync_location_fsx_windows_file_system,aws_datasync_location_hdfs,aws_datasync_location_nfs,aws_datasync_location_object_storage,aws_datasync_location_s3,aws_datasync_location_smb,aws_datasync_task,aws_dms_certificate,aws_dms_endpoint,aws_dms_event_subscription,aws_dms_replication_config,aws_dms_replication_instance,aws_dms_replication_subnet_group,aws_dms_replication_task,aws_dms_s3_endpoint,aws_transfer_connector,aws_transfer_server,aws_transfer_user,aws_transfer_workflow -out live/e2e/estates/data-movement
```

(`-types` is explicit because `defaultCohortTypes` matches a cohort name
against exactly one `live/mapping.json` CFN service, and this cohort spans
four — Transfer, DataSync, DMS and AppIntegrations — the same reason the
`devtools`, `data`, `ecs-eks`, `storage` and `route53-cloudfront` cohorts'
own README regenerate commands are illustrative rather than literally
reproducible with `-cohort` alone.)

Left outside this batch's named scope, and not part of this cohort: six
further Transfer Family types (`aws_transfer_certificate`,
`aws_transfer_profile`, `aws_transfer_web_app`,
`aws_transfer_web_app_customization`, `aws_transfer_agreement`,
`aws_transfer_ssh_key`) — issue #65 names servers, users, workflows and
connectors only. Storage Gateway (registry-absent beyond a single TapePool
type — cfn-unmodeled) and MGN/DRS (no CFN Registry footprint at all) are
skipped entirely; row-gen proposes nothing worth ratifying for either.

## Verifying by hand

```
docker run -d --rm -p 4622:4566 --name tofu-data-movement-cohort-verify \
  ghcr.io/lex00/floci@sha256:4753246c0260a22af1056c65993f4d73b0a907729a9580b9baba5d628b6dad34

export AWS_ENDPOINT_URL=http://localhost:4622 AWS_ACCESS_KEY_ID=test \
       AWS_SECRET_ACCESS_KEY=test AWS_REGION=us-east-1

terraform init
terraform validate
terraform apply -auto-approve

terraform destroy -auto-approve
docker rm -f tofu-data-movement-cohort-verify
```

`terraform validate` passes against the real provider release (6.58.0) this
fixture pins — confirming every argument name above is real, not just
registry-plausible.

An `apply` against the pinned `lex00/floci` image was run by hand during
ratification (not wired into any automated tier — see "Gating" below). The
container's own startup log ("Enabled services: [...]") lists `transfer`
but none of `datasync`, `dms` or `appintegrations`, and the apply confirmed
it exactly:

- `aws_transfer_server.app` and `aws_transfer_user.app` both created (and
  read back) cleanly — Transfer's `CreateServer` and `CreateUser` are real.
- `aws_transfer_connector.app` and `aws_transfer_workflow.app` both fail
  create with `UnknownOperationException: Unknown operation:
  AmazonTransfer.CreateConnector` / `.CreateWorkflow` — Transfer's own
  coverage in this image is partial, real but incomplete, not evidence
  against either type's admission (the identity and the documented import
  behavior are independently confirmed against the provider's own docs; see
  `internal/live/identity/table.go`).
- Destroying the server that did create surfaced a genuine lifecycle gap
  independent of admission: `DeleteServer` 409s
  (`ConflictException: Server must be in OFFLINE state to be deleted`) — the
  same server-must-be-stopped-before-delete behavior the real AWS API
  documents; this cohort's fixture does not attempt to stop the server
  first, so a hand-verification run needs `docker rm -f` to clean up rather
  than a clean `terraform destroy`.
- Every DataSync type (the agent and all eleven locations) fails create
  with `UnknownOperationException: Unknown operation:
  FmrsService.Create...` — entirely unimplemented in this image, consistent
  with its absence from "Enabled services".
- Every DMS type that reached a create call (`aws_dms_certificate`,
  `aws_dms_endpoint`, `aws_dms_event_subscription`,
  `aws_dms_replication_instance`, `aws_dms_replication_subnet_group`,
  `aws_dms_s3_endpoint`) fails the same way
  (`UnknownOperationException: Unknown operation:
  AmazonDMSv20160101.Create...`/`.ImportCertificate`) — entirely
  unimplemented. `aws_dms_replication_config.app` and
  `aws_dms_replication_task.app` never reach their own create call at all:
  both reference `aws_dms_endpoint.app.endpoint_arn`, which never exists
  once that create fails, so Terraform's own dependency graph cancels them
  rather than attempting a doomed call.
- `aws_appintegrations_event_integration.app` fails create with a
  deserialization error (`400`, `invalid character '<' looking for
  beginning of value`) rather than a clean `UnknownOperationException` —
  the request lands on some unrouted fallback that returns an HTML error
  page instead of a JSON one, the same "entirely absent" verdict as
  DataSync and DMS, just a messier failure shape.
  `aws_appintegrations_data_integration.app` never reaches its own create
  call either, for the same dependency-cancellation reason as the two DMS
  types above (it references
  `aws_appintegrations_event_integration.app.name`).

None of this blocks ratification: every type's admission rests on the
identity being recoverable from configuration and confirmed against the
provider's own documented import behavior (`internal/live/identity/table.go`),
not on this one pinned emulator image implementing the service. The gaps
above are the same "real but partial" / "entirely unimplemented" shape
earlier batches' own cohort READMEs already document for their own emulator
gaps (see `live/e2e/estates/devtools/README.md`, `live/e2e/estates/storage/README.md`).

Two apply-time-only argument gaps `terraform validate` does not catch were
found this way and are fixed in `tools/estate-gen/overrides.go` rather than
just noted in prose, since both are cheap, real fixes independent of floci's
own coverage: `aws_datasync_agent.app` needs one of `activation_key` or
`ip_address` (this fixture sets `activation_key`, since `ip_address` makes
Terraform itself perform a live HTTP GET against that address before the
DataSync call happens at all); `aws_datasync_location_hdfs.app` needs
`authentication_type` set before the AWS SDK's own client-side request
validation will even attempt the call.
