# security cohort

Cohort: `security`. Ratified by: the fifth registry-backed ratification
batch against #40's strategy and #44's row generator, covering issue #65's
"security and secrets" suggestion — Secrets Manager, the KMS remainder,
the SSM remainder, ACM-PCA, GuardDuty, Macie2, SecurityHub, Inspector2 and
WAFv2. Mechanism: #48 (see `live/e2e/estates/example/README.md` for the
proof-of-mechanism cohort, and `live/e2e/estates/lambda/README.md` for the
first registry-backed cohort this one follows). Generated by
`tools/estate-gen` (issue #56) from hashicorp/aws 6.58.0's schema and
`internal/live/identity/table.go`'s identity table.

This cohort exercises every type this batch ratified into
`internal/live/lint/admission.go` and `internal/live/identity/table.go`:
46 types across nine services, rejecting or deferring roughly as many
again. This batch's own instruction was to reject freely — several of
these services are dense with credential- and permission-adjacent types —
and the rejected list below is long on purpose.

## Credential-adjacent exclusions

Issue #65's own instruction for this batch: reject freely, and extend
`internal/live/lint/admission.go`'s `opsExcluded`-style reasoning
deliberately wherever a new credential-carrying type turns up, saying so
rather than folding it silently into an ordinary rejection.

Two KMS-remainder types are the finding. Both already resolve to "moves to
Ops" on ordinary recoverability grounds alone (`live/survey-full.json`:
untaggable, no native provider list resource, `cfn-unmodeled` — no
`AWS::KMS::Grant` or `AWS::KMS::CustomKeyStore` type exists in the CFN
Registry to fall back on either), so neither actually needed a credential
judgment to stay out. This batch makes the judgment explicit anyway,
because it would matter if the recoverability gap ever closed:

- **`aws_kms_grant`**: a grant conveys scoped, revocable *permission* to
  use a key, returned at create time as a `GrantToken` — a bearer
  credential in miniature (confirmed live: floci's `kms:CreateGrant`
  returns exactly this shape, a `GrantToken` alongside the `GrantId`). Even
  setting recoverability aside, a live read of this type's population would
  be reading a permission grant back into a plan, the same category of
  operation `opsExcluded`'s `aws_iam_access_key` entry excludes an access
  key over.
- **`aws_kms_custom_key_store`**: its own `key_store_password` argument is
  a literal password value (the CloudHSM cluster's kmsuser credential, or
  the external key manager's proxy credential for an XKS store) — not
  merely permission-adjacent the way a grant is, but a plain secret in the
  resource's own schema, the same shape `opsExcluded`'s comment already
  names as the class ("the secret half is unreadable after create").

Neither entry is added to `tools/survey-gen/classify.go`'s `opsExcluded`
map itself: doing so would relabel an already-correct "moves to Ops"
verdict without changing it (both fail on recoverability regardless), and
`opsExcluded`'s own doc comment scopes it to judgments no schema carries —
these two are schema-provable exclusions first, credential-adjacent
second. The judgment is recorded here, in the identity table's own comment
for the KMS-remainder rows, and in this README, so a future batch that
finds a CFN mapping or a native list resource for either type still has to
read this reasoning before reconsidering them.

No other rejected type in this batch carries a live-readable secret value
of its own. `aws_acmpca_certificate` and `aws_acmpca_certificate_authority_certificate`
carry certificate/CSR material, which is public-key data, not a secret —
ratifying the singleton-child certificate above follows the same
`aws_kms_key_policy`/`aws_secretsmanager_secret_policy` precedent every
other resource-policy row in this fork's table already sets.

## A registry/schema mismatch (SecurityHub's legacy v1 types)

Several SecurityHub v1 types' CFN registry entries claim
`tagging.taggable: true` (`AWS::SecurityHub::Hub`, `AWS::SecurityHub::FindingAggregator`,
`AWS::SecurityHub::Standard`), but `live/survey-full.json`'s signal — read
off the real, pinned AWS provider's wire schema, not the registry — shows
the v1 *resource* itself ships no `tags` argument at all. This is the
"newer-API-generation false friend" issue #65 flagged (the same genre of
gap the ram-servicecatalog family sweep's own overlay comments document
for `aws_securityhub_standards_control`'s identity, cited below): the CFN
Registry models what the *service API* accepts, and SecurityHub's Hub API
does accept tags at the CloudFormation layer — but the Terraform provider's
`aws_securityhub_account` resource, unlike its `aws_securityhub_account_v2`
successor, never plumbed a `tags` argument through. Trusting the registry's
claim alone would have produced a marker row this batch's own estate could
never round-trip a tag through.

The newer v2 generation (`HubV2`, `AggregatorV2`, `AutomationRuleV2`,
`ConnectorV2`) is where the registry and the real schema agree, and all
four ratify above. `aws_securityhub_automation_rule` — the *v1* automation
rule — is the one v1 type this batch found where the real schema itself
confirms genuine tagging support, so it ratifies alongside its v2 sibling
rather than being swept into the same untaggable-singleton bucket as
`aws_securityhub_account`.

`aws_securityhub_standards_control` and `aws_securityhub_standards_control_association`
are a related but distinct finding, already caught upstream: the
ram-servicecatalog family sweep (issue #53,
`tools/mapping-gen/overlay.d/sweep-ram-servicecatalog.json`) recorded that
`AWS::SecurityHub::SecurityControl`'s own primary identifier is
`SecurityControlId` alone — the newer, standard-independent unified
control view — not the per-standard-scoped `standards_control_arn` these
two TF types actually manage, so `live/mapping.json` correctly leaves both
types unmapped to that CFN type rather than folding onto it. Both ratify
above through the provider's own Identity Schema directly instead.

## A listability gap admitted anyway (WAFv2's four marker types)

`internal/live/registry.Roster.Listable` reports every one of
`aws_wafv2_ip_set`, `aws_wafv2_regex_pattern_set`, `aws_wafv2_rule_group`
and `aws_wafv2_web_acl` unlistable through the Cloud Control fallback:
each CFN type's `handlers.list_required_input` names `Scope`, and that
package's own doc comment is explicit that `Listable` is true "only for
`handlers.list` with an *empty* required-input list ... this package's
callers have no way to supply [one] from a bare type name" — the identical
shape that already excludes `aws_efs_mount_target` from the storage batch.
No native provider list resource exists for any of the four either
(`live/survey-full.json`: `list_resource: false`).

All four are admitted anyway, on the same footing the storage batch's
entire FSx family was: `aws_fsx_lustre_file_system` and its five FSx
siblings are server-assigned, taggable, and reach *no* enumeration
mechanism at all today (their own CFN type is not even `handlers.list`,
let alone list-with-no-input) — admission there does not depend on a
working discovery path existing yet, only on the identity concept itself
being sound and the type being taggable in principle (an estate-wide
tag-based sweep, `internal/live/cloudcontrol`'s `NewTagging` client, is
tested but not yet wired into discovery — see that package's own history).
The gap is real and worth tracking, but it is a discovery-mechanism
limitation to close later, not a reason to withhold admission now.

## A waiter cohort

`aws_guardduty_invite_accepter`, `aws_macie2_invitation_accepter` and
`aws_securityhub_invite_accepter` are the same shape, one per service:
each flips a pending cross-account invitation to accepted and has no cloud
resource of its own (no identity schema in v6.59.0, because there is

`aws_acm_certificate_validation` category — "waiter: ... waiting belongs to
the lifecycle layer" — extended to three more services rather than
re-argued for each.

## aws_ssm_document and the swap rule

`live/residue.go`'s `EmulatorBlocked` roster carries exactly one
`Admitted: false` entry today: `aws_ssm_document`, curated as "the
roster's sole 'kept out of a wiring slice entirely' example" — floci
answers `ssm:CreateDocument` with `UnsupportedOperation` outright, and that
package's own comment judges admitting it "real work with nothing to prove
it against." `internal/live/lint/residue_test.go`'s
`TestRefusalNamesEmulatorBlockedCohort` fixture
(`testdata/residue-emulator`) depends on this type staying unadmitted to
exercise the `RuleUnadmittedType` refusal for `CohortEmulatorBlocked` at
all.

This batch re-verified the gap live rather than trusting the prior
record: `aws --endpoint-url http://floci ssm create-document ...` still
answers `UnsupportedOperation` against the pinned image, unchanged.
`aws_ssm_document`'s identity is otherwise clean — client-named by its
`name` argument, taggable, listable, no different in shape from
`aws_dynamodb_table` or `aws_cloudfront_key_value_store` — and the same
live probe found floci blocks the *entire* SSM remainder this batch
otherwise ratifies (`ssm:CreateAssociation`, `CreatePatchBaseline` and
`CreateMaintenanceWindow` all answer the identical `UnsupportedOperation`,
not just `CreateDocument`). Ratifying the remainder anyway (see "SSM
remainder" above) while leaving `aws_ssm_document` alone could look
inconsistent without this note: it is not. The remainder's ratification
rests on identity soundness independent of floci support, the same
standard `aws_db_instance` and the whole storage batch's FSx/EFS rows

### Provenance quirk: the "detector_id" collision

`tools/estate-gen`'s generic pass wires a required argument to another
resource's own identity argument by matching argument *names*
(`gen.go`'s `parentRef`). `aws_guardduty_organization_configuration`'s own
identity is `Components: []Component{attr("detector_id")}` — its own
identity argument is *named* `detector_id` — so every other coverage row
in this cohort with a plain `detector_id` argument (the filter, IP set,
threat intel set, publishing destination and member rows) matched against
*that* resource instead of the real `aws_guardduty_detector` marker, which
has no `Components` at all (server-assigned types self-identify by nothing
in configuration) and so never appears as a `parentRef` candidate. Left
uncorrected, every GuardDuty child row in this estate would have pointed
at `aws_guardduty_organization_configuration.app.detector_id` — itself
just an echo of a placeholder string, not a real detector. `tools/estate-gen/overrides.go`
fixes all six affected rows (five children plus the organization
configuration singleton itself) to reference `aws_guardduty_detector.app.id`
directly. Same collision class as `aws_glue_catalog_database`'s existing
entry in that file (the data-plane batch's own "name" collision with
`aws_athena_data_catalog`), fixed the same way.

## Verifying by hand

A pinned floci container (`ghcr.io/lex00/floci`, the same image
`internal/live/flocitest`'s `defaultImage` runs) was probed twice: first
directly with the AWS CLI for every service in this batch's scope, before
any ratification decision; then with a real `terraform apply` against a
trimmed slice of this cohort's own served resources, after ratification,
to confirm the identity table's rows round-trip through the actual
provider rather than only through hand-typed CLI calls.

**Direct AWS CLI probe, every service in scope:**

- **Secrets Manager, KMS, WAFv2**: fully served at the API level.
  `secretsmanager:CreateSecret` minted the documented six-character-suffixed
  ARN live; `kms:CreateKey`, `TagResource`, `ListResourceTags`, `CreateGrant`
  and `ListGrants` all round-trip; `wafv2:CreateIPSet`/`ListIPSets`
  round-trip (tag persistence itself did not at the raw-API level: a
  `TagResource` call against a freshly created IP set returned no error,
  but a follow-up `ListTagsForResource` came back empty).
- **SSM**: partially served. `ssm:PutParameter` (the pre-existing
  `aws_ssm_parameter`) works; `CreateDocument`, `CreateAssociation`,
  `CreatePatchBaseline` and `CreateMaintenanceWindow` all answer
  `UnsupportedOperation`. See "aws_ssm_document and the swap rule" above.
- **ACM-PCA, GuardDuty, Macie2, SecurityHub, Inspector2**: none served at
  all. `acm-pca:CreateCertificateAuthority` answers `UnknownOperationException`
  (the service is not registered with floci's router at all — absent
  from its own `/_localstack/health` service list); `guardduty:CreateDetector`,
  `macie2:EnableMacie` and `securityhub:EnableSecurityHub` all fall through
  to a generic S3-shaped `InvalidArgument` handler rather than a real
  `UnsupportedOperation`, the router-level tell that these services have no
  handler registered at all; `inspector2:ListFilters` gets the same
  fallthrough. None of the five services this batch ratifies from is
  reachable against the pinned image today.

**Real `terraform apply`, the served subset** (`aws_secretsmanager_secret`,
`aws_secretsmanager_secret_policy`, `aws_kms_external_key`,
`aws_kms_replica_key`, `aws_wafv2_ip_set`, `aws_wafv2_web_acl`,
`aws_wafv2_web_acl_rule`, `aws_ssm_association`,
`aws_ssm_maintenance_window`, `aws_ssm_patch_baseline`, endpoints pointed
at the pinned container, real provider 6.58.0 in the loop):

- `aws_secretsmanager_secret.app`, `aws_wafv2_ip_set.app`,
  `aws_wafv2_web_acl.app` and `aws_wafv2_web_acl_rule.app` all created
  cleanly and destroyed cleanly — a full round trip through the real
  provider, not just the raw API.
- `aws_secretsmanager_secret_policy.app` creates but never finishes: the
  provider's own post-create read (`GetResourcePolicy`) polls for two
  minutes and times out with "couldn't find resource." Direct inspection
  confirms why — `secretsmanager:GetResourcePolicy` against floci returns
  `200 OK` with the secret's ARN and name but no `ResourcePolicy` field at
  all, so `PutResourcePolicy` is silently accepted and never persisted.
  Same shape as `aws_iam_role`'s own `GetRole`-omits-Tags entry in
  `live/residue.go`: the write succeeds, the read-back the provider itself
  requires does not see it.
- `aws_kms_external_key.app` creates (floci accepts `Origin: EXTERNAL` on
  `CreateKey` and returns a real key ID), but the provider's own post-create
  invariant check then fails immediately: "KMS External Key (…) has invalid
  Origin: AWS_KMS" — floci's `CreateKey` accepts the origin parameter but
  always reports the key back as `AWS_KMS`-origin regardless of what was
  requested, which the provider (correctly) treats as the wrong resource.
- `aws_kms_replica_key.app` fails outright: `kms:ReplicateKey` answers
  `UnsupportedOperation`.
- `aws_ssm_association.app`, `aws_ssm_maintenance_window.app` and
  `aws_ssm_patch_baseline.app` all fail exactly as the CLI probe predicted:
  `CreateAssociation`, `CreateMaintenanceWindow` and `CreatePatchBaseline`
  each answer `UnsupportedOperation`.

None of this blocks ratification — issue #65's own recipe treats a floci
gap as "documented in the cohort README, not blocking," the same standing
the storage batch's EFS/FSx rows and the RDS batch's `aws_db_instance` row
already have. Every gap found here is a *floci* limitation (a real-AWS run
would not hit any of them: `Origin` really is respected by real KMS,
`GetResourcePolicy` really does return the policy, `ReplicateKey`/`CreateAssociation`/
`CreateMaintenanceWindow`/`CreatePatchBaseline` are all real, long-standing
AWS APIs) — none is an identity-soundness problem with the table rows
themselves. `terraform validate` against the real, pinned provider release
(6.58.0) is what this fixture actually gates on in CI (see "Gating"
below); the `terraform apply` and `docker run` commands above reproduce
every finding here against the pinned floci image.
