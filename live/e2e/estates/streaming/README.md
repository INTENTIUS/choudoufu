# streaming cohort

Cohort: `streaming`. Ratified by: the fifth registry-backed ratification
batch against issue #65's recipe — MQ (AmazonMQ), MSK (clusters,
configurations, serverless, plus its KafkaConnect service-alias), AppFlow,
one AppSync type, EventBridge Pipes, and Scheduler's schedule group.
Mechanism: #48 (see `live/e2e/estates/example/README.md` for the
proof-of-mechanism cohort, and `live/e2e/estates/lambda/README.md` for the
first registry-backed cohort this one follows).

Generated by `tools/estate-gen` (issue #56) from hashicorp/aws 6.58.0's
schema and `internal/live/identity/table.go`'s identity table. Regenerate
with:

```
go run ./tools/estate-gen -cohort streaming -types aws_mq_broker,aws_mq_configuration,aws_msk_cluster,aws_msk_configuration,aws_msk_serverless_cluster,aws_mskconnect_connector,aws_mskconnect_custom_plugin,aws_mskconnect_worker_configuration,aws_appflow_connector_profile,aws_appflow_flow,aws_appsync_graphql_api,aws_pipes_pipe,aws_scheduler_schedule_group -out /tmp/estate-gen/streaming
```

(`-types` is explicit because this cohort spans seven CFN services — AmazonMQ,
MSK, KafkaConnect, AppFlow, AppSync, Pipes, Scheduler — and
`tools/estate-gen`'s no-`-types` default only ever matches one CFN service
per cohort name.)

This cohort exercises every type this batch ratified into
`internal/live/lint/admission.go` and `internal/live/identity/table.go`.

## Rejected

Six of `tools/row-gen`'s proposals in this batch's scope were rejected on
independent verification against the provider's documented import behavior
(and, where the pinned v6.59.0 release ships one, its own
`ResourceIdentitySchema`), not against the registry:

- **`aws_appsync_api`** — row-gen proposed server-assigned via the
  registry's `ApiArn` (`AWS::AppSync::Api`'s `primaryIdentifier`). The
  provider disagrees: its documented import command (`terraform import
  aws_appsync_api.example example-api-id`) and Attribute Reference both
  name the identifier `api_id`, not the arn. `api_id` is itself a registry
  `readOnlyProperty`, so a corrected row is possible in principle — this
  batch does not write one, leaving the type out rather than guessing which
  of the registry's two readOnly fields the provider actually meant.
- **`aws_appsync_api_cache`** and **`aws_appsync_api_key`** — row-gen
  proposed both server-assigned off registry `readOnlyProperties` (`Id`,
  `ApiKeyId`). Independent inspection of `live/registry.json` finds both
  CFN types' `handlers` block is `create`/`read`/`update`/`delete`/`list`
  **all false** — the "registry-laggard" shape `live/LIMITATIONS.md`'s
  Registry-laggard live services table already names both of these exact
  types for (they are two of that table's existing rows, unchanged by this
  batch). A registry entry with no working handler at all supplies no real
  evidence, whatever its `primaryIdentifier` field claims.
- **`aws_appsync_domain_name_api_association`** — row-gen proposed
  server-assigned via the registry's `ApiAssociationIdentifier`. The
  provider disagrees outright, not just on which field: its documented
  import command (`terraform import
  aws_appsync_domain_name_api_association.example example.com`) imports by
  the client-supplied `domain_name` argument, already in configuration —
  this type is client-named, not server-assigned, and the registry's own
  claim is simply wrong for what this provider does.
- **`aws_appsync_function`** — row-gen proposed server-assigned via the
  registry's `FunctionArn`, a single field. The provider disagrees: its
  documented import command (`terraform import
  aws_appsync_function.example xxxxx-yyyyy`) is a hyphen-joined composite
  of `api_id` (a configured argument) and `function_id` (a server-assigned
  output first available only after creation) — the correction needs a
  component `internal/live/identity/table.go`'s vocabulary does not have
  (composing a configured argument with the type's own not-yet-created
  output), not just a separator guess.
- **`aws_scheduler_schedule`** — row-gen itself never proposed this row:
  its `name` argument was GUESSED, not backed by an identity schema,
  `live/import-grammar.json` or the carve seed, so it landed
  evidence-only. Independent verification confirms row-gen's own caution
  was warranted — the provider's documented import ID is the composite
  `group_name/name`, and its own v6.59.0 identity schema lists both
  `group_name` and `name` as `required_for_import` but neither as a
  required argument. This batch ratifies what row-gen proposes; a row it
  never proposed stays out.

## Deferred, out of this batch's scope

MSK's scope this batch is deliberately narrow — clusters, configurations
and the serverless cluster, plus MSK Connect. `tools/row-gen`'s MSK section
proposes six more types this batch does not evaluate at all, left for a
future batch: `aws_msk_cluster_policy`, `aws_msk_replicator`,
`aws_msk_single_scram_secret_association` and `aws_msk_vpc_connection` are
all pastable proposals; `aws_msk_scram_secret_association` and
`aws_msk_topic` are evidence-only. None of the six is rejected on the
merits here — they are simply out of scope.

SWF never entered scope at all: `live/mapping.json` carries `aws_swf_domain`
as `via: "cfn-unmodeled"` (`tools/mapping-gen/overlay.d/sweep-servicequotas-
xray.json`'s own note: "all three services have zero matching CFN Registry
types at all"), so `tools/row-gen` prints nothing for it — registry-absent,
per issue #65's own scoping.

## Untaggable types

Two types in the table above carry no `tags` argument in the AWS provider:
`aws_msk_configuration` (its Argument Reference names no tags block at all,
and `live/registry.json`'s own `tagging.taggable` is `false`) and
`aws_appflow_connector_profile` (its Attribute Reference exports only `arn`
and `credentials_arn`, no tags — also `tagging.taggable: false` in the
registry). Both are added to `live/LIMITATIONS.md`'s "Untaggable types
cannot be removed by the sweep" entry, which — since issue #54 landed —
derives from `live/survey-full.json` across the whole registry-backed
roster rather than the curated 68 intersected with the admission table, so
no doc-gate follow-up is needed the way the messaging batch's
`aws_cloudwatch_dashboard` once required.

Applied by hand against the pinned floci image (the same digest
`internal/live/flocitest.defaultImage` pins). The supporting `aws_iam_role`,
`aws_appsync_graphql_api` and `aws_scheduler_schedule_group` create cleanly
with real identity values assigned immediately (`aws_appsync_graphql_api.app`,
for instance, comes back with a real `8457a224ccce4cb7bd00fa8c67`-shaped id
in well under a second). `aws_mq_broker` needed its `engine_type` switched
from `ACTIVEMQ` to `RABBITMQ` first — floci's own AmazonMQ emulation refuses
`ACTIVEMQ` outright (`BadRequestException: Only RABBITMQ EngineType is
supported`, both values equally real and valid against the actual AWS API,
so this is a floci accommodation, not a correctness compromise, see the
Provenance table above) — after which `CreateBroker` is accepted and the
broker's identity (`arn`, `id`) is assigned immediately, though the broker
then settles into `BrokerState: CREATION_FAILED` asynchronously, almost
certainly because this cohort supplies no `subnet_ids`/`security_group_ids`
and floci's sandbox has no default VPC to fall back to the way real AWS
does — a networking gap in the verification environment, not in the
identity this batch ratifies (the create call's synchronous response
already proves the ARN/id shape). None of what follows is evidence against
the remaining eight either:

- `aws_appflow_connector_profile`, `aws_appflow_flow`,
  `aws_mq_configuration`, `aws_msk_configuration`,
  `aws_mskconnect_custom_plugin` and `aws_mskconnect_worker_configuration`
  all fail identically: `deserialization failed, failed to decode response
  body, invalid character '<' looking for beginning of value`. floci's own
  container log has no matching line at all for any of the six
  `Create*` calls — no warning, no stack trace, nothing — which is what an
  unmapped REST route looks like from the framework's side: a bare HTML
  404 page the AWS SDK then fails to parse as JSON. AppFlow, AmazonMQ (only
  `CreateBroker`, not `CreateConfiguration`) and KafkaConnect (only
  `CreateConnector`, not `CreateCustomPlugin`/`CreateWorkerConfiguration`)
  are each listed among floci's own "Enabled services," so this is six
  specific unimplemented actions, not six unmodeled services — a floci
  coverage gap, not evidence against any of these six types' identity.
- `aws_msk_cluster` and `aws_msk_serverless_cluster` both start a real
  `RedpandaManager` (a genuine Redpanda Docker container floci launches to
  back each MSK cluster it emulates), which needs floci's own container to
  reach a Docker daemon over TCP at `localhost:2375`. This batch's
  verification environment has no such daemon exposed, and floci's own log
  names the exact failure: `java.net.SocketException: No such file or
  directory` from `RedpandaManager.startContainer`, retried immediately and
  indefinitely rather than failing outright — a Docker-in-Docker
  requirement this environment cannot supply, not an identity problem. Both
  types' `Arn` identity is independently confirmed correct by the
  provider's own v6.59.0 `ResourceIdentitySchema` regardless (see the
  Coverage map above).
- `aws_mskconnect_connector` and `aws_pipes_pipe` both reference
  `aws_msk_cluster.app`'s own computed outputs (`bootstrap_brokers` and
  `arn` respectively), so neither could be independently exercised while
  `aws_msk_cluster` itself cannot complete in this environment. Left for a
  verification pass with real Docker-in-Docker access.
