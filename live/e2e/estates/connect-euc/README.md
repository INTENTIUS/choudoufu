# connect-euc cohort

Cohort: `connect-euc`. Ratified by: the eighth registry-backed ratification
batch against issue #65's recipe — Amazon Connect, WorkSpaces and
WorkSpacesWeb. Mechanism: #48 (see `live/e2e/estates/example/README.md`
for the proof-of-mechanism cohort, and `live/e2e/estates/lambda/README.md`
for the first registry-backed cohort this one follows).

Generated by `tools/estate-gen` (issue #56) from hashicorp/aws 6.58.0's
schema and `internal/live/identity/table.go`'s identity table. Regenerate
with:

(`-types` is explicit because this cohort spans three CFN services —
Connect, WorkSpaces, WorkSpacesWeb — and `tools/estate-gen`'s no-`-types`
default only ever matches one CFN service per cohort name.)

This cohort exercises every type this batch ratified into
`internal/live/lint/admission.go` and `internal/live/identity/table.go`: 34
types across the three services, rejecting one
(`aws_connect_instance_storage_config`). AppStream (deprecated, never
evaluated) and WorkSpaces' directory/bundle surface (real but outside
`tools/row-gen`'s CFN-registry-keyed scope) are out of this batch's scope
entirely. See `internal/live/identity/table.go` for the per-type evidence.

**A note on scope drift mid-batch**: this batch's recipe named
WorkSpacesWeb's eight `*_association` property-children of
`AWS::WorkSpacesWeb::Portal` as deferred, pending issue #68's fold-child
admission path merging to main. That branch merged while this batch was
being written; re-checking (grep for a fold-child section in
`internal/live/lint/admission.go`) found it landed, and all eight ratify
below as a result — see "Parent-derived composite (fold-child)" in the
coverage map.

## Rejected

- **`aws_connect_instance_storage_config`** — row-gen filed this
  needs-hand-separator (`InstanceArn`, `AssociationId`, `ResourceType`).
  The real Import section confirms the same three-part, colon-joined
  composite the nine ratified Connect children above have — `instance_id`
  and `resource_type` are both configuration arguments, but the middle
  component, `association_id`, is the provider's own Attribute
  Reference-only output (a UUID Connect mints at create time). Every
  ratified Connect child above is taggable, which is what makes the same
  composite shape ratifiable there; this type's Argument Reference names
  no `tags` block at all — untaggable, so no marker path recovers it
  either, the same "no admission path recovers it" verdict the identity
  batch already gave `aws_identitystore_group(_membership)`.

## Deferred, out of this batch's scope

AppStream is a deprecated AWS service and was never evaluated here — out
of scope by this batch's own recipe, not rejected on the merits.

WorkSpaces' directory and bundle surface stays out for a different reason:
`aws_workspaces_directory` is a real resource in the provider, but
`live/mapping.json` carries it via `"cfn-unmodeled"` ("real WorkSpaces
directory registration with no CFN model — the registry's four
`AWS::WorkSpaces::*` types carry no Directory type at all"), so
`tools/row-gen` — which walks the CFN registry — never proposes it.
`aws_workspaces_bundle` does not exist as a managed resource in the pinned
provider release at all (a data source only). Neither is a row-gen
proposal this batch could ratify or reject.

```

terraform apply -auto-approve

terraform destroy -auto-approve
docker rm -f tofu-connect-euc-cohort-verify
```

An `apply` against the pinned floci image above was run by hand during
ratification (not wired into any automated tier — see "Gating" above),
against the 26-type fixture this cohort had before the eight
`*_association` fold-children joined it (see the scope-drift note at the
top of this file); the eight were never separately exercised against
floci, but nothing in the earlier apply run suggests WorkSpacesWeb fares
any better for them than for the ten WorkSpacesWeb types already tried.
`_localstack/health` on this image lists neither `connect`, `workspaces`
nor `workspaces-web` among its running services at all — this batch's
three CFN services have no floci implementation whatsoever, wider than
every earlier batch's own gap (the identity batch's own two entirely
unimplemented services, Cognito Identity and SSO Admin, is the closest
precedent). Zero of the 26 types tried create and destroy cleanly:

- **Amazon Connect**: `aws_connect_instance.app`'s `CreateInstance` call
  is accepted, but the provider's post-create `DescribeInstance` wait
  fails (`serialization failed: input member InstanceId must not be
  empty`) — floci's create response never returns a usable instance id,
  so the resource never finishes creating. Every other Connect type in
  this cohort references `aws_connect_instance.app`'s own `arn`/`id`
  (directly or transitively through `aws_connect_user_hierarchy_structure.app`)
  and is never attempted as a result — Terraform skips a resource whose
  dependency failed rather than erroring it independently, the same
  dependency-skip shape the identity batch's own Cognito Identity and SSO
  Admin gaps found. `aws_connect_user_hierarchy_structure.app` was
  attempted independently regardless (it depends only on a literal
  `instance_id`, not the instance resource) and fails on its own:
  `UpdateUserHierarchyStructure` returns a non-JSON (HTML) response,
  effectively unimplemented.
- **WorkSpaces (the whole service) is absent**: `aws_workspaces_connection_alias.app`
  (`CreateConnectionAlias`), `aws_workspaces_ip_group.app`
  (`CreateIpGroup`) and `aws_workspaces_workspace.app`
  (`CreateWorkspaces`) all fail on `UnknownOperationException: Unknown
  operation` — the same "recognized as belonging to a real AWS API, but
  floci refuses it" shape the identity batch's own Cognito Identity gap
  found. `aws_workspaces_pool.app`'s `CreateWorkspacesPool` fails the same
  way once its own override supplies the required `capacity` block
  `terraform validate` does not catch (without the override, the failure
  is a same-shaped-but-different validation error from the AWS SDK's own
  client-side check, not floci's — both point at the same real
  requirement, confirmed against the provider's own Argument Reference).
- **WorkSpacesWeb is almost entirely absent**: `aws_workspacesweb_browser_settings.app`,
  `_data_protection_settings.app`, `_ip_access_settings.app`,
  `_network_settings.app`, `_portal.app`, `_session_logger.app`,
  `_user_access_logging_settings.app` and `_user_settings.app` all fail
  their respective `Create*` calls on a non-JSON (HTML) response — the
  same shape as the Connect hierarchy structure gap above, effectively
  unimplemented rather than explicitly refused. `aws_workspacesweb_trust_store.app`
  is the one exception: its `CreateTrustStore` call reaches real,
  well-formed validation logic (`missing required field,
  CreateTrustStoreInput.CertificateList`) — the one operation in the
  whole service floci's routing recognizes. `certificate` is genuinely
  Optional in the real provider's own Argument Reference, so this is a
  floci-specific accommodation this cohort's fixture does not adopt (the
  same "found by hand against floci, not a correctness compromise"
  category `aws_mq_broker`'s own `RABBITMQ` engine choice is in the
  streaming batch), left undone here since fabricating a placeholder PEM
  certificate body would not make the type any more real. Every
  `*_association` fold-child depends on `aws_workspacesweb_portal.app`
  (untried against floci directly, but skipped the same dependency-skip
  way if it were: the portal's own `CreatePortal` call is one of the
  eight non-JSON-response failures above).

None of this is evidence against any of the thirty-four types' admission:
identity and taggability are properties of the provider and the registry,
not of one emulator's completeness, the same standard every earlier
cohort's own "Verifying by hand" section states. It is, however, the
widest gap any batch in this campaign has found — every earlier batch
landed at least a partial floci surface; this one lands none.
