# observability cohort

Cohort: `observability`. Ratified by: the fifth registry-backed ratification
batch against #40's strategy and #44's row generator — the observability and
eventing remainder (CloudWatch, Logs, EventBridge/Events, Step Functions,
X-Ray, Grafana, RUM, Synthetics; issue #65's ratification campaign).
Mechanism: #48 (see `live/e2e/estates/example/README.md` for the
proof-of-mechanism cohort, and `live/e2e/estates/lambda/README.md` for the
first registry-backed cohort this one follows).

This cohort exercises every type this batch ratified into
`internal/live/lint/admission.go` and `internal/live/identity/table.go`.
Because those types come from eight different CloudFormation services
(CloudWatch, Logs, Events, StepFunctions, XRay, Grafana, RUM, Synthetics)
rather than one, `-types` was passed explicitly rather than letting
`tools/estate-gen`'s default `-cohort`-name-matches-CFN-service derivation
pick them up (that default only works for a single-service cohort; see
`tools/estate-gen/cohort.go`'s `defaultCohortTypes`).

Generated by `tools/estate-gen` (issue #56) from hashicorp/aws 6.58.0's schema and `internal/live/identity/table.go`'s identity table.

## Rejected, and out of scope

`tools/row-gen`'s CloudWatch, Logs, Events, StepFunctions, XRay, Grafana,
APS, RUM and Synthetics service sections proposed or evidenced far more than
this batch's 29 ratified types. What this batch declined, and why:

- `aws_cloudwatch_event_bus_policy` — row-gen filed this needs-hand-separator
  over the registry's composite `[EventBusName, StatementId]`. Independent
  verification against the provider's own Identity Schema and Argument
  Reference found a single-component identity (`event_bus_name` alone), but
  that argument is Optional in configuration — "if you omit this, the
  permissions are set on the `default` event bus" — so a real, valid
  configuration may carry no argument for the component to read at all. This
  is `live/survey-full.json`'s own `needs-config-signal` classification for
  this type (identity attrs settable but not required arguments), and the
  same missing-literal-default gap the messaging batch already declined for
  `aws_cloudwatch_event_rule`. Rejected, not deferred: the gap is a table
  mechanism this batch does not build, not missing evidence. Its documented
  synonym, `aws_cloudwatch_event_permission` (both map to the one CFN
  resource `AWS::Events::EventBusPolicy`, an allowlisted
  `mapping_gen_test.go` contradiction), ratifies instead — its own Identity
  Schema requires only `statement_id`, already a required argument.
- Amazon Managed Prometheus (`AWS::APS::*`, the `aws_prometheus_*` TF
  prefix) is deliberately untouched: issue #68's concurrent batch owns it.
  Admitting any of its nine types here too would be a straight collision on
  both `admittedTypesV0` and `DefaultTable`.
- Amazon Application Signals has no CloudFormation resource type in
  `live/mapping.json`'s roster at all (row-gen's service listing has no
  ApplicationSignals section), so there is no evidence to ratify or reject.
- `aws_sfn_alias` (a Step Functions state-machine alias) is out of this
  batch's named scope — "Step Functions remainder (activities)" — and is
  left for a future batch.
- Every `(property-child of ...)` fold row-gen filed evidence-only in this
  batch's services — `aws_cloudwatch_log_data_protection_policy`,
  `aws_cloudwatch_log_delivery_destination_policy`,
  `aws_cloudwatch_log_destination_policy`, `aws_cloudwatch_log_index_policy`,
  `aws_cloudwatch_event_target`, `aws_grafana_workspace_saml_configuration`
  and `aws_synthetics_group_association` — is deferred for the same reason
  the ApiGateway batch's method/response children were: admitting a
  property-child needs a parent-derived admission mechanism this table does
  not have yet, the same gap `aws_prometheus_alert_manager_definition` and
  its APS siblings are waiting on upstream.
- Several evidence-only rows corrected into ratified ones instead of staying
  rejected: `aws_cloudwatch_alarm_mute_rule`, `aws_cloudwatch_contributor_insight_rule`
  and `aws_xray_sampling_rule` were each filed evidence-only because the
  registry's own primaryIdentifier is a read-only ARN, but each provider doc
  disagrees — the same correction shape the messaging batch's
  `aws_sns_topic_policy` and the RDS batch's five corrections already
  established.

See `internal/live/identity/table.go`'s own comment block for this batch
(search "fifth batch, observability") for the full per-type evidence trail.

## Untaggable types

Fourteen of the twenty-nine rows above carry no `tags` argument in the AWS
provider, confirmed against each type's documented Argument Reference:
`aws_cloudwatch_otel_enrichment` (a per-region singleton with no arguments
at all beyond the optional `region`), `aws_cloudwatch_log_account_policy`,
`aws_cloudwatch_log_metric_filter`, `aws_cloudwatch_log_resource_policy`,
`aws_cloudwatch_log_stream`, `aws_cloudwatch_log_subscription_filter`,

`aws_cloudwatch_event_api_destination`, `aws_cloudwatch_event_archive`,
`aws_cloudwatch_event_connection`, `aws_cloudwatch_event_endpoint`,
`aws_cloudwatch_event_permission` and `aws_xray_resource_policy` — the same
shape the Lambda batch's `aws_lambda_layer_version`, the messaging batch's
`aws_cloudwatch_dashboard`, and the Route53/CloudFront batch's eight
untaggable rows already established. All fourteen are added to
`internal/live/stamp/stamp_test.go`'s `untaggableAdmittedTypes` pin, and
`live/LIMITATIONS.md`'s "Untaggable types cannot be removed by the sweep"
entry picks them up mechanically through
`go run ./tools/survey-gen -render`, which derives that entry from
`live/survey-full.json` (the full registry-backed roster) intersected with
the admission table, not from a hand edit here.

## Verifying by hand

```
docker run -d --rm -p 4620:4566 --name tofu-observability-cohort-verify ghcr.io/lex00/floci:latest
export AWS_ENDPOINT_URL=http://localhost:4620 AWS_ACCESS_KEY_ID=test \
       AWS_SECRET_ACCESS_KEY=test AWS_REGION=us-east-1

terraform init
terraform validate
terraform apply -auto-approve

terraform destroy -auto-approve
docker rm -f tofu-observability-cohort-verify
```

An `apply` against `ghcr.io/lex00/floci:latest` was run by hand during
ratification (not wired into any automated tier — see "Gating" above).
Three of the twenty-nine ratified types created and destroyed cleanly:
`aws_cloudwatch_event_bus.app`, `aws_cloudwatch_event_archive.app` and
`aws_cloudwatch_event_permission.app` (plus the supporting
`aws_iam_role.observability`). The rest split two ways, neither of which is
evidence against admission — identity and enumeration are properties of the
provider and the registry, not of one emulator's completeness, the same
stance the Lambda and messaging batches' own floci gaps already took:

- **Explicit floci gaps** (the emulator returns `UnsupportedOperation`, or
  the service is unimplemented and the emulator's routing layer returns an
  HTML error page instead of a JSON one — "deserialization failed ...
  invalid character '<'"): `aws_cloudwatch_alarm_mute_rule`,
  `aws_cloudwatch_contributor_insight_rule`,
  `aws_cloudwatch_event_connection`, `aws_cloudwatch_event_endpoint`,
  `aws_cloudwatch_log_anomaly_detector`,
  `aws_cloudwatch_log_delivery_destination`,
  `aws_cloudwatch_log_delivery_source`, `aws_cloudwatch_log_destination`,
  `aws_cloudwatch_log_resource_policy`, `aws_cloudwatch_log_transformer`,
  `aws_cloudwatch_otel_enrichment`, `aws_grafana_workspace`,
  `aws_rum_app_monitor`, `aws_synthetics_canary`, `aws_synthetics_group`,
  `aws_xray_group`, `aws_xray_resource_policy` and
  `aws_xray_sampling_rule`. `/_localstack/health` does not list `grafana`,
  `rum`, `synthetics` or `xray` among its services at all (confirmed by
  reading the health response directly), so those seven fail before ever
  reaching type-specific logic; `events`, `logs` and `monitoring` are listed
  as `running` but several of their operations (`PutAlarmMuteRule`,
  `PutInsightRule`, `CreateConnection`, `CreateEndpoint`,
  `PutDeliveryDestination`/`PutDeliverySource`/`PutDestination`/
  `PutResourcePolicy`/`PutTransformer`, `StartOTelEnrichment`) are not
  implemented behind that "running" status — the same "presence, not
  completeness" split the messaging batch's CloudWatch trio found.
- **Not independently exercised**, skipped by Terraform's own dependency
  graph because each references an attribute of a type in the first group
  above: `aws_cloudwatch_log_account_policy` (references
  `aws_cloudwatch_log_resource_policy.app.policy_name`),
  `aws_cloudwatch_log_delivery` (references both
  `aws_cloudwatch_log_delivery_destination.app.arn` and
  `aws_cloudwatch_log_delivery_source.app.name`),
  `aws_cloudwatch_query_definition`, `aws_cloudwatch_log_metric_filter`,
  `aws_cloudwatch_log_stream` and `aws_cloudwatch_log_subscription_filter`
  (the generic pass points their own `name` argument at
  `aws_cloudwatch_alarm_mute_rule.app.name`, a same-shaped cross-reference
  `tools/estate-gen` wires whenever two admitted types share an argument
  name), `aws_sfn_activity` (same), and `aws_cloudwatch_event_api_destination`
  (references `aws_cloudwatch_event_connection.app.arn`). Each of these
  types' own identity and required-argument shape passed `terraform
  validate` cleanly; only the emulator coverage of what they reference was
  never reached.

Two genuine configuration bugs turned up during this apply and are now
fixed in `tools/estate-gen/overrides.go` rather than left as floci gaps:
`aws_cloudwatch_alarm_mute_rule`'s `rule { schedule { ... } }` block and
`aws_cloudwatch_event_endpoint`'s `routing_config.failover_config.primary.health_check`/
`secondary.route` are both required in practice but typed as
zero-`MinItems` blocks in the wire schema, so `terraform validate` never
caught their absence — only the real `apply` against floci did (see the
Provenance table above for each fix). Once fixed, both types progressed
past their own configuration and failed only on the emulator's
`UnsupportedOperation` response, confirmed by rerunning the apply after each
fix.
