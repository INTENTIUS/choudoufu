# data cohort

Cohort: `data`. Ratified by: the fourth registry-backed ratification batch
against #40's strategy and #44's row generator, issue #65's recipe — the
data-plane services (Kinesis, KinesisFirehose, Glue, Athena). Mechanism:
#48 (see `live/e2e/estates/example/README.md` for the proof-of-mechanism
cohort, and `live/e2e/estates/lambda/README.md` for the first
registry-backed cohort this one follows). Generated by `tools/estate-gen`
(issue #56) from hashicorp/aws 6.58.0's schema and
`internal/live/identity/table.go`'s identity table.

This cohort exercises every type this batch ratified into
`internal/live/lint/admission.go` and `internal/live/identity/table.go`.

Regenerate with:

```
go run ./tools/estate-gen -cohort data -out live/e2e/estates/data
```

## Rejected, and deferred, and out of this batch's named scope

`tools/row-gen`'s Kinesis, KinesisFirehose, Glue and Athena sections
proposed pastable rows well beyond issue #65's named scope (Kinesis streams
and consumers, Firehose delivery streams, Glue catalog database/table plus
registries/jobs/crawlers/connections, and Athena workgroups/data
catalogs/named queries). Fourteen are ratified above (`aws_kinesis_stream`
and `aws_kinesis_stream_consumer` fill the Kinesis pair; the fifteenth,
`aws_kinesis_firehose_delivery_stream`, is Firehose's whole slice). Three
more were independently verified and rejected outright, not deferred:

- `aws_athena_named_query` — row-gen proposed server-assigned via the
  registry's opaque `NamedQueryId`, and the provider agrees: the documented
  import command uses the query ID, which no argument reconstructs. Unlike
  this table's singleton-per-account rows (`aws_ecr_registry_policy`,
  `aws_glue_data_catalog_encryption_settings` above), a named query is not
  a singleton — many exist per workgroup — and the pinned provider's wire
  schema confirms it carries no `tags` argument and no native list
  resource either. None of the four admission paths recovers a
  pre-existing instance; `live/survey-full.json`'s own classifier reaches
  the same "moves to Ops" verdict for exactly this reason.
- `aws_glue_schema` — row-gen proposed server-assigned via the registry's
  `Arn`, and the provider's documented import command confirms an ARN
  (`arn:aws:glue:REGION:ACCOUNT:schema/REGISTRY_NAME/SCHEMA_NAME`) — but
  unlike `aws_glue_registry` above, `REGISTRY_NAME` is not reconstructable:
  the resource's only registry reference is `registry_arn` (the parent's
  full ARN string), and the pinned provider's wire schema shows
  `registry_name` is computed-only, never settable. Parsing a bare name out
  of a parent ARN string needs a component this table's vocabulary does
  not have.
- `aws_glue_partition` — otherwise fully reconstructable
  (`catalog_id:database_name:table_name:` plus the joined partition
  values), except `partition_values` is a required `list(string)` argument
  the pinned provider's wire schema confirms is joined into the import
  string with `#`. This table's Components vocabulary has no list-join
  primitive.

Everything else `tools/row-gen` proposed or surfaced as evidence in these
four services is outside issue #65's named scope, not rejected on the
merits — left for a future batch:

- `aws_kinesis_resource_policy` — proposed cleanly (client-named via
  `resource_arn`), but the recipe scopes Kinesis to streams and consumers.
- `aws_kinesis_analytics_application`, `aws_kinesisanalyticsv2_application`,
  `aws_kinesis_video_stream` — different CFN services (KinesisAnalytics,
  KinesisAnalyticsV2, KinesisVideo), not Kinesis or KinesisFirehose.
- `aws_glue_catalog` — a distinct, newer top-level "Catalog" resource
  (federated catalog registration), easily confused by name with
  `aws_glue_catalog_database`/`aws_glue_catalog_table` but a different
  concept; the recipe names only "catalog database/table". Its own
  identity schema (`required=[name]`) would make it a clean pickup later.
- `aws_glue_catalog_table_optimizer`, `aws_glue_dev_endpoint`,
  `aws_glue_security_configuration`, `aws_glue_user_defined_function`,
  `aws_glue_workflow`, `aws_glue_data_quality_ruleset` — evidence-only per
  row-gen. `aws_glue_catalog_table_optimizer` looks fully reconstructable
  on inspection (`catalog_id,database_name,table_name,type`, no list-join
  needed) — a plausible pickup for a future batch.
- `aws_athena_capacity_reservation`, `aws_athena_prepared_statement` —
  needs-hand-separator and evidence-only respectively.

## Untaggable types

Three types in the table above carry no `tags` argument in the pinned
provider's wire schema: `aws_glue_catalog_table`, `aws_glue_classifier` and
`aws_glue_data_catalog_encryption_settings`. All three follow the Lambda
batch's `aws_lambda_layer_version` and the messaging batch's
`aws_cloudwatch_dashboard`: they are added to
`internal/live/stamp/stamp_test.go`'s `untaggableAdmittedTypes` list and,
because `live/LIMITATIONS.md`'s "Untaggable types cannot be removed by the
sweep" entry is now derived from the full registry roster rather than the
curated 68 (issue #54 landed since the messaging batch), regenerating that
doc with `go run ./tools/survey-gen -render` picks all three up
automatically — no hand edit to the doc itself.

## Verifying by hand

```
docker run -d --rm -p 4631:4566 --name tofu-data-cohort-verify \
  ghcr.io/lex00/floci@sha256:4753246c0260a22af1056c65993f4d73b0a907729a9580b9baba5d628b6dad34
export AWS_ENDPOINT_URL=http://localhost:4631 AWS_ACCESS_KEY_ID=test \
       AWS_SECRET_ACCESS_KEY=test AWS_REGION=us-east-1

terraform init
terraform validate
terraform apply -auto-approve

terraform destroy -auto-approve
docker rm -f tofu-data-cohort-verify
```

`terraform validate` passes against the real provider release (6.58.0) this
fixture pins — confirming every argument name above is real, not just
registry-plausible. An `apply` was run by hand against the pinned floci
image (`ghcr.io/lex00/floci`, the digest `internal/live/flocitest` pins,
not `floci/floci:latest`) during ratification, not wired into any automated
tier — see "Gating" above. The recipe's own hint ("floci historically
serves kinesis and glue basics") holds, with more nuance once the emulator
is actually driven:

- `aws_kinesis_stream.app`, `aws_kinesis_firehose_delivery_stream.app` and
  `aws_glue_registry.app` create, tag round-trip and destroy cleanly.
- `aws_kinesis_stream_consumer.app`, `aws_glue_catalog_database.app` and
  `aws_athena_workgroup.app` create cleanly (the provider's `SetId` call
  succeeds and Terraform's own error-recovery keeps the partial state
  rather than losing the object) but the very next read — the tag
  round-trip every taggable type's create cycle does — fails: floci's
  `RegisterStreamConsumer`/`ListTagsForResource` pair for Kinesis stream
  consumers, `CreateDatabase`/`GetTags` pair for Glue databases, and
  `CreateWorkGroup`/`ListTagsForResource` pair for Athena workgroups each
  implement the write half and not the matching read. The Glue case is the
  most specific: floci's `GetTags` handler recognizes only Registry and
  Schema ARNs (`InvalidInputException: Resource ARN does not point to a
  Registry or Schema`) and rejects a Database ARN outright, confirmed by
  probing `aws glue get-tags --resource-arn arn:...:database/...` directly.
  This is a floci gap (`choudoufu#26` territory), not evidence against any
  of the three types' admission — identity and enumeration are properties
  of the provider and the registry, not of one emulator's completeness.
- `aws_glue_catalog_table.app` was never reached through this apply — its
  `database_name` argument refers to `aws_glue_catalog_database.app`,
  whose own apply step errored above, and Terraform will not proceed past
  an unresolved reference. Probed directly instead
  (`aws glue create-table --database-name ... --table-input Name=...`
  against the same running container): creates cleanly.
- `aws_glue_job.app`, `aws_glue_crawler.app`, `aws_glue_connection.app`,
  `aws_glue_classifier.app`, `aws_glue_data_catalog_encryption_settings.app`
  and `aws_athena_data_catalog.app` fail outright at create
  (`CreateJob`/`CreateCrawler`/`CreateConnection`/`CreateClassifier`/
  `PutDataCatalogEncryptionSettings`/`CreateDataCatalog`, each
  `InvalidAction: Action ... is not supported`) — floci's
  `/_localstack/health` reports `glue: running` and `athena: running`, but
  only the operations above are missing, the same "presence, not
  completeness" split the Lambda and messaging batches found for
  CloudWatch.
- `aws_glue_trigger.app` and `aws_glue_ml_transform.app` were likewise
  never reached (blocked on `aws_glue_job.app` and on
  `aws_glue_catalog_database.app`/`aws_glue_catalog_table.app`
  respectively). Probed directly instead
  (`aws glue create-trigger`/`aws glue create-ml-transform` against the
  same container): both fail the same way,
  `InvalidAction: Action CreateTrigger/CreateMLTransform is not supported`.

None of the create failures above is evidence against the types' admission
either. `live/registry.json`'s own `handlers` field — the CFN Registry's
declared create/read/update/delete/list support, independent of any
emulator — names `AWS::Glue::Connection`, `AWS::Glue::Classifier`,
`AWS::Glue::MLTransform`, `AWS::Glue::Table` and
`AWS::Glue::SecurityConfiguration` as carrying **no CloudFormation handler
at all** (`{"create": false, "read": false, "update": false, "delete":
false, "list": false}`), the "handler-less laggards" issue #65's recipe
flagged in advance. That axis is orthogonal to floci's own coverage,
though: `AWS::Glue::Table` is handler-less in the registry yet floci's
native Glue API creates a table fine (Terraform calls the native SDK
directly, never through CloudFormation), while `AWS::Glue::Job`,
`AWS::Glue::Crawler` and `AWS::Glue::Trigger` all carry full CloudFormation
handler support yet floci does not implement their native create calls at
all. The registry's handler field and floci's emulated surface are two
independent gaps that happen to overlap on `Connection`, `Classifier` and
`MLTransform` and diverge everywhere else — neither one bears on whether
this batch's identity evidence is correct.

Destroying the fully- and partially-created resources (`terraform destroy
-auto-approve -refresh=false`, since a plain refresh re-runs the same
failing tag reads) removed all seven objects cleanly before the container
came down.
