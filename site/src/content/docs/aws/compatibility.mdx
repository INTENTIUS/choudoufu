```
choudoufu live-check
```

It needs no credentials and makes no cloud calls. Each refusal names the block, the rule and the fix. Most refusals come from one rule: a marker must be known before the resource exists, so whatever names it must come from your configuration alone.

## The backend

A `backend` or `cloud` block is refused. The markers are the record of ownership, so a backend would be a second one. Workspaces other than `default` and `force-unlock` are refused too.

## Expansions and identity arguments

`count` and `for_each` over variables, locals, data sources or a sibling's attribute work. Refused: expansion over a module output, a `for_each` keyed by a parent's live id, and a name from `uuid()`, `timestamp()`, a `sensitive` variable or a generated prefix.

## Resource types

Every type the AWS provider ships is admitted. Three types that mint credentials are excluded. [READINESS.md](https://github.com/INTENTIUS/choudoufu/blob/main/live/READINESS.md) lists every type by tier.

## Running it

`plan -out` then `apply <planfile>` works, and so does `-target`. Without a `live` block you get stock behaviour.

## Other providers

A resource from another provider is admitted when its identity resolves from configuration, and refused as `unadmitted-type` when it does not, as with `github_*` and `fastly_*`. [Kubernetes](/choudoufu/kubernetes/compatibility/) has its own marker. [COMPATIBILITY.md](https://github.com/INTENTIUS/choudoufu/blob/main/live/COMPATIBILITY.md) has every construct, and [LIMITATIONS.md](https://github.com/INTENTIUS/choudoufu/blob/main/live/LIMITATIONS.md) every refusal with its fix.
